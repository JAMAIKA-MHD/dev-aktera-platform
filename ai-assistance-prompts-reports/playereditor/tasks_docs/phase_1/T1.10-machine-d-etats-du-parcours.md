## 1. Objectif

Décrire **tout le parcours du joueur** (accueil → inscription → jeu → tirage → résultat, erreurs comprises) dans une fonction **pure**, testable sans interface ni réseau. C'est le cœur de la logique métier. L'écran (phase 4) ne fera qu'**afficher l'état** et **envoyer des événements**.

Le principe : `flowReducer(état, événement) → nouvel état`. Même état et même événement donnent toujours le même résultat : pas d'appel réseau, pas d'horloge, pas de hasard.


## 5. Le code expliqué

### 5.1 Le parcours

```
welcome ──START──► register ──SUBMIT──► play
                                         │
      roue, carte à gratter : DRAW_STARTED (le joueur lance la roue / commence à gratter)
      quiz, boîtes, Hit It  : INTERACTION_DONE(réponses, boîte choisie, touches)
                                         │
                                         ▼
                                     resolving ──RESOLVED──► revealing ──REVEAL_DONE──► win | lose
                                         │
                                       FAILED
            ┌──────────────┬─────────────┼──────────────────┐
     ALREADY_PARTICIPATED  CAMPAIGN_CLOSED  INVALID_INPUT   NETWORK / UNKNOWN
            ▼              ▼             ▼                  ▼
        duplicate        closed       register            error ──RETRY──► resolving
```

| Écran                            | Ce que voit le joueur                                                          |
| -------------------------------- | ------------------------------------------------------------------------------ |
| `welcome`                        | Accueil avec l'accroche du jeu                                                 |
| `register`                       | Formulaire et consentement                                                     |
| `play`                           | Le jeu, prêt (roue à l'arrêt, questions, boîtes, cible)                        |
| `resolving`                      | Tirage en cours sur le serveur                                                 |
| `revealing`                      | Le jeu montre le résultat reçu (la roue tourne vers le lot, la boîte s'ouvre…) |
| `win` / `lose`                   | Résultat                                                                       |
| `duplicate` / `closed` / `error` | Déjà joué / campagne terminée / problème technique                             |

**Réconciliation avec le plan.** Le diagramme du plan §6.1 tirait la roue **dès l'inscription** (`register → resolving`), puis revenait à `play` pour l'animation. La fiche T1.10, plus récente, définit l'écran `revealing` et l'événement `DRAW_STARTED`, et la fiche T5.2 précise : « la rotation démarre **quand `phase` passe à `revealing`** ; le CTA et le clic sur la roue émettent le même événement ». J'ai donc suivi la fiche : le tirage part quand le joueur **lance** la roue (ou commence à gratter), puis l'animation atterrit sur le résultat reçu. Les deux familles de jeux suivent alors **le même chemin**, `play → resolving → revealing → résultat`, et seul l'événement qui déclenche le tirage change.

« Tirage avant l'animation » reste vrai : le résultat est connu **avant** que la roue tourne (`revealing`). Il ne l'est simplement pas avant que le joueur appuie.

### 5.2 Le moment du tirage est vérifié

| Timing                                     | Événement accepté dans `play` | Charge envoyée (`gamePayload`)          | Événement refusé   |
| ------------------------------------------ | ----------------------------- | --------------------------------------- | ------------------ |
| `before-animation` (roue, grattage)        | `DRAW_STARTED`                | `{ kind: "none" }`                      | `INTERACTION_DONE` |
| `after-interaction` (quiz, boîtes, Hit It) | `INTERACTION_DONE(payload)`   | Celle du jeu (réponses, boîte, touches) | `DRAW_STARTED`     |

Un événement du mauvais type est **ignoré** : un moteur défaillant ne peut pas lancer un tirage sans les données attendues.

**Quiz sans question** (noté en T1.3). En production, un quiz sans question part directement au tirage, comme une roue. `outcomeTimingFor(campaign)` reproduit ce comportement : un quiz sans question reçoit le timing `before-animation`. Le champ `timing` de l'état, déjà prévu par la fiche, le porte. Côté serveur, la RPC calcule alors un score de 0 : le joueur perd, sauf seuil à 0. Le Studio signalera ce cas comme une erreur (T1.11).

### 5.3 L'inscription et `canSubmit`

`canSubmit(état, formulaire)` est vrai seulement si :

1. le **consentement** est coché (loi 18-07, jamais pré-coché : l'état initial est `false`) ;
2. le **téléphone** est un mobile algérien valide (`isValidDzMobile`, T1.2 : `05…`, `06…`, `07…`, avec espaces, tirets ou `+213`), **même si** le formulaire le déclare désactivé ou facultatif (clé anti-doublon, règle N4) ;
3. chaque champ **activé et obligatoire** est rempli (espaces seuls = vide) ;
4. l'email, s'il est activé **et** saisi, a une forme valide.

L'écran utilisera la même fonction pour griser le bouton. `SUBMIT` ne fait **rien** si `canSubmit` est faux.

**Horodatage du consentement.** `SET_CONSENT` porte l'heure (`at`), gardée dans `consentAcceptedAt` ; décocher l'efface. Le hook en fera le `ConsentRecord` (T1.5) envoyé avec la participation.

### 5.4 Les erreurs

| Code (T1.5)            | Écran          | Pourquoi                                                                                                                               |
| ---------------------- | -------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `ALREADY_PARTICIPATED` | `duplicate`    | Le serveur refuse un 2ᵉ essai pour ce numéro                                                                                           |
| `CAMPAIGN_CLOSED`      | `closed`       | Campagne terminée ou introuvable                                                                                                       |
| `INVALID_INPUT`        | **`register`** | Le joueur corrige ses informations (elles sont gardées, l'erreur est affichée) ; le prochain `SUBMIT` ouvre une **nouvelle** tentative |
| `NETWORK`, `UNKNOWN`   | `error`        | Problème technique : `RETRY` possible                                                                                                  |

**`RETRY`** n'est accepté que depuis `error`, pour une erreur réessayable, et **réutilise le même `clientRequestId` et la même charge**. Si la première requête a en fait abouti côté serveur, la seconde ne compte pas un deuxième essai.

### 5.5 Robustesse : les événements tardifs

Chaque événement n'est accepté **que sur son écran**. Sinon, le reducer renvoie **le même objet état**, inchangé. Conséquences :

- une réponse du serveur qui arrive **après** un `RESTART` est ignorée ;
- un double appui (deux `SUBMIT`, deux `CONFIRM_COUPON`) ne produit qu'un effet ;
- React ne redessine rien, puisque l'état est le même objet.

`RESTART` est **refusé** pendant `resolving` et `revealing` : on ne jette pas un tirage en cours ou en train d'être montré.

### 5.6 `RESTART` et le coupon

**`RESTART`** ramène à l'accueil depuis tous les autres écrans (gain, perte, déjà joué, fermé, erreur, jeu). Il **garde** les informations déjà saisies (nom, téléphone…), `startedAt` et le timing. Il **efface** la tentative : consentement (à redonner), identifiant de requête, charge, résultat, erreur. Une nouvelle participation avec le même numéro est refusée par le serveur (`ALREADY_PARTICIPATED`) : `RESTART` ne contourne jamais l'anti-doublon (règle N4).

**`CONFIRM_COUPON`** (« J'ai copié mon code ») n'est accepté que sur l'écran de gain, avec un code et une participation connue, et une seule fois.

### 5.7 `nextCommand` : les effets à lancer

Le reducer ne fait aucun appel. Après chaque transition, `nextCommand(avant, après)` dit au hook (T4.1) quoi faire :

| Retour      | Quand                                                    | Le hook fait                                                                                                           |
| ----------- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `"DRAW"`    | On **entre** dans `resolving` (premier essai ou `RETRY`) | Appelle la passerelle avec l'état (participant, consentement, charge, identifiant), puis envoie `RESOLVED` ou `FAILED` |
| `"CONFIRM"` | `couponConfirmed` passe à vrai                           | Appelle `confirmCoupon(entryId)`                                                                                       |
| `null`      | Sinon                                                    | Rien                                                                                                                   |

### 5.8 Pureté

Aucune lecture d'horloge, aucun hasard, aucun réseau dans le reducer :

- l'heure de début est donnée à la création (`createInitialFlowState(jeu, { startedAt })`) ;
- l'heure du consentement arrive avec `SET_CONSENT` ;
- l'identifiant de requête arrive avec `SUBMIT` (créé par le hook avec `createClientRequestId`, T1.5).

Un test le **prouve** : il espionne `Date.now`, `Math.random` et `crypto.randomUUID` pendant un parcours complet (avec erreur, `RETRY`, gain, coupon, `RESTART`). Aucun n'est appelé, et l'état de départ n'est pas modifié.

## 6. Décisions et alternatives

| Décision                                                      | Alternative écartée                          | Raison                                                                                                                    |
| ------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Tirage au lancement (`DRAW_STARTED`), puis `revealing`        | Tirage dès l'inscription (diagramme du plan) | Fiches T1.10 et T5.2 ; un seul chemin pour tous les jeux                                                                  |
| `SUBMIT` porte `form` et `clientRequestId`                    | `{ type: "SUBMIT" }` seul (fiche)            | Sans le formulaire, le reducer ne peut pas appliquer `canSubmit` ; sans l'identifiant, il devrait tirer au hasard (impur) |
| `SET_CONSENT` porte `at`                                      | Horodatage par le hook au moment de l'envoi  | Loi 18-07 : l'heure du consentement, pas celle de l'envoi ; reducer pur                                                   |
| `consentAcceptedAt` et `gamePayload` ajoutés à l'état         | État de la fiche strictement                 | Nécessaires pour construire la requête et pour `RETRY`                                                                    |
| `createInitialFlowState(jeu, { startedAt, timing? })`         | `createInitialFlowState(jeu)` (fiche)        | Pas de `Date.now()` caché ; `timing` pour le quiz sans question                                                           |
| `INVALID_INPUT` → formulaire                                  | Écran d'erreur générique                     | Le joueur peut corriger son numéro au lieu d'être bloqué                                                                  |
| `RESTART` garde les informations saisies, pas le consentement | Tout effacer / tout garder                   | Fiche (« sans effacer les données déjà envoyées ») ; le consentement vaut pour une participation                          |
| Événements hors écran ignorés (même objet)                    | Lever une erreur                             | Les réponses tardives et les doubles appuis sont normaux sur mobile                                                       |

## 9. Écarts, imprévus et points d'attention

- **Événements et état enrichis** par rapport à la fiche (§6) : `SUBMIT` (`form`, `clientRequestId`), `SET_CONSENT` (`at`), `consentAcceptedAt`, `gamePayload`, second paramètre de `createInitialFlowState`. Tous découlent de l'exigence de pureté de la fiche.
- **Écart au diagramme du plan §6.1** (§5.1) : le tirage part au lancement, pas à l'inscription. Conséquence produit : un joueur qui s'inscrit puis **quitte sans jouer** n'a **pas** consommé sa participation (en production actuelle, pour la roue, si). À toi de dire si tu préfères l'inverse.
- **Quiz sans question** : traité comme en production (§5.2). Un comportement plus protecteur, afficher « jeu indisponible », est possible si tu le préfères.
- **Correction des erreurs de champ** : `canSubmit` dit seulement « oui / non ». Les messages par champ (« numéro invalide »…) seront calculés dans le formulaire (T4.2).
- **Journaux de T1.7, T1.8 et T1.9 recalés** sur les heures réelles des commits (17:11, 17:28, 17:42). Les heures avaient été estimées trop tard.

## 10. Qualité visuelle

Sans interface ici, mais deux choix protègent directement l'expérience :

- **pas d'impasse** : chaque écran final propose une sortie (`RESTART`, `RETRY`, retour au formulaire) ;
- **pas de double effet** : un double appui ou une réponse tardive ne fait ni sauter ni clignoter l'écran.
