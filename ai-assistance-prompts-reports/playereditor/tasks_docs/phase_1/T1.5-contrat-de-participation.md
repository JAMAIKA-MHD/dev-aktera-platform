## 1. Objectif

Fixer le **contrat** des échanges avec la « source d'autorité » qui tire les lots :

- ce qu'on lui envoie : `DrawRequest` ;
- ce qu'elle répond : `DrawResult` ;
- les erreurs possibles et leurs messages pour le joueur.

Ce contrat est calqué sur `select-prize`. Ainsi, la **passerelle de démonstration** du MVP (T2.4) et la **future passerelle Supabase** (après le MVP) pourront s'échanger sans que le runtime ni le Studio changent (règle A4).

## 5. Le code expliqué

### Ce qu'on envoie : `ConsentRecord`, `GamePayload`, `DrawRequest`

```ts
export interface ConsentRecord {
  accepted: true; // a participation without consent is never sent
  acceptedAt: string; // ISO 8601
  policyVersion: string;
  locale: Locale;
}
```

- **`accepted: true`** est un type littéral : il est **impossible** de construire une participation avec `accepted: false`. Le consentement est une condition préalable, pas une option (règle N3, loi 18-07).
- La date, la version de la politique et la langue permettent de prouver **à quel texte** le joueur a consenti, et quand.

```ts
export type GamePayload =
  | { kind: "none" } // wheel, scratch card: drawn before the animation
  | { kind: "quiz"; answers: Record<string, number> } // question id → option index, database order
  | { kind: "boxes"; selectedIndex: number }
  | { kind: "hitIt"; hits: number };
```

- **Une union « discriminée » par `kind`** : TypeScript sait, selon `kind`, quels champs existent. Chaque jeu envoie exactement ce dont le serveur a besoin (tableau des moments du tirage, T1.3).
- **`answers`** associe un identifiant de question à un **index d'option dans l'ordre de la base** : une traduction ne peut pas changer la réponse envoyée (règle B10).

```ts
export interface DrawRequest {
  clientRequestId: string; // reused on retry so the same attempt is never counted twice
  campaignId: string;
  participant: {
    phone: string;
    fullName?: string;
    email?: string;
    wilaya?: string;
  }; // phone normalized
  consent: ConsentRecord;
  gamePayload: GamePayload;
  humanToken: string | null; // captcha token; null until a HumanVerification adapter exists
  context: {
    sessionId: string;
    dwellTimeSeconds: number;
    userAgent: string;
    source: "studio_preview" | "demo" | "web_player";
  };
}
```

- **`clientRequestId`** : identifiant unique de la tentative. En cas de coupure réseau, le « Réessayer » renvoie **le même** identifiant. La passerelle de démo (T2.4) s'en sert déjà pour ne pas compter deux fois la même tentative ; le serveur pourra faire de même plus tard (plan §12.2).
- **`participant.phone`** : toujours le numéro normalisé par `normalizeDzPhone` (T1.2).
- **`context.source`** distingue l'aperçu du Studio, la démo et la vraie page joueur, pour les statistiques et pour la sécurité (plan §7.4).

### Ce qu'on reçoit : `DrawOutcome` et `DrawResult`

```ts
export interface DrawOutcome {
  isWinner: boolean;
  prize: DrawPrize | null;
  couponCode: string | null;
}

export type DrawResult =
  | { ok: true; entryId: string; outcome: DrawOutcome }
  | { ok: false; error: ParticipationError };
```

- **`DrawResult`** reprend la forme de la réponse du serveur (`ok: true` ou `ok: false`). Avec `if (result.ok)`, TypeScript sait si l'on a un `outcome` ou une `error` : impossible de lire un lot sur une réponse en erreur.
- **`DrawOutcome`** est exactement ce que la machine d'états transmet au moteur de jeu : gagné ou non, quel lot, quel code. **Le moteur ne décide rien, il reçoit** (règle N1).
- **`entryId`** sert ensuite à confirmer la copie du code (`confirm-coupon`).

### Les erreurs : `ParticipationErrorCode` et `isRetryable`

```ts
// ALREADY_PARTICIPATED and CAMPAIGN_CLOSED are the codes select-prize returns.
// The other three are produced on the client side.
export type ParticipationErrorCode =
  | "ALREADY_PARTICIPATED"
  | "CAMPAIGN_CLOSED"
  | "INVALID_INPUT"
  | "NETWORK"
  | "UNKNOWN";

// Only technical failures may be retried: a business refusal would fail the same way again.
export function isRetryable(code: ParticipationErrorCode): boolean {
  return code === "NETWORK" || code === "UNKNOWN";
}
```

| Code                   | Origine                         | Écran joueur           | Réessayer ?                             |
| ---------------------- | ------------------------------- | ---------------------- | --------------------------------------- |
| `ALREADY_PARTICIPATED` | Serveur (`select-prize` l. 212) | « Déjà participé »     | Non : le résultat serait le même        |
| `CAMPAIGN_CLOSED`      | Serveur (l. 251)                | « Campagne terminée »  | Non                                     |
| `INVALID_INPUT`        | Client                          | Retour au formulaire   | Non : il faut corriger la saisie        |
| `NETWORK`              | Client (coupure, délai)         | Erreur + « Réessayer » | **Oui**, avec le même `clientRequestId` |
| `UNKNOWN`              | Client (réponse inattendue)     | Erreur + « Réessayer » | **Oui**                                 |

`isRetryable` sera utilisé par la machine d'états (T1.10) et par l'écran d'erreur (T4.3) pour afficher ou non le bouton « Réessayer ».

### Les messages : `PARTICIPATION_ERROR_MESSAGES`

Un message par code, en **français, arabe et anglais** : des valeurs de contenu joueur, seule exception autorisée à la règle R0. Ils sont écrits pour le joueur, sans jargon technique (« Connexion impossible. Vérifiez votre réseau et réessayez. »), conformément à la règle D12 (des erreurs dites avec un message humain).

### `createClientRequestId` et `uuid.ts`

```ts
// crypto.randomUUID only exists in secure contexts (https, localhost). The dev server is also
// reached over plain http on the local network (host 0.0.0.0), so fall back to getRandomValues.
export function createUuid(): string {
  if (typeof crypto.randomUUID === "function") return crypto.randomUUID();
  const bytes = crypto.getRandomValues(new Uint8Array(16));
  bytes[6] = (bytes[6] & 0x0f) | 0x40; // version 4
  bytes[8] = (bytes[8] & 0x3f) | 0x80; // RFC 4122 variant
  // … mise en forme 8-4-4-4-12
}
```

**Imprévu important, évité.** La fiche demande `crypto.randomUUID()`. Or les navigateurs ne fournissent cette fonction que dans un **contexte sécurisé** : `https` ou `localhost`. Le serveur de développement tourne sur `0.0.0.0` (règle N6), justement pour être ouvert depuis un téléphone ou une VM **par l'adresse IP du réseau local, en `http`**. Dans ce cas, `crypto.randomUUID` n'existe pas, et la page planterait au premier « Participer ».

`createUuid` utilise donc `crypto.randomUUID` quand il existe, et sinon construit un UUID v4 standard à partir de `crypto.getRandomValues`, disponible partout. Les deux lignes de masques de bits posent la « version 4 » et la « variante RFC 4122 » exigées par le format.

Il vit dans son propre fichier, car T1.8 en aura aussi besoin pour l'identifiant de chaque configuration.

## 6. Décisions et alternatives

| Décision                                       | Alternative écartée                             | Raison                                                                                   |
| ---------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `createUuid` avec repli                        | `crypto.randomUUID()` seul, comme dans la fiche | Il planterait sur le téléphone de test, ouvert en `http://192.168.x.x:3000` (§5)         |
| `uuid.ts` séparé                               | Générateur caché dans `participation.ts`        | Il est réutilisé par T1.8                                                                |
| Test de contrat qui **lit le code du serveur** | Recopier les deux codes dans un test            | Si `select-prize` ajoute ou renomme un code, le test échoue et force à revoir le contrat |
| `DrawPrize` nommé                              | Objet écrit en ligne dans `DrawOutcome`         | Même structure, plus lisible et réutilisable                                             |
| `Readonly<…>` sur les messages                 | `Record<…>` de la fiche                         | Même logique que les tables précédentes                                                  |

## 9. Écarts, imprévus et points d'attention

- **Imprévu corrigé, à retenir pour la suite : Vite réécrit `new URL("…", import.meta.url)`.** Mon premier test de contrat construisait le chemin du fichier serveur avec cette expression. Vite la transforme automatiquement en URL d'asset (`http://…`) ; `readFileSync` a alors refusé l'URL (« The URL must be of scheme file »). Le test utilise maintenant `node:path` et `node:url`, avec un commentaire qui explique pourquoi. Le test de `phone.test.ts` (T1.2) fonctionne, parce que son chemin passe par une variable que Vite ne reconnaît pas. Il reste correct, mais repose sur ce détail.
- **Pour l'adaptateur Supabase (après le MVP)** : trois erreurs du serveur **n'ont pas de code** et devront être traduites par l'adaptateur, pas par le runtime :

  | Réponse de `select-prize`                                                                                                | Code à produire        |

  | 400 « Campaign is not active. » (l. 176) ; 404 « Campaign not found. » (l. 166)                                          | `CAMPAIGN_CLOSED`      |
  | 400 « You have already participated… » **sans code**, en cas de doublon détecté par la contrainte d'unicité (l. 416-425) | `ALREADY_PARTICIPATED` |
  | 400 « Invalid Algerian phone number format. » (l. 100) ; « campaign_id and phone_number are required. » (l. 88)          | `INVALID_INPUT`        |

  Je les reporterai dans `services/supabase/README.md` (T2.6), qui décrit le contrat attendu de cet adaptateur.
