## 1. Objectif

Écrire la « table de vérité » des 5 mécaniques de jeu, au même endroit :

- **leur identifiant**, le même que dans la base et dans le reste de l'application ;
- **le moment où le serveur tire le résultat** : avant l'animation, ou après que le joueur a joué ;
- **leur nom dans le Studio**.

Ce moment du tirage est ce qui fait fonctionner différemment une roue et un quiz. La machine d'états (T1.10), la passerelle de démo (T2.4) et les moteurs de jeu (T5.x) s'appuieront tous sur cette table plutôt que de coder chacun leur propre liste.

## 5. Le code expliqué

### `GameType` : les 5 mécaniques

```ts
// Same union as Campaign["gameType"] in src/types.ts (checked by gameTypes.test.ts).
export type GameType =
  "lucky_wheel" | "quiz" | "scratch_card" | "mystery_box" | "hit_it";
```

- **Les mêmes identifiants que la base de données** (`campaigns.game_type`) et que le modèle `Campaign` de l'application : aucune traduction à faire entre le module et le reste du code.
- **Pourquoi réécrire la liste plutôt qu'écrire `Campaign["gameType"]` ?** Pour que le domaine se lise seul, sans dépendre du fichier de types de l'application (1 300 lignes). La contrepartie est un risque de divergence si la base gagne un jeu : il est neutralisé par l'**assertion de type** du test (§7), qui fait échouer `npm run typecheck` au moindre écart, dans un sens comme dans l'autre.

### `OutcomeTiming` et `OUTCOME_TIMING` : le moment du tirage

```ts
// When the server draws the outcome, relative to what the player does:
// - before-animation: drawn right after registration; the game only animates towards the known result.
// - after-interaction: the player plays first; the draw uses what they did (answers, chosen box, hits).
export type OutcomeTiming = "before-animation" | "after-interaction";

// Mirrors the production flow (handleRegister in src/pages/play/PlayerFlowPage.tsx).
export const OUTCOME_TIMING: Readonly<Record<GameType, OutcomeTiming>> = {
  lucky_wheel: "before-animation",
  scratch_card: "before-animation",
  quiz: "after-interaction",
  mystery_box: "after-interaction",
  hit_it: "after-interaction",
};
```

C'est la notion la plus importante de la tâche :

| Moment                  | Jeux                         | Déroulement                                                                                              | Pourquoi                                                                                                                                                                             |
| ----------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **`before-animation`**  | Roue, grattage               | Inscription → **tirage** → la roue tourne jusqu'au lot déjà connu, ou le ticket révèle le lot déjà connu | Le geste du joueur (tourner, gratter) n'influe pas sur le résultat : c'est un pur hasard, donc le serveur tire tout de suite. L'animation se contente d'« atterrir » sur le résultat |
| **`after-interaction`** | Quiz, boîtes mystère, Hit It | Inscription → **le joueur joue** → tirage, avec ce qu'il a fait                                          | Le serveur a besoin de ce que le joueur a fait : ses réponses (pour les corriger), la boîte choisie, son nombre de touches (pour vérifier le seuil)                                  |

- **`Record<GameType, OutcomeTiming>`** oblige TypeScript à exiger **une entrée pour chaque jeu**. Si un sixième jeu est ajouté à `GameType` sans son moment de tirage, le code ne compile plus.
- **`Readonly<…>`** empêche de modifier la table par erreur à l'exécution (`OUTCOME_TIMING.quiz = …` serait refusé à la compilation). Même choix que `LOCALES` en T1.1.

### `GAME_LABELS` : les noms dans le Studio

```ts
// Studio labels (English), aligned with the dashboard campaign list.
export const GAME_LABELS: Readonly<Record<GameType, string>> = {
  lucky_wheel: "Spin Wheel",
  quiz: "Quiz Challenge",
  scratch_card: "Scratch Card",
  mystery_box: "Mystery Box",
  hit_it: "Hit It",
};
```

- **En anglais** (libellés de l'interface, règles N5 et R0).
- **Les mêmes noms que la liste des campagnes du tableau de bord** (`CampaignsList.tsx`), pour qu'une marque retrouve dans le Studio le nom qu'elle voit ailleurs. Voir §9 : le tableau de bord lui-même n'est pas uniforme.
- Ce sont des libellés **pour la marque**. Le joueur, lui, ne voit jamais « Spin Wheel » : il voit les textes de l'écran d'accueil, en fr/ar/en (T1.7).

## 6. Décisions et alternatives

| Décision                                         | Alternative écartée                                                       | Raison                                                                                                                                                       |
| ------------------------------------------------ | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Liste écrite dans le domaine + assertion de type | `export type GameType = Campaign["gameType"]`                             | Le domaine reste lisible seul ; l'assertion garantit la même sécurité (§5)                                                                                   |
| Assertion placée dans le **test**                | Dans `gameTypes.ts`                                                       | Le code du domaine n'importe pas les types de l'application ; seul le test le fait                                                                           |
| `expectTypeOf` de Vitest                         | Une astuce de type écrite à la main                                       | Outil standard, lisible, avec un message clair en cas d'écart. Il est vérifié par `tsc`, et donc par `npm run typecheck`, exactement ce que demande la fiche |
| Libellés de la liste des campagnes               | « Lucky Wheel » (maquettes du Studio), « Lucky Spin Wheel » (Wizard)      | La liste des campagnes est l'écran que la marque voit le plus souvent                                                                                        |
| `Readonly<Record<…>>`                            | `Record<…>`, comme dans la fiche                                          | Plus strict, sans rien casser : même logique que `LOCALES`                                                                                                   |
| Ajout d'un fichier de test                       | Aucun test, comme le suggère la fiche (vérification par `typecheck` seul) | L'assertion de type doit vivre dans un fichier vérifié par `tsc` ; le test sert aussi l'objectif de couverture du domaine (≥ 90 %, règle C8)                 |

## 9. Écarts, imprévus et points d'attention

- **Un quiz sans question est tiré tout de suite en production.** Dans `handleRegister`, un quiz ne passe par l'écran de questions **que s'il a au moins une question** ; sinon, il part directement au tirage, comme une roue. `OUTCOME_TIMING` indique toujours `after-interaction` pour le quiz, comme le demande la fiche. **À traiter** :
  - en T1.10 (machine d'états), qui doit gérer le cas « quiz sans question » ;
  - en T5.5 (moteur du quiz).

  De son côté, le Studio signalera ce cas comme une erreur (T1.11 : « campagne quiz sans question active »).

- **Hors périmètre, noté et non corrigé :** le tableau de bord n'est pas uniforme sur les noms des jeux. La roue s'appelle « Spin Wheel », « Lucky Wheel » ou « Lucky Spin Wheel », et Hit It « Hit It », « Hit It Challenge » ou « Hit It Reaction Game », selon l'écran (`CampaignsList.tsx`, `CampaignWizard.tsx`). Le Studio suit la liste des campagnes.
- **Fichier de test ajouté**, que la fiche ne listait pas (§6).
