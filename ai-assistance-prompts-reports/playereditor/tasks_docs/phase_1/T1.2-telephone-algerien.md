## 1. Objectif

Normaliser et valider les numéros de téléphone algériens **exactement comme le serveur** (`select-prize`).

Le numéro normalisé est la **clé anti-doublon** (règle N4) : une participation par campagne et par numéro. Si le client et le serveur normalisaient différemment, un même joueur pourrait être accepté par l'un et refusé par l'autre. Ou pire, la passerelle de démonstration (T2.3) détecterait les doublons autrement que la production, et l'aperçu du Studio mentirait.

## 5. Le code expliqué

### Le motif de validation

```ts
// Algerian mobile numbers: 10 digits, starting with 05, 06 or 07.
// Same check as select-prize: /^(05|06|07)[0-9]{8}$/.
const DZ_MOBILE_PATTERN = /^0[567]\d{8}$/;
```

- **Un numéro mobile algérien** : un `0`, puis `5`, `6` ou `7` (les préfixes des opérateurs mobiles), puis 8 chiffres, soit 10 chiffres au total.
- **Même règle que le serveur, écrite autrement :** `0[567]` équivaut à `(05|06|07)`, et `\d` à `[0-9]` (en JavaScript, `\d` ne reconnaît que les chiffres 0 à 9). La forme de la fiche est plus courte, et le commentaire cite celle du serveur, pour qu'on puisse comparer d'un coup d'œil.
- **Constante interne, non exportée** : utilisée par les deux fonctions du fichier.

### `normalizeDzPhone` : la copie exacte du serveur

```ts
// Exact copy of normalizeDzPhone in supabase/functions/select-prize/index.ts:25 — keep both in sync.
export const normalizeDzPhone = (rawPhone: string): string => {
  const digitsOnly = rawPhone.replace(/\D/g, "");
  if (digitsOnly.startsWith("213") && digitsOnly.length === 12) {
    return `0${digitsOnly.slice(3)}`;
  }
  if (digitsOnly.length === 9 && /^[567]/.test(digitsOnly)) {
    return `0${digitsOnly}`;
  }
  return digitsOnly;
};
```

**Recopiée caractère pour caractère**, y compris la forme « fonction fléchée » et le nom du paramètre, pour qu'une comparaison automatique soit possible (voir le test de synchronisation). Seul le mot `export` a été ajouté.

Son fonctionnement, en trois temps :

| Étape | Code                                   | Effet                                                                                 | Exemple                                  |
| ----- | -------------------------------------- | ------------------------------------------------------------------------------------- | ---------------------------------------- |
| 1     | `rawPhone.replace(/\D/g, "")`          | Supprime tout ce qui n'est pas un chiffre : espaces, tirets, `+`, parenthèses, points | `"+213 555 12 34 56"` → `"213555123456"` |
| 2     | commence par `213` et fait 12 chiffres | Format international : remplace `213` par `0`                                         | `"213555123456"` → `"0555123456"`        |
| 3     | 9 chiffres commençant par 5, 6 ou 7    | Numéro saisi sans le `0` initial : on l'ajoute                                        | `"555123456"` → `"0555123456"`           |
| sinon | `return digitsOnly`                    | Renvoie les chiffres tels quels. La validation décidera                               | `"0555123456"` → `"0555123456"`          |

**Elle ne valide rien** : elle nettoie. Un numéro invalide ressort « nettoyé », mais toujours invalide (`"abc"` → `""`).

### `isValidDzMobile` : la validation

```ts
export function isValidDzMobile(raw: string): boolean {
  return DZ_MOBILE_PATTERN.test(normalizeDzPhone(raw));
}
```

On normalise d'abord, puis on vérifie le motif : **la même séquence que le serveur** (normalisation ligne 96, test ligne 97). Le joueur peut donc saisir son numéro comme il en a l'habitude : avec espaces, tirets, `+213`, ou sans le `0`.

### `formatDzPhone` : l'affichage

```ts
// Display format "0555 12 34 56". Input that is not a valid mobile number is returned unchanged,
// so what the player typed is never altered.
export function formatDzPhone(raw: string): string {
  const phone = normalizeDzPhone(raw);
  if (!DZ_MOBILE_PATTERN.test(phone)) return raw;
  return `${phone.slice(0, 4)} ${phone.slice(4, 6)} ${phone.slice(6, 8)} ${phone.slice(8)}`;
}
```

- **Numéro valide** : il est affiché groupé, `0555 12 34 56` (4, 2, 2, 2 chiffres), la façon habituelle de lire un mobile en Algérie. Découpage : `slice(0, 4)` donne `0555`, `slice(4, 6)` donne `12`, etc.
- **Numéro invalide** (y compris une saisie en cours, comme `"05 55"`) : **renvoyé tel quel**. On ne transforme jamais ce que le joueur a tapé tant que ce n'est pas un numéro complet et valide : cela évite un champ qui « saute » sous ses doigts.

## 6. Décisions et alternatives

| Décision                                                  | Alternative écartée                                                    | Raison                                                                                                                                                                                                                                                                                                                                |

| **Test de synchronisation avec le serveur**               | Se contenter du commentaire « keep both in sync » demandé par la fiche | Un commentaire n'empêche rien. ## 9. Écarts, imprévus et points d'attention

- **Test de synchronisation ajouté** : il va au-delà du commentaire demandé par la fiche (§6).
- **Limites du serveur, reproduites volontairement.** Trois saisies réalistes sont **refusées par le serveur**, donc aussi par le client :
  - `+213 0555 12 34 56` : le « 0 » ajouté par erreur après +213 ;
  - `00213 555 12 34 56` : le préfixe international « 00 » ;
  - les **chiffres arabes-indiens** (٠١٢٣…), que certains claviers arabes produisent.

  On ne peut pas les accepter dans `normalizeDzPhone` sans modifier le serveur (interdit, règle R7). **Proposition pour T4.2** : convertir ces saisies en format standard dans le champ lui-même, **avant** la normalisation. Par exemple, `٠٥٥٥…` devient `0555…` et `+2130555…` devient `0555…`. Le serveur recevrait ainsi un numéro qu'il accepte, sans changer le contrat.

- **Une troisième copie de la fonction existe** (serveur, page publique, module). La copie de `PlayerFlowPage.tsx` disparaîtra quand la page publique utilisera le nouveau module (après le MVP).
