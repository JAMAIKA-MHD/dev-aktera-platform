## 1. Objectif

Toute configuration qui **entre** dans le module doit être vérifiée : relecture depuis `localStorage`, import d'un fichier, plus tard lecture en base. Un fichier ancien, abîmé ou modifié à la main ne doit **jamais** faire planter le Studio ni l'écran du joueur (règle A6).

Deux pièces :

- **`experienceConfigSchema`** : la description exacte d'une configuration valide ;
- **`parseExperienceConfig(raw)`** : lit n'importe quoi, **ne lève jamais d'exception**, et renvoie toujours une configuration utilisable. Si l'entrée est défectueuse, elle est **réparée champ par champ** et les problèmes sont listés.

## 2. Où elle se situe

```
localStorage / fichier importé / (plus tard) base
            │  raw: unknown
            ▼
  parseExperienceConfig ──► { config: ExperienceConfig, issues: string[], recovered: boolean }
            │                     (toujours valide)
            ├─ valide ? → renvoyé tel quel (clés inconnues retirées)
            └─ sinon    → réparé contre createDefaultExperience(gameType)
```

**Utilisé ensuite par :**

- T1.8 : les valeurs par défaut doivent passer le schéma ;
- T1.9 : les migrations passent avant la validation ;
- T2.2 : le dépôt local relit la configuration ;
- T6.7 : l'import de fichier affiche les `issues` à la marque.

## 5. Le code expliqué

### Le principe : « chargeable » et non « publiable »

```ts
// Structural validation: can this configuration be loaded and rendered safely?
// Design rules ("publishable": contrast, 4+ wheel segments, consent text filled…) belong to
// validation.ts, so that the Studio can hold work-in-progress states without losing them.
```

Il y a **deux niveaux** de contrôle, et cette séparation est volontaire :

| Niveau        | Où                      | Question                                                      | Exemple                                                                    |
| ------------- | ----------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Structure** | `schema.ts` (ici)       | Peut-on charger et afficher cette configuration sans risque ? | Une couleur `"red"` est refusée : ce n'est pas `#rrggbb`                   |
| **Design**    | `validation.ts` (T1.11) | Peut-on la publier ?                                          | 3 segments de roue sont acceptés ici, mais signalés comme erreur de design |

Si le schéma était aussi exigeant que la validation de design, une marque qui vide le texte du consentement pour le réécrire **perdrait son travail** au rechargement. Le schéma accepte donc les états « en cours de travail », et la validation les signale.

### Les contraintes du schéma

| Contrainte                                                                 | Demandée par la fiche  | Pourquoi                                                                                           |
| -------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------- |
| Couleurs `#rrggbb`                                                         | Oui                    | Seul format que le thème sait décliner (transparences, dégradés)                                   |
| `overlayOpacity` entre 0 et 1                                              | Oui                    | C'est une opacité                                                                                  |
| 1 à 4 étiquettes de lots                                                   | Oui                    | Mise en page de l'accueil                                                                          |
| 2 à 12 segments de roue                                                    | Oui                    | En dessous de 2, ce n'est plus une roue ; la validation de design exigera 4                        |
| `policyVersion` non vide                                                   | Oui                    | Chaque consentement enregistre sa version (loi 18-07)                                              |
| Liens `https:`, `mailto:`, `tel:`                                          | Oui                    | Refuse `http:` et surtout `javascript:`                                                            |
| **Images** : `remote` en `https://`, `dataUrl` en `data:image/`            | Ajout                  | Même raison de sécurité : une « image » ne doit pas pouvoir être `javascript:` ou `data:text/html` |
| `focus` entre 0 et 100, seuil de grattage entre 1 et 100                   | Ajout                  | Pourcentages                                                                                       |
| **Langues** : la langue par défaut est activée, sans doublon               | Ajout, annoncé en T1.4 | Invariant que le type seul ne peut pas exprimer                                                    |
| **Téléphone** présent, activé et obligatoire ; champs uniques              | Ajout                  | Règle N4 : c'est la clé anti-doublon                                                               |
| **Le bloc du jeu choisi existe** (roue → `wheel`, etc.)                    | Ajout                  | Sans lui, le moteur de jeu n'aurait rien à afficher                                                |
| `shareBonus` = `false`, `schemaVersion` = 1, `templateId` = `"eight-slot"` | Découle du type        | Valeurs verrouillées                                                                               |
| Clés inconnues **supprimées**                                              | Comportement de zod    | Un ancien champ ne pollue pas la configuration                                                     |

Les messages d'erreur sont en anglais (règle R0) : ils s'afficheront dans le Studio, dont l'interface est en anglais.

### `parseExperienceConfig` : lire sans jamais planter

```ts
export function parseExperienceConfig(
  raw: unknown,
  fallbackGameType?: GameType,
): ParseResult {
  const gameType = fallbackGameType ?? readGameType(raw) ?? DEFAULT_GAME_TYPE;
  try {
    const strict = experienceConfigSchema.safeParse(raw);
    if (strict.success) {
      return {
        config: strict.data as ExperienceConfig,
        issues: [],
        recovered: false,
      };
    }
    const fallback = createDefaultExperience({ gameType });
    const repaired = experienceConfigSchema.safeParse(
      repair(experienceConfigSchema, raw, fallback),
    );
    return {
      config: repaired.success ? (repaired.data as ExperienceConfig) : fallback,
      issues: strict.error.issues.map(formatIssue),
      recovered: true,
    };
  } catch (error) {
    return {
      config: createDefaultExperience({ gameType }),
      issues: [`(root): unreadable configuration (…)`],
      recovered: true,
    };
  }
}
```

Le déroulement :

1. **Type de jeu de secours** : celui demandé par l'appelant (la campagne), sinon celui trouvé dans l'entrée s'il est valide, sinon la roue.
2. **Entrée valide** : elle est renvoyée telle quelle, sans les clés inconnues. `recovered: false`.
3. **Entrée invalide** : les problèmes sont listés sous la forme `chemin: message` (par exemple `theme.colors.primary: Expected a #rrggbb color`), puis l'entrée est **réparée** (voir ci-dessous). `recovered: true`.
4. **Imprévu absolu** (un objet qui lève une exception quand on le lit, par exemple) : configuration par défaut. La fonction ne lève jamais d'exception, comme l'exige la fiche.

### La réparation, champ par champ

```ts
// Keeps every valid part of `raw` and replaces each invalid part by the fallback.
// Objects are repaired field by field; records keep their valid entries; anything else
// (arrays, unions, leaves) is kept whole or replaced whole.
function repair(schema: z.ZodType, raw: unknown, fallback: unknown): unknown {
  if (schema.safeParse(raw).success) return raw;
  const base = schema instanceof z.ZodOptional ? schema.unwrap() : schema;
  if (
    base instanceof z.ZodObject &&
    isPlainObject(raw) &&
    isPlainObject(fallback)
  ) {
    // … répare chaque champ récursivement …
    return base.safeParse(repaired).success ? repaired : fallback;
  }
  if (base instanceof z.ZodRecord && isPlainObject(raw)) {
    // … garde les entrées valides …
  }
  return fallback;
}
```

La fonction descend dans le schéma **en même temps** que dans l'entrée et dans la configuration de secours :

| Ce qu'elle rencontre                                                          | Ce qu'elle fait                              | Exemple                                                            |
| ----------------------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| Une partie **valide**                                                         | La garde telle quelle                        | Les couleurs correctes de la marque sont conservées                |
| Un **objet** invalide                                                         | Le répare **champ par champ**                | Seule la couleur fautive est remplacée ; le nom de la marque reste |
| Un objet dont une **règle d'ensemble** échoue (« langue par défaut activée ») | Remplace l'objet entier par celui de secours | `locales` redevient `fr` + `fr/ar/en`                              |
| Un **dictionnaire** (`prizeDisplay`, traductions)                             | Garde les entrées valides, retire les autres | Un lot mal décrit disparaît ; les autres restent                   |
| Une **liste**, une union, une valeur simple                                   | La garde entière ou la remplace entière      | 13 segments → segments de secours                                  |

**Pourquoi c'est important :** sans cette réparation, une seule couleur mal saisie dans un fichier importé ferait perdre **toute** la personnalisation de la marque. Avec elle, on perd seulement ce qui était faux, et la marque voit la liste précise des corrections dans `issues`.

Les outils de zod 4 utilisés (vérifiés avant d'écrire le code) : `ZodObject.shape` (les champs), `ZodOptional.unwrap()` (le contenu d'un champ facultatif), `ZodRecord.valueType` (le type des valeurs d'un dictionnaire). Point important : en zod 4, `superRefine` ne change pas la nature d'un objet, qui reste un `ZodObject` parcourable.

### `defaults.ts` : une première version, et pourquoi

**Imprévu dans les fiches : une dépendance circulaire.** `parseExperienceConfig` doit « compléter avec les valeurs par défaut », qui ne sont créées qu'en T1.8, alors que T1.8 dépend de T1.6.

**Solution :** T1.6 crée `domain/defaults.ts` avec une **première version** de `createDefaultExperience`, qui a déjà la signature finale de la fiche T1.8 :

- structure complète et valide pour les 5 jeux (bloc du jeu compris) ;
- valeurs neutres : couleurs Midnight Gold, formulaire avec le téléphone verrouillé, `shareBonus: false` ;
- **textes vides**.

T1.8 l'enrichira (presets, textes fr/ar/en, segments construits à partir des lots). Pas de code jetable : `schema.ts` appelle déjà la bonne fonction et n'aura pas à changer.

### Imprévu majeur : le projet n'est pas en TypeScript strict

**Constat.** La fiche demande `experienceConfigSchema: z.ZodType<ExperienceConfig>`. Le typecheck a refusé cette correspondance, avec le message « `campaignId` is optional » : `tsconfig.json` n'active pas `strict`, donc `strictNullChecks` est désactivé. Dans ce mode :

- zod 4 ne sait plus distinguer « peut valoir `null` » de « facultatif » ;
- **plus largement, aucun `| null` du projet n'est vérifié** par TypeScript.

Or la règle C1 exige le mode strict dans le module.

**Mesure.** J'ai compilé en mode strict :

- le **module seul** : 0 erreur ;
- le **projet entier** : seulement **5 erreurs, dans 3 fichiers existants** (`AnalyticsCenter.tsx`, `CampaignWizard.tsx`, et `RenderedElement.tsx` de l'ancien éditeur).

Les corriger sortirait du périmètre (règles R5 et R7).

**Solution retenue, sans toucher à l'application :**

| Pièce                                              | Rôle                                                                                                                                                                                                                                |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tsconfig.strict.json`                             | Hérite de `tsconfig.json`, active `strict`, ne compile **que** le module (et ce qu'il importe, soit `src/types.ts`, qui passe aussi en strict)                                                                                      |
| `npm run typecheck`                                | `tsc --noEmit && tsc --noEmit -p tsconfig.strict.json` : les deux vérifications, donc aussi dans `verify` et le `pre-push`                                                                                                          |
| `schema.strict-check.ts`                           | La **preuve** que le schéma correspond **exactement** à `ExperienceConfig` (assignable dans les deux sens). Compilé uniquement par la configuration stricte, et exclu de `tsconfig.json`, où il échouerait pour la raison ci-dessus |
| Conversions `as ExperienceConfig` dans `schema.ts` | Nécessaires pour la compilation non stricte, et **justifiées** par la preuve stricte ; un commentaire l'explique                                                                                                                    |

**Deux pièges trouvés en vérifiant, puis corrigés :**

1. `tsconfig.strict.json` **héritait** de la liste `exclude` de `tsconfig.json`, qui exclut justement les preuves `*.strict-check.ts`. La preuve n'était donc compilée **nulle part**, et le test de mutation (§7) est passé alors qu'il devait échouer. Correction : `tsconfig.strict.json` redéfinit sa propre liste `exclude`. La mutation échoue désormais, comme attendu.
2. La couverture comptait `schema.strict-check.ts` à 0 %, alors que c'est un fichier de preuve de type, sans rien à exécuter. Il est maintenant exclu de la couverture dans `vitest.config.ts`.

## 6. Décisions et alternatives

| Décision                                                         | Alternative écartée                                                           | Raison                                                                                                                                                                          |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Configuration stricte dédiée au module                           | Activer `strict` pour tout le projet                                          | Demanderait de corriger 3 fichiers de l'application, hors périmètre. **À décider par toi** : le coût est faible (5 erreurs)                                                     |
| Preuve « exactement égal » dans un fichier strict                | `satisfies z.ZodType<ExperienceConfig>` dans `schema.ts`, comme dans la fiche | Impossible en non strict. Et `satisfies` ne vérifie qu'un sens : un champ oublié dans le schéma passerait inaperçu                                                              |
| Réparation champ par champ                                       | Tout remplacer par les valeurs par défaut au moindre problème                 | Perdrait toute la personnalisation pour une erreur isolée                                                                                                                       |
| Première version de `defaults.ts` en T1.6                        | Une valeur de secours provisoire cachée dans `schema.ts`                      | Pas de code jetable ; la signature finale est déjà en place                                                                                                                     |
| Contraintes de sécurité sur les images et règles d'ensemble (§5) | S'en tenir à la liste de la fiche                                             | Mêmes raisons que les liens ; invariants N4 et « bloc du jeu présent »                                                                                                          |
| `any` dans le fichier de test                                    | Types stricts partout                                                         | Les tests construisent volontairement des données **invalides** : un typage strict les empêcherait. Exception limitée aux tests ; le code du domaine n'a aucun `any` (règle C1) |
