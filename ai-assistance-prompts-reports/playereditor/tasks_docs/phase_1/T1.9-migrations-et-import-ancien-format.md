## 1. Objectif

Deux besoins distincts, réunis dans `domain/migrations.ts` :

1. **Faire évoluer le format sans rien casser.** Chaque configuration porte un numéro de version (`schemaVersion`). Quand le format changera (version 2, 3…), une configuration enregistrée avec une version plus ancienne sera **montée** automatiquement à la version actuelle au chargement.
2. **Récupérer le travail fait avec l'ancien éditeur.** Des campagnes ont déjà un `PlayerScreenConfig` (couleurs, logo, titres). Au lieu de repartir de zéro, on en reprend **au mieux** ce qui a encore un sens.

## 5. Le code expliqué

### 5.1 La chaîne de versions

```ts
const MIGRATIONS = {
  0: (raw) => ({ ...raw, schemaVersion: 1 }),
  // 1: (raw) => …   ← à ajouter le jour où la version 2 existera
};
```

Chaque étape transforme une version N en version N + 1. `migrateExperienceConfig(raw)` lit la version, puis applique les étapes **une par une** jusqu'à la version actuelle (`CURRENT_SCHEMA_VERSION = 1`).

| Entrée                                                                     | Résultat                                                                                        |
| -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Version actuelle (1)                                                       | Renvoyée **telle quelle** (même objet)                                                          |
| Pas de version (« v0 »)                                                    | Montée en version 1 ; l'entrée d'origine n'est pas modifiée                                     |
| Version inconnue ou future (2, 7…), version illisible (`"1"`, `1.5`, `-1`) | Renvoyée telle quelle : le schéma la refuse, puis la **réparation** de T1.6 garde tout le reste |
| Pas un objet (`null`, texte, nombre, tableau)                              | Renvoyée telle quelle : la réparation produit une configuration par défaut                      |

`migrateExperienceConfig` **ne valide rien** : c'est le rôle du schéma, juste après. Les deux responsabilités restent séparées.

**Qu'est-ce que la « v0 » ?** Une configuration sans `schemaVersion`. Aucune n'existe encore, puisque le format est neuf ; l'étape 0 sert de modèle et couvre le cas d'un fichier écrit à la main ou par un outil qui aurait oublié le numéro.

### 5.2 Le branchement dans `parseExperienceConfig`

`parseExperienceConfig` (T1.6) appelle maintenant `migrateExperienceConfig` **avant** la validation. Une configuration migrée proprement n'est **pas** une « réparation » : `recovered` reste à `false` et aucun problème n'est listé.

Une version future (par exemple 7, écrite par une version plus récente de l'application) est signalée (`schemaVersion` dans les problèmes), ramenée à 1, et **tout le travail valide de la marque est conservé** (test : un titre personnalisé survit).

`migrations.ts` n'importe **pas** `schema.ts` : il n'y a donc pas de dépendance circulaire entre les deux fichiers.

### 5.3 Qui écrit vraiment l'ancien format ?

Avant d'écrire l'import, j'ai vérifié quel code produit un `PlayerScreenConfig`. **Un seul** : `PlayerEditorShell.tsx` (l'ancien éditeur Aktera). Ce qu'il enregistre :

| Champ               | Contenu réel                                                                        |
| ------------------- | ----------------------------------------------------------------------------------- |
| `theme`             | Couleurs, logo, fond (type + valeur, parfois un dégradé CSS), police, arrondi, mode |
| `content.preGame`   | Titre, sous-titre, règle ; **`formFields` toujours vide** (`[]`)                    |
| `content.winState`  | Titre, bouton « Copier le code », action `claim`                                    |
| `content.loseState` | Titre, bouton « Rejouer maintenant », action `retry`                                |
| `gameAssets`        | Uniquement `sound.muted` : **aucune tranche de roue**                               |

Ces constats ont guidé trois choix (§5.5).

### 5.4 La correspondance (plan §16.2)

`importLegacyPlayerScreenConfig(legacy, gameType, campaign?)` part d'une configuration **par défaut complète** (T1.8), puis y dépose chaque valeur ancienne **valide**. Une valeur invalide est ignorée : la valeur par défaut reste. Le résultat passe donc **toujours** le schéma.

| Ancien champ                                            | Nouveau champ                                   | Règle                                                                                            |
| ------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `theme.primaryColor` / `secondaryColor` / `accentColor` | `theme.colors.primary` / `secondary` / `accent` | `#rrggbb` accepté ; `#abc` développé en `#AABBCC` ; noms (`red`), `rgb()` ignorés                |
| `theme.background.type`                                 | `theme.background.kind`                         | `brandImage` → `image` ; type inconnu ignoré                                                     |
| `theme.background.value`                                | `theme.background.image`                        | Seulement une URL `https://` ou une image importée (`data:image/`) ; un dégradé CSS est ignoré   |
| `theme.logoUrl`                                         | `brand.logo`                                    | Même règle que l'image de fond ; `http://` refusé                                                |
| `theme.borderRadius`                                    | `theme.radius`                                  | `sharp`, `rounded` ou `pill`                                                                     |
| `theme.mode`                                            | `theme.mode`                                    | `light` → départ du preset Clean Light ; sinon Midnight Gold                                     |
| `content.preGame.title` / `subHeader`                   | `screens.welcome.title` / `subtitle`            | Texte non vide                                                                                   |
| `content.preGame.formFields`                            | `form.fields`                                   | Par type : `text` → nom, `tel` → téléphone, `email` → email, `select` → wilaya ; `number` ignoré |
| `content.winState.title` / `ctaLabel`                   | `screens.win.title` / `primaryCta`              | Bouton ignoré si l'action est `claim` (§5.5)                                                     |
| `content.loseState.title` / `ctaLabel`                  | `screens.lose.title` / `primaryCta`             | Bouton ignoré si l'action est `retry` (§5.5)                                                     |
| `gameAssets.wheel.slices`                               | `game.wheel.segments`                           | Roue seulement ; 2 à 12 tranches ; `prizeId: null` (à relier dans le Studio)                     |
| `uiProject`                                             | —                                               | Ignoré                                                                                           |

Sans `theme` ni `content`, par exemple quand seul `uiProject` est présent, la fonction renvoie **`null`** : il n'y a rien à reprendre.

**Style personnalisé.** Dès qu'une valeur ancienne diffère du preset de départ, `theme.presetId` passe à `null` : le Studio saura que ce n'est plus un style prédéfini. Un ancien thème clair qui ne change rien d'autre reste « Clean Light ».

### 5.5 Trois écarts assumés par rapport à la table du plan

1. **Boutons dont l'action n'existe plus.** « Copier le code » (`claim`) : le code se copie désormais depuis le bon lui-même, le bouton principal de l'écran de gain est « Terminer ». « Rejouer maintenant » (`retry`) : **faux**, une seule participation par numéro (règle N4). Importer ces libellés mettrait un texte mensonger sur un bouton. Ils sont ignorés ; un libellé lié à une autre action est importé.
2. **Langue des anciens textes.** L'ancien format n'indique pas la langue. Le plan dit « `.fr` », mais l'ancien éditeur existait aussi en arabe. Un texte en **écriture arabe** va donc dans `ar`, tout autre texte dans `fr`. Le texte importé **remplace** le texte par défaut dans toutes les langues (par exemple `{ fr: "Tentez votre chance !" }`) : un joueur arabophone voit alors le titre de la marque (repli), pas un titre générique différent. Le Studio signalera les traductions manquantes.
3. **Liste de champs vide.** L'ancien éditeur enregistrait toujours `formFields: []`. Une liste vide signifie donc « non personnalisé » : le formulaire par défaut est gardé. Sinon, un champ absent de la liste est désactivé.

Et deux règles de sécurité :

- **Le téléphone reste activé et obligatoire**, même si l'ancienne configuration disait `required: false` : c'est la clé anti-doublon (règle de T1.6).
- Les tables de correspondance sont des `Map`, pas des objets simples : une valeur piégée comme `"constructor"` ne peut pas atteindre `Object.prototype` (testé).

### 5.6 Le paramètre `campaign`

La fiche prévoit `importLegacyPlayerScreenConfig(legacy, gameType)`. J'ai ajouté un **troisième paramètre facultatif**, `campaign`. Sans lui, la configuration par défaut serait construite sur la **campagne de démonstration**, et sa roue désignerait des lots de démonstration (`demo-prize-…`) qui n'existent pas dans la vraie campagne. Avec lui, la roue et `campaignId` correspondent à la vraie campagne. Le paramètre étant facultatif, la signature de la fiche reste valable.

## 6. Décisions et alternatives

| Décision                                           | Alternative écartée                                 | Raison                                                                                           |
| -------------------------------------------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Migrations appliquées dans `parseExperienceConfig` | Appel séparé par chaque lecteur                     | Plan §5.3 ; un seul point d'entrée, impossible d'oublier                                         |
| Version future renvoyée telle quelle, puis réparée | Refus total                                         | La réparation garde le travail de la marque                                                      |
| Import construit valeur par valeur                 | Construire, puis passer par `parseExperienceConfig` | Éviterait les contrôles manuels, mais créerait une dépendance circulaire `schema` ↔ `migrations` |
| Libellés `claim` / `retry` ignorés                 | Import littéral (plan §16.2)                        | Texte mensonger, contraire à la règle N4                                                         |
| Écriture arabe → `ar`                              | Tout dans `fr` (plan)                               | Un texte arabe rangé en `fr` casserait le sens de lecture et les repli de langue                 |
| `campaign` facultatif                              | Signature stricte de la fiche                       | Sinon la roue importée désignerait des lots de démonstration                                     |
| Départ du preset de la bonne luminosité            | Toujours Midnight Gold                              | L'ancien format n'a ni couleur de fond ni couleur de texte                                       |

## 9. Écarts, imprévus et points d'attention

- **Trois écarts à la table du plan** (§5.5) et **un paramètre facultatif** (§5.6), tous justifiés ci-dessus.
- **L'import des tranches de roue est théorique** : aucun code actuel n'écrit `gameAssets.wheel.slices`. Il est implémenté comme le plan le demande, mais une roue importée n'a **aucun lot relié** tant que la marque ne les relie pas dans le Studio. La validation de design (T1.11) devra le signaler.
- **Non importés, faute d'être dans la table** : `fontFamily`, `rulesText`, `gameAssets.sound.muted` (→ `features.sound`), `gameParams`. `sound.muted` serait facile à reprendre (1 ligne) : **à toi de dire** si tu le veux.
- **Qui appellera l'import ?** Le Studio, à l'ouverture d'une campagne qui a un ancien `playerScreenConfig` mais pas encore de nouvelle configuration (phase 6).

## 10. Qualité visuelle

Un ancien thème clair repart du style Clean Light, pour garder un fond et un texte lisibles. Un texte arabe importé reste en arabe, lu de droite à gauche. Aucun bouton ne promet ce qui n'existe plus.
