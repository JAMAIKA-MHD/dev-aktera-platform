## 1. Objectif

Relier la nouvelle configuration au modèle de campagne de l'application. `PlayerScreenConfig`, le type de la colonne `campaigns.player_screen_config`, reçoit un champ **`experience`**. ## 5. Le code expliqué

```ts
import type { ExperienceConfig } from "./features/player-experience";

export interface PlayerScreenConfig {
  // New versioned configuration of the player screens (Player Experience module).
  // Replaces uiProject, which is obsolete and removed in phase 7.
  experience?: ExperienceConfig;
  uiProject?: any;
  // … theme, gameAssets, content : inchangés
}
```

- **`import type`** : l'import disparaît à la compilation. Il n'ajoute aucun code au bundle et ne crée aucune dépendance à l'exécution.
- **Import par `index.ts`**, pas par `domain/types` comme l'écrit la fiche. La règle ESLint des frontières (T0.3) interdit au reste de l'application d'importer un fichier interne du module ; `index.ts` exporte déjà `ExperienceConfig`. C'est le chemin prévu par l'architecture.
- **Champ facultatif** (`?`) : les campagnes existantes n'ont pas ce champ, et restent valides.
- **Dépendance circulaire de types** : `domain/campaign.ts` lit `Campaign` dans `src/types.ts` (T1.8), et `src/types.ts` lit maintenant `ExperienceConfig` dans le module. Les deux imports sont `import type`, que TypeScript résout sans problème et qui n'existent plus à l'exécution.

## 7. Tests

La fiche n'autorise aucun autre fichier : pas de nouveau test permanent. La vérification du typage a été faite avec une **sonde temporaire**, un fichier compilé puis supprimé :

1. `campaign.playerScreenConfig?.experience?.game.type` est bien du type des 5 jeux ;
2. une clé inconnue (`experience?.notAField`) est **refusée** par TypeScript.

**Test de mutation de la sonde** : avec `experience?: any`, TypeScript accepte la clé inconnue, et la sonde **échoue** (`Unused '@ts-expect-error' directive`). Le champ est donc réellement typé. Fichier restauré (vérifié avec `cmp`) et sonde supprimée.
