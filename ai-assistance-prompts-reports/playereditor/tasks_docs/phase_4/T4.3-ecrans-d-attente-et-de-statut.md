## 5. Le code expliqué

### 5.1 L'attente (`ResolvingScreen.tsx`)

Rien à faire pendant que le tirage est en cours : le contenu de l'écran `play` (même en-tête, mêmes sections), un médaillon qui tourne (`ScreenMedallion` avec `waiting`), le texte « Préparation de votre partie… » dans les trois langues (`STATUS_TEXT.resolving`, annoncé aux lecteurs d'écran par `role="status"`), et **aucun CTA** : quitter cet écran perdrait le résultat du tirage (le reducer refuse `RESTART` tant que l'écran est `resolving` ou `revealing`, `LOCKED_SCREENS` dans `domain/flow.ts`, T1.10). Le pied de page légal reste affiché (B9) : ce n'est pas une impasse, juste un écran sans bouton.

### 5.2 Les trois statuts (`StatusScreen.tsx`)

Un seul composant, trois variantes lues sur `state.screen` :

| Variante    | Icône       | Titre                 | Sortie                                          |
| ----------- | ----------- | --------------------- | ----------------------------------------------- |
| `duplicate` | `UserCheck` | « Déjà joué ! »       | « Retour » seul → `RESTART`                     |
| `closed`    | `CalendarX` | « Campagne terminée » | « Retour » seul → `RESTART`                     |
| `error`     | `WifiOff`   | « Oups ! »            | « Réessayer » → `RETRY`, « Retour » → `RESTART` |

Le message vient de `PARTICIPATION_ERROR_MESSAGES[state.error?.code ?? variant.code]` : le vrai code renvoyé par la passerelle quand il y en a un, sinon le code par défaut de la variante (cas d'un écran imposé par l'aperçu du Studio, où `createPreviewFlowState` pose un message d'aperçu générique plutôt qu'un vrai message d'erreur — T4.1). Le titre, en revanche, dépend seulement de l'écran affiché, pas du code : un statut `duplicate` dit toujours « Déjà joué ! ».

**Pourquoi `duplicate` et `closed` n'offrent jamais de réessayer** : ce sont des refus métier (le numéro a déjà joué, la campagne est finie) — retenter la même tentative échouerait exactement pareil. Seule une erreur technique (`error`, réseau ou inconnue) peut réussir la deuxième fois (`isRetryable`, `domain/participation.ts`, déjà en place depuis T1.5).

`RETRY` garde le même `clientRequestId` et la même charge utile (T1.10, `domain/flow.ts`) : le bouton « Réessayer » de `StatusScreen` appelle `flow.retry()`, qui redispatche l'événement `RETRY` sans rien reconstruire — le serveur ne compte donc jamais deux fois la même tentative. Un test end-to-end le vérifie en jouant le vrai parcours (§7).

Comme pour tous les écrans du parcours (T4.2), chaque bouton passe par `press(flow, action, cta)` : il rapporte `cta_clicked` avant d'émettre son événement.

### 5.3 `PendingScreen.tsx` allégé

Les quatre cas retirés laissent `View.key` toujours renseigné (`"play" | "win" | "lose"`, plus jamais `null`) : la branche `view.key ? … : null` de `editPath` était devenue du code mort (relevé par la couverture de branches, §8), simplifiée en `editPath={`screens.${view.key}`}`.

### 5.4 Le branchement (`PlayerExperience.tsx`)

```tsx
if (screen === "resolving") return <ResolvingScreen {...props} />;
if (screen === "duplicate" || screen === "closed" || screen === "error") {
  return <StatusScreen {...props} />;
}
return <PendingScreen {...props} />;
```

Même schéma que T4.2 pour `welcome`/`register` : une correspondance directe entre l'écran de la machine d'états et le composant qui le dessine.

## 6. Décisions et alternatives

| Décision                                                               | Alternative écartée                              | Raison                                                                                                                                                                        |
| ---------------------------------------------------------------------- | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Un seul `StatusScreen.tsx` pour les trois variantes                    | Trois fichiers séparés (`DuplicateScreen`, etc.) | La fiche ne nomme qu'un fichier (`StatusScreen.tsx`) ; les trois partagent tout sauf l'icône, le titre et la sortie                                                           |
| Le titre suit l'écran, le message suit le vrai code d'erreur           | Les deux suivant systématiquement l'écran        | Un écran imposé par l'aperçu n'a pas de vrai message ; un vrai tirage peut renvoyer un code différent du code par défaut de l'écran (rare, mais le message doit rester exact) |
| `duplicate`/`closed` : un seul bouton « Retour », pas de « Réessayer » | Toujours offrir les deux boutons                 | Un refus métier échoue à nouveau à l'identique (`isRetryable`, T1.5) : proposer de réessayer serait trompeur                                                                  |
| `View.key` n'accepte plus `null` dans `PendingScreen.tsx`              | Garder le type `ScreenKey \| null`               | Plus aucune branche ne produit `null` depuis le retrait des statuts ; le garder aurait laissé une branche morte (couverture)                                                  |

## 9. Écarts, imprévus et points d'attention

### 9.1 Presque rien de nouveau à écrire

Contrairement à T4.2, cette tâche n'a inventé aucun nouveau contenu ni comportement : T4.1 avait déjà posé les bons textes, les bonnes icônes et le bon câblage des CTA dans `PendingScreen.tsx`, en avance sur son propre périmètre pour que le parcours soit démontrable dès T4.1. Le travail de T4.3 a été d'**extraire** ce code dans ses propres fichiers (comme demandé), de retirer le code devenu mort, et d'ajouter la couverture de test dédiée à ces deux écrans, qui manquait — `PendingScreen.test.tsx` ne testait jusque-là qu'un seul statut (`closed`), sans vérifier `RETRY` ni l'absence d'impasse.

### 9.2 Rien retiré, rien ajouté hors fiche

Aucun écart avec le contenu de la fiche : les deux fichiers qu'elle nomme (`ResolvingScreen.tsx`, `StatusScreen.tsx`) sont ceux créés. Les quatre fixtures et l'ajustement de `PendingScreen.tsx`/`PlayerExperience.tsx` sont la conséquence directe du déplacement de code, pas des ajouts de périmètre.

### 9.3 Point d'attention pour T4.5

Le test de bout en bout de `RETRY` (§7) couvre déjà le scénario `network-error` → `lose`. T4.5, qui doit jouer les cinq scénarios de bout en bout, pourra réutiliser le même schéma pour `duplicate` et `closed` (déjà couverts ici en surface, avec un flux simulé plutôt que rejoué).
