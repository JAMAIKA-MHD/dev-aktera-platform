## 1. Objectif

Relier la machine d'états du parcours (T1.10, pure) aux services (T2.x) : un hook `useExperienceFlow` qui fait avancer le parcours et exécute ses effets (tirage, confirmation du coupon, analytics), et le composant racine `PlayerExperience` qui affiche l'écran courant dans le cadre à 8 slots, refuse une passerelle non autorisée et porte le badge DEMO. `/xp-frame` rend désormais ce parcours dans l'aperçu.

## 2. Où elle se situe

- **Avant** : la machine d'états pure (T1.10, `domain/flow.ts`) ; les ports et les services locaux (T2.1 à T2.6), dont la passerelle scriptée ; l'hôte `/xp-frame` et son pont (T3.3) ; le cadre à 8 slots (T3.4 à T3.6) ; les hooks de session et de temps passé (T3.7) ; l'audit de mise en page (T3.8).
- **Maintenant** : le parcours tourne. Un joueur (ou le Studio) avance d'écran en écran ; chaque bouton émet un événement de la machine d'états (B4) ; le tirage part vers la passerelle, qui seule décide du résultat (N1).

**Le flux d'un tirage :**

```
 bouton du slot 7 ──► flow.startDraw()            (B4 : un bouton émet un événement)
                          │ dispatch DRAW_STARTED
                          ▼
        flowReducer : play → resolving            (domaine pur, T1.10)
                          │ nextCommand(prev, next) === "DRAW"
                          ▼
        useExperienceFlow : draw(state)
          ├─ humanVerification.getToken()          (null au MVP)
          ├─ buildDrawRequest(state, …)            (null → INVALID_INPUT, rien n'est envoyé)
          ├─ analytics « draw_requested »
          └─ participation.draw(request) ──► passerelle (demo | scripted | live)
                          │
                          ▼ RESOLVED(entryId, outcome) | FAILED(error)
        flowReducer : resolving → revealing | duplicate | closed | register | error
                          │
                          ▼ le moteur montre le résultat, puis REVEAL_DONE (phase 5 ;
                            en attendant, l'écran provisoire le fait aussitôt)
                      win | lose
```

## 5. Le code expliqué

### 5.1 Le domaine : la requête de tirage et l'écran imposé (`domain/flow.ts`)

La fiche demande « aucune logique métier dans le composant : tout vient du domaine ». Deux fonctions **pures** rejoignent donc `flow.ts`, sans toucher au reducer.

**`buildDrawRequest(state, input)`** construit la requête du plan §7.2 à partir de l'état du parcours :

```ts
const participant: DrawRequest["participant"] = {
  phone: normalizeDzPhone(state.participant.phone),
};
for (const field of input.form.fields) {
  if (!field.enabled || field.key === "phone") continue;
  const value = state.participant[field.key].trim();
  if (value) participant[field.key] = value;
}
```

- **Elle n'envoie que ce que le joueur a donné** : le téléphone normalisé (copie exacte de la fonction serveur, B5), puis les champs **activés** et **remplis**. Un e-mail tapé alors que le champ est désactivé n'est pas envoyé.
- **Le consentement devient un `ConsentRecord`** (N3, loi 18-07) : `acceptedAt` en ISO 8601 (depuis l'horodatage enregistré par `SET_CONSENT`), la version de la politique lue dans la configuration, la langue du moment.
- **Elle renvoie `null` si la tentative est incomplète** : pas de consentement, pas d'horodatage, téléphone invalide, pas de `clientRequestId` ni de charge utile. **Une participation incomplète ne part jamais** ; le hook la transforme en `INVALID_INPUT`, qui ramène au formulaire.
- Aucune horloge lue (`new Date(ms)` convertit l'horodatage reçu) : un test le vérifie.

**`createPreviewFlowState(screen, campaign, options)`** donne l'état de départ d'un écran **imposé par l'aperçu** (prop `initialScreen` du plan §8.1, pour l'onglet d'écran du Studio) :

| Écran demandé                     | État construit                                                                                |
| --------------------------------- | --------------------------------------------------------------------------------------------- |
| `welcome`, `register`             | L'état initial, sur cet écran                                                                 |
| `play`, `resolving`               | Une tentative ouverte (`clientRequestId` fourni), **sans aucune coordonnée ni consentement**  |
| `revealing`, `win`                | Le **premier lot** de la campagne, avec le code `PREVIEW_COUPON_CODE = "DEMO-0000-0000"` (B6) |
| `lose` (ou une campagne sans lot) | Une perte                                                                                     |
| `duplicate`, `closed`, `error`    | L'erreur correspondante (`ALREADY_PARTICIPATED`, `CAMPAIGN_CLOSED`, `NETWORK`)                |

**Rien n'est tiré** : c'est un décor d'aperçu. Un tirage lancé depuis un écran imposé (bouton de la roue, « Réessayer ») n'a ni consentement ni téléphone : `buildDrawRequest` renvoie `null` et le joueur revient au formulaire. Et le runtime **refuse** tout écran imposé avec la passerelle `live` (§5.2).

### 5.2 Le hook du parcours (`runtime/useExperienceFlow.ts`)

```ts
useExperienceFlow({ config, campaign, services, locale, source?, initialScreen?, now? })
  → { state, canSubmit, couponStatus, start, updateField, setConsent, submit, startDraw,
      completeInteraction, completeReveal, confirmCoupon, retry, restart, track }
```

**L'état** vit dans `useReducer(flowReducer)`, comme le demande la fiche. L'état de départ vient de `createInitialFlowState`, avec le timing de la campagne (un quiz sans question est tiré tout de suite, T1.10), ou de `createPreviewFlowState` pour un écran imposé.

**Les actions** sont celles des écrans : aucun écran ne parle aux services. Le hook ajoute ce que le domaine ne sait pas produire : l'horodatage du consentement (`now()`) et un `clientRequestId` neuf à chaque `submit` (`createClientRequestId`, UUID). `submit` ne fait rien hors de l'inscription et, si le formulaire n'est pas valide, **rapporte `form_invalid` sans rien envoyer**.

**Les effets suivent les transitions.** Un effet compare l'état précédent (gardé dans une `ref`) au nouveau :

```ts
const previous = useRef(state);
useEffect(() => {
  const prev = previous.current;
  previous.current = state;
  if (prev === state) return;
  for (const event of transitionEvents(prev, state)) {
    track(event.name, state.screen, event.data);
  }
  const command = nextCommand(prev, state);
  if (command === "DRAW") void draw(state);
  if (command === "CONFIRM" && state.entryId) void confirm(state.entryId);
}, [state, track, draw, confirm]);
```

- `nextCommand` (T1.10) dit « DRAW » à l'entrée dans `resolving` (premier essai **ou** `RETRY`), « CONFIRM » quand le coupon vient d'être confirmé. Comme le reducer garde le même `clientRequestId` et la même charge utile au `RETRY`, **le serveur ne compte jamais deux fois la même tentative**.
- Le mode strict de React rejoue les effets au montage : l'état n'ayant pas changé (`prev === state`), rien n'est lancé deux fois.
- Deux événements envoyés dans le même lot de rendu seraient vus comme une seule transition. Ce n'est jamais le cas d'une commande : le tirage est asynchrone.

**Le tirage (`draw`)** : jeton de vérification humaine (`null` au MVP ; s'il échoue, `null` aussi, le serveur décidera), requête (`buildDrawRequest`), analytics `draw_requested`, appel de la passerelle. Une passerelle qui **lève une exception** (au lieu de renvoyer une erreur) devient `UNKNOWN`, que le joueur peut réessayer. Une réponse qui arrive **après le démontage** est ignorée (`mounted`).

**Ce que lisent les effets** : la configuration, la campagne, les services, la langue et la source **du moment** (une `ref` mise à jour après chaque rendu). Le Studio peut changer de passerelle ou de langue pendant la partie sans la redémarrer.

**La confirmation du coupon** : `couponStatus` passe de `idle` à `sending`, puis `confirmed` ou `failed`. Le statut est **rattaché à son `entryId`** : après un `RESTART`, il revient à `idle` de lui-même. Le reducer n'accepte qu'une confirmation (T1.10) : un deuxième appui ne renvoie rien.

**Analytics** (plan §7.5). Chaque événement porte `{ name, at, campaignId, sessionId, screen, locale }` et des données **plates, sans donnée personnelle** (un test vérifie que ni le téléphone ni le nom n'apparaissent). Un traqueur qui lève une exception est ignoré : il ne casse jamais le parcours.

| Événement                                                         | Émis par                                                                   |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `experience_viewed`                                               | Le montage (une fois)                                                      |
| `form_invalid`                                                    | `submit` sur un formulaire invalide                                        |
| `form_submitted`, `game_started`                                  | La transition `register → play` (`game_started` seul pour un écran imposé) |
| `draw_requested`                                                  | Le départ de la requête (`data.payload` : `none`, `quiz`…)                 |
| `outcome_received`, `reveal_completed`                            | L'entrée dans `revealing`, puis sa sortie (`isWinner`)                     |
| `error_shown`                                                     | Chaque nouvelle erreur (`code`)                                            |
| `coupon_confirmed`                                                | La réponse de la confirmation (`ok`)                                       |
| `cta_clicked`, `consent_opened`, `coupon_copied`, `share_clicked` | Les écrans, par `flow.track` (ce que le parcours ne voit pas)              |

La correspondance transition → événements est une fonction pure, `transitionEvents(prev, next)`, testée à part.

**La passerelle `live`** : `initialScreen` est ignoré (avec un avertissement en console) et la source par défaut devient `web_player` ; sinon `studio_preview`.

### 5.3 Le composant racine (`runtime/PlayerExperience.tsx`)

Les props du plan §8.1 : `config`, `campaign`, `locale`, `allowedGatewayModes`, `initialScreen?`, `onFlowEvent?` (plus `source?`). **Pas de prop `surface`** : un seul mode de rendu, le document plein.

- **Services** : lus par `useExperienceServices()` (injectés par `ServicesProvider`, jamais créés ici).
- **Thème** : `ThemeScope` pose les variables, `dir`, `lang` et le fond (image résolue par `AssetStorage`) ; la police est chargée. `PlayerExperience` est la **racine du runtime** (`.xp-runtime`, celle que l'audit de T3.8 examine).
- **Garde de passerelle** (plan §7.4, N1) : si le mode de la passerelle n'est pas dans `allowedGatewayModes`, l'écran « Jeu indisponible » remplace le parcours. Sur la page publique (`["live"]`), une passerelle de démo injectée par erreur ne tirera jamais de résultat dans le navigateur.
- **Badge DEMO** (B6) : dans l'en-tête du cadre dès que la passerelle n'est pas `live`, du côté de fin de lecture et dans les zones sûres (règles de T3.3 et T3.4). Le point « live » suit le statut de la campagne (`active`).
- **Le parcours survit à tout, sauf à un nouveau jeu** : le composant `Journey` porte une clé faite de la campagne, du jeu, du timing et de l'écran imposé. Changer un texte, le thème, la langue ou la taille ne la change pas : l'état reste dans le reducer (critère de la fiche). Changer de jeu ou d'écran imposé repart de zéro.
- **`onFlowEvent(screen)`** est appelé à chaque écran affiché, y compris le premier.

### 5.4 Les écrans (`runtime/screens/`)

**Écrans provisoires (`PendingScreen.tsx`)**, jusqu'aux vrais écrans de T4.2 à T4.4 et aux jeux de la phase 5. Chacun a déjà **son cadre, son contenu, son CTA branché sur le parcours** (B4) et **une sortie** (B9) ; le slot 5 dit ce qui le remplira.

| Écran du parcours     | Contenu (slots 1 à 4)                                             | Slot 5                                                              | CTA (slot 7)                                                                                                 |
| --------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `welcome`             | `screens.welcome` + sections (jackpot, chips)                     | « Game teaser » (T4.2, puis phase 5)                                | `START`                                                                                                      |
| `register`            | `screens.register`                                                | « Registration form » (T4.2) ; message d'une erreur `INVALID_INPUT` | `SUBMIT`, **désactivé** tant que le formulaire est invalide                                                  |
| `play`                | `screens.play`                                                    | « Game engine » (phase 5)                                           | `DRAW_STARTED` pour la roue et le grattage ; aucun pour un jeu joué d'abord (son moteur enverra le résultat) |
| `resolving`           | `screens.play`                                                    | Médaillon avec arc tournant et « Préparation de votre partie… »     | Aucun : le tirage est en cours                                                                               |
| `revealing`           | `screens.play`                                                    | « Game engine » ; la révélation se termine aussitôt                 | Aucun                                                                                                        |
| `win`                 | `screens.win`                                                     | Médaillon cadeau, nom du lot, code                                  | `RESTART` (« Terminer »)                                                                                     |
| `lose`                | `screens.lose`                                                    | Médaillon trèfle                                                    | `RESTART`                                                                                                    |
| `duplicate`, `closed` | Titre de `STATUS_TEXT`, message de `PARTICIPATION_ERROR_MESSAGES` | Médaillon (utilisateur validé, calendrier barré)                    | « Retour » → `RESTART`                                                                                       |
| `error`               | Idem                                                              | Médaillon (wifi coupé)                                              | « Réessayer » → `RETRY` ; secondaire « Retour » → `RESTART`                                                  |

Chaque appui rapporte `cta_clicked` (`{ cta: "primary" | "secondary" }`) avant d'émettre son événement.

**`GatewayRefusedScreen.tsx`** (définitif) : titre « Jeu indisponible », message « Revenez un peu plus tard » (fr, ar, en), médaillon sablier, **aucun CTA**, pied de page et liens légaux conservés (B9), badge DEMO si la passerelle n'est pas `live`, point « live » éteint. Le développeur reçoit la raison en console (`console.error` : le mode reçu et les modes autorisés).

**`ScreenMedallion.tsx`** : le corps du slot 5 des écrans sans jeu, dans le style du héros du slot 2 (dégradé radial, anneau et halo dans la couleur de marque), dimensionné sur le slot (`cqmin`), avec un arc tournant pour l'attente (arrêté en mouvement réduit par les règles existantes de `frame.css`). Jamais un simple texte sur un fond vide (D12).

**`textContent.ts`** : le `ScreenContent` d'un écran que les marques ne modifient pas (attente, statut, indisponible), pour que le cadre le dessine comme les autres.

### 5.5 L'hôte `/xp-frame` (`runtime/host/`)

**`FrameExperience.tsx`** compose le parcours de l'aperçu : `createLocalServices({ participation, campaign, scenario })`, puis `ServicesProvider` et `PlayerExperience` (modes autorisés : `demo` et `scripted`), dans une enveloppe qui pose les zones sûres reçues. Les services ne changent qu'avec **le contenu** de la campagne (clé JSON) : le Studio renvoie la campagne avec chaque configuration, et recréer la passerelle à chaque frappe serait inutile. Une nouvelle passerelle ne redémarre de toute façon jamais le parcours, qui la lit au moment du tirage.

**`createLocalServices` accepte désormais `campaign`** : sans règles fournies, les règles de démo autonomes sont construites sur la campagne **reçue** (et plus sur la campagne de démonstration par défaut). Sans cela, la passerelle de démo aurait tiré selon les règles de la roue pour un quiz, ou répondu « campagne fermée » pour une autre campagne.

**Le pont (`BridgeFrame`)** applique maintenant tout le message `xp:ui` (T3.3 n'en appliquait que la langue et les zones sûres) :

| Champ de `xp:ui`     | Effet dans le cadre                                                                                                                      |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `mode`               | `demo` : passerelle de démo (vraies chances, anti-doublon) ; `scripted` et `static` : passerelle scriptée                                |
| `scenario`           | Le résultat de la passerelle scriptée                                                                                                    |
| `screen`             | Écran imposé (`initialScreen`) ; `status` montre celui du scénario (doublon, fermée, sinon erreur) ; en `static` sans onglet : l'accueil |
| `restartKey`         | Une nouvelle valeur redémarre le parcours                                                                                                |
| `locale`, `safeArea` | Comme en T3.3                                                                                                                            |

Il relaie `xp:flow-event` à chaque écran affiché, pour l'onglet d'écran du Studio.

**La fenêtre séparée (`LocalFrame`)** joue le parcours de démo de la configuration enregistrée. **Les fixtures** gagnent la vue `flow` : `flow-welcome` (parcours complet, passerelle scriptée, perte) et `flow-gateway-refused` (une page qui n'accepte que `live`, avec une passerelle de démo).

## 6. Décisions et alternatives

| Décision                                                                | Alternative écartée                                             | Raison                                                                                                                            |
| ----------------------------------------------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `buildDrawRequest` et `createPreviewFlowState` dans le domaine          | Les écrire dans le hook                                         | « Aucune logique métier dans le composant : tout vient du domaine » ; fonctions pures, testées sans React                         |
| `useReducer` + effet sur les transitions                                | Machine hors de React, avec un `send` qui calcule la transition | La fiche le demande ; les effets de React servent à se synchroniser avec l'extérieur ; aucune commande ne peut être fusionnée     |

## 9. Écarts, imprévus et points d'attention

### 9.1 Ajouts hors fiche (à valider, R5)

La fiche nomme deux fichiers. Pour la tenir entièrement (« props du plan §8.1 », « tout vient du domaine », « `FrameHost` rend désormais `PlayerExperience` »), j'ai ajouté :

- **`buildDrawRequest` et `createPreviewFlowState`** dans `domain/flow.ts` (§5.1).
- **`initialScreen`** (prop du plan §8.1) et son garde-fou en `live`.
- **Les écrans provisoires** (`PendingScreen`) : sans eux, `PlayerExperience` n'aurait rien à afficher avant T4.2. Ils seront remplacés écran par écran.
- **L'écran de refus** et ses deux textes (fr, ar, en) dans `STATUS_TEXT` : l'« écran d'erreur explicite » de la fiche.
- **Tout `xp:ui` appliqué** par le pont (T3.3 l'avait reporté « à partir de T4.1 ») et l'option `campaign` de `createLocalServices`.
- **Deux fixtures** du parcours, et la fenêtre séparée qui joue le parcours.

### 9.2 Imprévu : `tsconfig.json` n'est pas strict

`if (result.ok) … else result.error` ne compile pas : sans `strictNullChecks`, TypeScript ne restreint pas une union sur la seule vérité d'un booléen littéral. J'utilise une comparaison explicite (`result.ok === false`), commentée. Le reste du module n'était pas concerné.

### 9.3 Points d'attention pour la suite

- **Mode `static` (« Still screen »)** : le cadre démarre sur l'onglet choisi avec la passerelle scriptée, mais le parcours reste jouable (un appui sur le CTA avance). Si le Studio veut un écran vraiment figé, c'est à décider en T6.2.
- **Le Studio ne doit pas renvoyer `screen` en écho à `xp:flow-event`** : un nouvel écran imposé redémarre le parcours (T6.2).
- **Un clic sur le CTA dans l'aperçu** envoie aussi `xp:edit-target` (le bouton porte `data-xp-edit`, T3.4). En mode « Full flow », le Studio voudra sans doute ignorer ces clics (T6.2).
- **Disponibilité de la campagne** : `checkAvailability` n'est pas appelé au démarrage. La machine d'états n'a pas d'événement pour « fermée avant de jouer », et le serveur refuse de toute façon au tirage (`CAMPAIGN_CLOSED`). À décider avec T4.3 si l'on veut prévenir dès l'accueil.
- **Règles de démo dans l'aperçu** : seul l'instantané de la campagne traverse le pont (B2 : aucune probabilité ni stock dans le runtime) ; la passerelle de démo du cadre utilise donc les règles autonomes (50 % de gain, stock de 100). Les vraies règles d'une campagne réelle sont un sujet de T6.x.
- **La source `demo`** de `DrawRequest.context` n'est pas utilisée (réservée au lien de démo, reporté après le MVP).
- **Console en développement** : l'écran de refus écrit son erreur deux fois par chargement (le mode strict de React rejoue les effets) ; une seule fois en production. Pour cette raison, la fixture `flow-gateway-refused` n'est pas faite pour le balayage, qui compte les erreurs de console.
