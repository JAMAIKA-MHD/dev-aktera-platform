## 5. Le code expliqué

### 5.1 La clé

Une clé par campagne, versionnée : `xp:experience:v1:<id de la campagne>`, ou `xp:experience:v1:standalone` sans campagne (démo). Le `v1` permettra, si un jour le stockage change de forme, de lire l'ancienne clé sans conflit.

### 5.2 `load` : relire sans jamais planter

1. Lire la clé. Si le stockage est **bloqué** (navigation privée, réglages du site), il n'y a rien à lire : `null`, et le Studio part des valeurs par défaut.
2. Rien d'enregistré → `null`.
3. Décoder le JSON. S'il est illisible, on le note (« the stored value is not valid JSON »).
4. `parseExperienceConfig` (T1.6) : montée de version (T1.9), validation et **réparation champ par champ**. `scope.fallbackGameType` donne le jeu à reconstruire si tout est illisible.
5. Si la configuration porte l'identifiant d'**une autre campagne** que sa clé (copie manuelle, par exemple), l'identifiant est aligné sur la clé et le problème est noté. Sinon, le prochain enregistrement irait sous une autre clé.
6. S'il y a eu des problèmes, un avertissement console (`[player-experience] … was repaired: …`).

Le résultat est un `ParseResult` : `{ config, issues, recovered }`. **Rien n'est réécrit au chargement** : les données d'origine restent intactes jusqu'à ce que la marque enregistre.

Une configuration d'une ancienne version, seulement **migrée**, n'est pas une réparation : aucun problème, aucun avertissement.

### 5.3 `save` : enregistrer sans écraser le travail d'un autre onglet

1. Lire la date `updatedAt` de la configuration déjà enregistrée.
2. **Contrôle optimiste** : si l'appelant donne `expectedUpdatedAt` (la date de la version qu'il avait chargée) et que la version enregistrée a une autre date, un autre onglet a enregistré entre-temps : `CONFLICT`, rien n'est écrit.
3. Nouvelle date `updatedAt` : maintenant, et **toujours plus tard que la précédente**, même pour deux enregistrements dans la même milliseconde (+1 ms). Sinon, un autre onglet pourrait ne pas voir un changement.
4. Écrire le JSON et renvoyer la configuration **telle qu'enregistrée**, relue depuis le JSON.

La configuration passée en paramètre n'est jamais modifiée.

| Situation                                            | Résultat                                                                                  |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Rien de changé depuis le chargement                  | Enregistré                                                                                |
| Pas de contrôle demandé (`expectedUpdatedAt` absent) | Enregistré (écrase)                                                                       |
| Autre onglet a enregistré entre-temps                | `CONFLICT` : « This experience was saved meanwhile in another tab or window. Reload it… » |
| Donnée enregistrée illisible (pas de date)           | Enregistré : il n'y a rien de fiable à protéger                                           |
| Quota dépassé                                        | `STORAGE_FULL` : « The browser storage is full, usually because of large images… »        |
| Stockage bloqué                                      | `STORAGE_UNAVAILABLE` : « The browser blocks local storage… »                             |

**Quota dépassé.** Chrome, Safari et Edge lèvent `QuotaExceededError` ; d'anciennes versions de Firefox, `NS_ERROR_DOM_QUOTA_REACHED`. Les deux sont reconnus. Toute autre exception signifie un stockage inutilisable.

### 5.4 Injection pour les tests

`createLocalExperienceRepository({ getStorage, now, warn })` : le stockage, l'horloge et l'avertissement peuvent être remplacés.

- `getStorage` est une **fonction**, pas une valeur : dans certains navigateurs, le simple accès à `window.localStorage` lève une exception quand le stockage est bloqué. Elle est appelée à chaque opération, à l'intérieur d'un `try`.
- Par défaut : le vrai `localStorage`, l'heure réelle et `console.warn`.

## 6. Décisions et alternatives

| Décision                                                          | Alternative écartée                    | Raison                                                                        |
| ----------------------------------------------------------------- | -------------------------------------- | ----------------------------------------------------------------------------- |
| Pas de réécriture au chargement                                   | Réenregistrer la configuration réparée | Non destructif : la marque décide en enregistrant                             |
| `updatedAt` strictement croissant                                 | Heure brute                            | Deux enregistrements dans la même milliseconde seraient indiscernables        |
| Stockage bloqué au chargement → `null`                            | Erreur                                 | Le Studio reste utilisable ; c'est l'enregistrement qui signalera le problème |
| Identifiant de campagne aligné sur la clé                         | Garder celui du fichier                | Sinon l'enregistrement suivant partirait sous une autre clé                   |
| Pas d'appel séparé à `migrateExperienceConfig` (la fiche le cite) | L'appeler ici aussi                    | `parseExperienceConfig` l'appelle déjà (T1.9) : un seul point d'entrée        |

## 9. Écarts, imprévus et points d'attention

- **Piège TypeScript à retenir pour la suite.** Le projet n'est pas en mode strict. Sans `strictNullChecks`, TypeScript ne réduit **pas** un résultat `{ ok: true } | { ok: false }` avec `if (!result.ok)`. Mes tests l'utilisaient : la passe non stricte a échoué. Correction : écrire `result.ok === false`, qui fonctionne dans les deux modes. **Tout le code qui lira `SaveResult`, `DrawResult` ou `UploadResult` devra faire de même** ; je l'appliquerai en T2.4 et en phase 4. Activer le mode strict pour tout le projet (question déjà posée en T1.6) supprimerait ce piège.
- **Pas d'appel séparé aux migrations** (§6) : `parseExperienceConfig` s'en charge.
- **Pas de synchronisation en direct entre onglets** (événement `storage`) : le conflit est détecté à l'enregistrement, ce que demande la fiche. Un rafraîchissement automatique pourrait être ajouté dans le Studio (phase 6).
