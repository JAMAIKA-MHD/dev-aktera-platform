## 1. Objectif

Dernière tâche de la phase 2 : **assembler** les adaptateurs locaux (T2.2 à T2.5) et les **rendre disponibles** dans l'arbre React.

| Pièce                          | Rôle                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------ |
| `createLocalServices(options)` | Construit l'objet `ExperienceServices` complet du MVP (Studio, démonstrations) |
| `ServicesProvider`             | Injecte cet objet dans l'arbre React                                           |
| `useExperienceServices()`      | Le lit, depuis n'importe quel composant du runtime ou du Studio                |
| `services/supabase/README.md`  | La feuille de route des adaptateurs Supabase, après le MVP                     |

## 2. Où elle se situe

```
src/features/player-experience/
├── index.ts                          ← exporte createLocalServices et ServicesProvider
├── README.md                         ← règle de dépendance précisée
└── services/
    ├── createLocalServices.ts        ← NOUVEAU : racine de composition
    ├── ServicesProvider.tsx          ← NOUVEAU : contexte React + hook
    ├── createLocalServices.test.ts   ← NOUVEAU : 7 tests
    ├── ServicesProvider.test.tsx     ← NOUVEAU : 2 tests
    ├── local/demoRules.ts            ← + règles de la campagne de démonstration
    └── supabase/README.md            ← NOUVEAU (remplace .gitkeep)
```

Comment l'expérience recevra ses services :

```
Studio (phase 6)              <ServicesProvider services={createLocalServices({ rules })}>
Page publique (après MVP)     <ServicesProvider services={createSupabaseServices()}>
                                        │
                              runtime, Studio : useExperienceServices()
                                        │
                     repository · participation · assets · analytics · humanVerification
```

Le runtime ne crée **jamais** d'adaptateur lui-même : il reçoit ce qu'on lui injecte. C'est ce qui permettra de passer du local à Supabase sans toucher aux écrans.

## 5. Le code expliqué

### 5.1 `createLocalServices(options)`

| Option          | Défaut                                     | Effet                                                                                 |
| --------------- | ------------------------------------------ | ------------------------------------------------------------------------------------- |
| `participation` | `"demo"`                                   | `"demo"` : tirage simulé honnête (T2.3, T2.4). `"scripted"` : résultat choisi (T2.4)  |
| `rules`         | Règles de la **campagne de démonstration** | Règles de tirage de la campagne en cours d'édition (`buildDemoRules(campaign)`, T2.3) |
| `scenario`      | `"lose"`                                   | Scénario de départ de la passerelle scriptée                                          |

Les cinq services sont toujours présents :

| Service             | Adaptateur                                                                                                       |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `repository`        | `createLocalExperienceRepository()` (T2.2)                                                                       |
| `participation`     | `createDemoParticipationGateway({ rules })` ou `createScriptedParticipationGateway({ scenario, prizes })` (T2.4) |
| `assets`            | `createDataUrlAssetStorage()` (T2.5)                                                                             |
| `analytics`         | `createConsoleAnalyticsTracker()` (T2.5)                                                                         |
| `humanVerification` | `createNoopHumanVerification()` (T2.5)                                                                           |

En mode scripté, les noms et messages des lots viennent des mêmes règles : « `win-voucher` » affiche le vrai nom du lot.

### 5.2 La campagne de démonstration peut maintenant être jouée

Point laissé ouvert en T2.3 : sans vraie campagne, le Studio utilise la campagne de démonstration (T1.8), dont les 3 questions n'avaient **pas de bonnes réponses**.

`buildStandaloneDemoRules(campagne)` fournit ses règles de tirage :

| Règle                     | Valeur                         | Pourquoi                                                                                                             |
| ------------------------- | ------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| Probabilité de gain       | **50 %**                       | On voit vite les deux issues dans le Studio                                                                          |
| Lots                      | Tous de poids 1, 100 en stock  | Chaque lot a sa chance, sans rupture                                                                                 |
| Participations par numéro | 1                              | Comme en production : l'écran « déjà joué » se voit aussi (le bouton de réinitialisation du Studio remet à zéro)     |
| Bonnes réponses           | Alger, 58, Le Sahara           | Rangées avec les autres secrets du tirage dans `services/local/`, **pas** dans les presets, que le runtime peut lire |
| Règles de jeu             | Seulement celles du jeu choisi | La campagne de démonstration porte les deux jeux de règles (quiz et Hit It)                                          |

Un test vérifie les bonnes réponses **par leur texte** (« Alger », « 58 », « Le Sahara »). Si les questions de démonstration changent, il échoue.

### 5.3 `ServicesProvider` et `useExperienceServices()`

- `<ServicesProvider services={…}>` place les services dans un contexte React.
- `useExperienceServices()` les lit. **Hors d'un provider**, il lève une erreur explicite qui dit quoi faire : « useExperienceServices() must be used inside <ServicesProvider>. Wrap the experience in <ServicesProvider services={createLocalServices()}>… ». Un oubli se voit donc tout de suite, au lieu d'une erreur obscure plus loin.

### 5.4 `services/supabase/README.md`

En anglais, comme tout le code du module (règle R0). Il contient :

- les 5 adaptateurs Supabase à écrire après le MVP, avec leur backend ;
- la correspondance `DrawRequest` → corps de `select-prize`, et réponse → `DrawResult` (plan §7.2) ;
- **les erreurs du serveur sans code**, avec leur traduction (« Campaign is not active. » → `CAMPAIGN_CLOSED`, doublon Postgres `23505` → `ALREADY_PARTICIPATED`, téléphone invalide → `INVALID_INPUT`…) : noté depuis T1.5 ;
- **les défauts du serveur** trouvés en écrivant la démo : seuil de Hit It non appliqué, consentement non vérifié, bonnes réponses du quiz publiques, mode « auto-pace » non simulé.

### 5.5 API publique du module

`index.ts` exporte désormais `createLocalServices` et `ServicesProvider`, comme T0.3 l'avait prévu. Le reste de l'application pourra monter l'expérience avec ses services sans importer de fichier interne (règle ESLint des frontières).

## 6. Décisions et alternatives

| Décision                                                            | Alternative écartée                      | Raison                                                                                                             |
| ------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Règles de la démo par défaut                                        | `rules` obligatoire                      | `createLocalServices()` sans argument doit donner une expérience jouable (Studio sans campagne, tests)             |
| Bonnes réponses de la démo dans `services/local/`                   | Dans `presets/demoCampaign.ts`           | Les presets sont lisibles par le runtime ; les réponses sont un secret du tirage, même en démo                     |
| La racine de composition lit la campagne de démonstration (presets) | Aucune dépendance `services` → `presets` | Seul `createLocalServices.ts` le fait, et seulement pour une donnée pure ; règle précisée dans le README du module |
| Scénario scripté par défaut : `lose`                                | `win-<premier lot>`                      | Neutre, et toujours valable, même sans lot                                                                         |
| Une participation par numéro dans la démo                           | Illimité                                 | Reproduit la production ; la réinitialisation existe (T2.3)                                                        |
| README Supabase en anglais                                          | En français                              | C'est de la documentation de code, dans le module (R0)                                                             |
