## 1. Objectif

Implémenter le port `ParticipationGateway` (T2.1) pour le Studio, de deux façons :

| Passerelle        | Mode       | À quoi elle sert                                                                                                            |
| ----------------- | ---------- | --------------------------------------------------------------------------------------------------------------------------- |
| **Démonstration** | `demo`     | Jouer « pour de vrai » dans le Studio : tirage simulé honnête (T2.3), mêmes refus que le serveur, participations mémorisées |
| **Scriptée**      | `scripted` | Vérifier chaque écran : le Studio **choisit** le résultat (gain de tel lot, perte, doublon, campagne fermée, erreur réseau) |

Les deux renvoient exactement la même forme de résultat que le serveur (`DrawResult`, T1.5). Le parcours (T1.10) et les écrans ne font donc aucune différence entre démo, script et production.

## 5. Le code expliqué

### 5.1 La passerelle de démonstration

`draw(request)`, étape par étape :

1. **Avertissement console**, une seule fois : « Demo gateway — outcomes are simulated client-side. Never use on the public player route. »
2. **Latence réaliste** : attente aléatoire de 400 à 900 ms, comme un vrai réseau. L'écran d'attente du parcours est donc réellement vu et testé dans le Studio.
3. **Idempotence** : si ce `clientRequestId` a déjà été traité, la **même** réponse est renvoyée, sans nouveau tirage ni nouvelle participation. C'est ce qui rend `RETRY` (T1.10) sûr.
4. **Contrôles, dans l'ordre de `select-prize`** :

| #   | Contrôle                                                          | Erreur                 | Message (celui du serveur)                                          |
| --- | ----------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------- |
| 1   | Campagne et téléphone présents                                    | `INVALID_INPUT`        | « campaign_id and phone_number are required. »                      |
| 2   | Mobile algérien valide après normalisation                        | `INVALID_INPUT`        | « Invalid Algerian phone number format. »                           |
| 3   | **Consentement accepté** (ajout, §6)                              | `INVALID_INPUT`        | « Consent is required before playing. »                             |
| 4   | Bonne campagne, et campagne active                                | `CAMPAIGN_CLOSED`      | « Campaign is not active. »                                         |
| 5   | Participations de ce numéro < limite (`maxEntries`, 0 = illimité) | `ALREADY_PARTICIPATED` | « You have already participated in this campaign. »                 |
| 6   | Il reste du stock (stock réel moins gains de démo)                | `CAMPAIGN_CLOSED`      | « This campaign is closed. All voucher rewards have been claimed. » |

5. **Tirage** : `drawDemoOutcome` (T2.3) sur les règles avec le stock de démo.
6. **Enregistrement** dans `demoEntryStore` : identifiant de participation (UUID), numéro normalisé, identifiant de requête, résultat, date. Une **perte** est enregistrée aussi : elle compte comme une participation, comme sur le serveur.

`checkAvailability(campaignId)` : `CLOSED` (autre campagne, ou campagne non active), `SOLD_OUT` (plus de stock de démo), sinon ouverte.

`confirmCoupon(entryId)` : marque le coupon comme confirmé ; identifiant inconnu → `INVALID_INPUT`.

**Tout est injectable** pour les tests : règles, magasin, hasard, latence, attente, horloge, avertissement.

### 5.2 La passerelle scriptée

| Scénario          | Résultat                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `win-<id du lot>` | Gain de ce lot : nom et message tirés des lots fournis (sinon, l'identifiant sert de nom), code `DEMO-XXXX-XXXX` |
| `lose`            | Perte                                                                                                            |
| `duplicate`       | `ALREADY_PARTICIPATED`                                                                                           |
| `closed`          | `CAMPAIGN_CLOSED` (et `checkAvailability` → fermée)                                                              |
| `network-error`   | `NETWORK` : permet de tester l'écran d'erreur et le bouton « Réessayer »                                         |

- `setScenario(scénario)` : le sélecteur du Studio change le résultat sans recréer la passerelle.
- Latence courte et fixe : **300 ms**.
- **Aucun effet de bord** : rien n'est enregistré (test : `localStorage` reste vide).
- Même avertissement console que la démo, une fois.
- Un scénario inconnu renvoie `UNKNOWN` plutôt que de planter.

### 5.3 Même forme de résultat

Un test compare la **structure** (toutes les clés, récursivement) des résultats des deux passerelles pour un gain, une perte et un doublon : elles sont identiques. Si l'une ajoutait ou oubliait un champ, le test échouerait (vérifié par mutation, §7).

## 6. Décisions et alternatives

| Décision                                                  | Alternative écartée                                      | Raison                                                                                                   |
| --------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Consentement vérifié par la démo                          | Reproduire le serveur, qui ne le vérifie pas             | Règle N3 (loi 18-07) : aucune participation sans consentement. **Le serveur devrait faire de même** (§9) |
| Idempotence par `clientRequestId`                         | Tirer à chaque appel                                     | Un `RETRY` après une coupure ne doit ni tirer deux fois ni compter un doublon                            |
| Stock épuisé = tous les lots à 0                          | Recalculer `quantité totale ≤ gagnants` comme le serveur | Les règles de démo portent le stock restant ; même résultat sauf pour des lots de quantité 0 (§9)        |
| Avertissement par passerelle, au premier tirage           | Une fois pour toute l'application                        | Simple et testable ; une passerelle est créée une fois par session du Studio                             |
| Pas de latence sur `checkAvailability` et `confirmCoupon` | Latence partout                                          | La fiche ne la demande que pour le tirage ; ces appels ne pilotent pas d'écran d'attente                 |
| `setScenario` sur la passerelle scriptée                  | Recréer la passerelle à chaque changement                | Le sélecteur du Studio change de scénario sans reconstruire les services                                 |

## 9. Écarts, imprévus et points d'attention

- **Le serveur ne vérifie pas le consentement.** `select-prize` accepte une participation sans aucune preuve de consentement : seul le client l'impose. La démo le vérifie. **Côté serveur, c'est à ajouter** (hors périmètre : `supabase/` non modifiable ici), avec l'enregistrement du `ConsentRecord` (heure, version de la politique, langue) exigé par la loi 18-07.
- **Rappel T2.3** : le serveur laisse gagner un joueur de Hit It sous le seuil ; la démo, non. Pour Hit It, la démo est donc plus stricte que la production tant que le serveur n'est pas corrigé.
- **Stock épuisé** : pour une campagne dont des lots ont une quantité 0, la démo peut se déclarer fermée là où le serveur ne le ferait pas. Cas marginal.
- **Nom de lot absent** dans le scénario scripté : l'identifiant sert de nom, pour que l'écran de gain reste lisible.
- **Interruption** : la tâche a été mise en pause après l'écriture des passerelles, puis reprise (voir journal).

## 10. Qualité visuelle

Sans interface. Deux choix servent directement l'expérience vue dans le Studio : la latence réaliste, qui fait réellement voir l'écran d'attente, et la passerelle scriptée, qui permet de contrôler chaque écran (gain, perte, doublon, fermeture, erreur réseau) sans jouer des dizaines de fois.
