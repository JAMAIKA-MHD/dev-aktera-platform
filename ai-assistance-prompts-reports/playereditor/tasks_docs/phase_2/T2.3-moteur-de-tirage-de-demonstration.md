## 1. Objectif

Dans le Studio, la marque doit pouvoir **jouer** à son expérience sans toucher à la vraie base : ni vraie participation, ni vrai stock consommé, ni vrai code distribué. Il faut donc **simuler le serveur**, et le simuler **honnêtement** : mêmes règles, mêmes chances, mêmes refus.

Trois pièces :

| Fichier             | Rôle                                                                                               |
| ------------------- | -------------------------------------------------------------------------------------------------- |
| `demoRules.ts`      | Extraire de la campagne ce qui décide du gain (probabilité, stock, poids, bonnes réponses, seuils) |
| `demoDrawEngine.ts` | Décider d'un résultat comme le serveur, avec un hasard injectable                                  |
| `demoEntryStore.ts` | Mémoriser les participations de démo : anti-doublon, stock de démo, réinitialisation               |

La passerelle de démonstration (T2.4) assemblera les trois.

## 2. Où elle se situe

```
src/features/player-experience/services/local/
├── demoRules.ts           ← NOUVEAU : buildDemoRules(campaign)
├── demoDrawEngine.ts      ← NOUVEAU : drawDemoOutcome(rules, payload, random)
├── demoEntryStore.ts      ← NOUVEAU : createDemoEntryStore(), withDemoStock()
└── *.test.ts              ← NOUVEAUX : 34 tests
```

Chemin d'une participation de démo (branché en T2.4) :

```
Campaign (useCampaigns) ──buildDemoRules──► DemoCampaignRules  (secrets du tirage)
                                                   │ withDemoStock (moins les gains de démo)
                                                   ▼
GamePayload du joueur ────────────────────► drawDemoOutcome ──► DrawOutcome
                                                                     │
                                                    demoEntryStore.record (localStorage)
```

**Cloisonnement.** Ces règles contiennent des secrets du tirage (probabilité, stock, **bonnes réponses**). Elles vivent dans `services/local/`, que le runtime n'a **pas le droit** d'importer (règle ESLint de T0.3). Elles ne sont jamais copiées dans `ExperienceConfig` ni dans le `CampaignSnapshot` du joueur.

## 5. Le code expliqué

### 5.1 Ce que fait réellement le serveur

J'ai relu les trois étages du serveur avant d'écrire la simulation :

| Étape             | Où                              | Règle                                                                                                                                                    |
| ----------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Données reçues | `select-prize`                  | Campagne et téléphone requis ; téléphone algérien valide après normalisation                                                                             |
| 2. Campagne       | `select-prize`                  | Elle doit exister et être `active`                                                                                                                       |
| 3. Doublon        | `select-prize`                  | Nombre de participations de ce téléphone ≥ `max_entries` (défaut 1 ; 0 = illimité) → `ALREADY_PARTICIPATED`                                              |
| 4. Stock global   | `select-prize`                  | Tous les lots distribués → `CAMPAIGN_CLOSED`                                                                                                             |
| 5. Jeu d'adresse  | `resolve_game_outcome`          | Quiz : score = bonnes réponses / questions actives × 100, réussi si ≥ seuil (défaut 100). Hit It : réussi si touches ≥ seuil (défaut 1)                  |
| 6. Tirage         | `draw_and_claim_campaign_prize` | Échec au jeu d'adresse → perdu. Sinon, hasard ≤ probabilité de gain → tirage **pondéré** parmi les lots **encore en stock** ; aucun lot en stock → perdu |

`drawDemoOutcome` reproduit les étapes 5 et 6. Les étapes 1 à 4 sont des refus, que la passerelle (T2.4) vérifiera **avant** d'appeler le moteur.

### 5.2 `buildDemoRules` : les règles de la campagne

À partir du modèle `Campaign` du tableau de bord (`useCampaigns`) :

| Règle            | Source                                              | Détail                                                                                                 |
| ---------------- | --------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `active`         | `status === "active"`                               | Seul statut pour lequel le serveur tire                                                                |
| `winProbability` | `winProbability` (0–100)                            | Bornée entre 0 et 100 ; valeur illisible → 0                                                           |
| `maxEntries`     | `"1"` → 1, `"2"` → 2, `"unlimited"` → 0, absent → 1 | Comme `campaignService` l'enregistre                                                                   |
| `prizes`         | Lots enregistrés                                    | Nom (via le modèle de lot, comme T1.8), poids, **stock restant** = quantité − déjà gagnés (jamais < 0) |
| `quiz`           | Questions + `pass_threshold_percentage`             | **Bonnes réponses** incluses : c'est ici, et seulement ici, qu'elles existent côté client              |
| `hitIt`          | `win_threshold`                                     | Défaut 1, comme la RPC                                                                                 |

Les noms des lots et les seuils viennent de `buildCampaignSnapshot` (T1.8) : les règles de démo et ce que voit le joueur ne peuvent pas diverger.

### 5.3 `drawDemoOutcome` : le tirage

1. **Jeu d'adresse** (`passesSkillGate`) : quiz ou Hit It raté → perdu, sans tirage. Une réponse n'est comptée que pour une question **de la campagne**, et seulement si c'est une propriété propre de l'objet des réponses : une clé héritée (`constructor`…) ne peut pas tricher. Un quiz sans question donne un score de 0, comme la RPC.
2. **Probabilité** : `random() × 100 < winProbability`, sinon perdu.
3. **Tirage pondéré** parmi les lots en stock et de poids positif. Un lot de poids 3 sort 3 fois plus souvent qu'un lot de poids 1.
4. **Code de coupon** `DEMO-XXXX-XXXX` : préfixe **obligatoire** pour qu'un code de démo ne soit jamais pris pour un vrai bon. L'alphabet exclut 0/O et 1/I (codes lus à voix haute ou recopiés).

**Hasard injectable.** `random` vaut `Math.random` par défaut. Les tests passent `createSeededRandom(graine)`, un petit générateur reproductible (mulberry32) : même graine, mêmes tirages.

Le moteur est **pur** : il n'enregistre rien. C'est le rôle du magasin.

### 5.4 `demoEntryStore` : les participations de démo

Enregistrées dans `localStorage` (`xp:demo:entries:v1`), pour que l'anti-doublon et le stock se comportent comme sur le serveur, même après un rechargement ou dans un autre onglet.

| Fonction                            | Rôle                                                                                    |
| ----------------------------------- | --------------------------------------------------------------------------------------- |
| `countByPhone(campagne, téléphone)` | Participations de ce numéro, **normalisé** (`+213 541…` = `0541…`)                      |
| `findByRequest(clientRequestId)`    | Retrouver une participation déjà faite, pour qu'un `RETRY` ne tire pas deux fois (T2.4) |
| `findById`, `confirmCoupon`         | Confirmation « j'ai copié mon code »                                                    |
| `wonByPrize(campagne)`              | Gains de démo par lot                                                                   |
| `reset(campagne?)`                  | Bouton « Reset demo data » du Studio : une campagne, ou tout                            |

`withDemoStock(règles, magasin)` retire les gains de démo du stock : un lot gagné en démo s'épuise comme sur le serveur. **Le vrai stock n'est jamais touché.**

Robustesse : des données de démo abîmées sont ignorées ; si le stockage est **bloqué ou plein**, le magasin continue **en mémoire**, sans perdre les participations déjà faites dans la session.

## 6. Décisions et alternatives

| Décision                                 | Alternative écartée                 | Raison                                                                                                                |
| ---------------------------------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Hit It raté → perdu (fiche)              | Reproduire le serveur à l'identique | Le serveur a un défaut (§9) ; la démo suit la règle voulue                                                            |
| `active` ajouté aux règles               | S'en tenir à la spécification       | La passerelle doit refuser une campagne non active, comme le serveur                                                  |
| Lots de poids 0 exclus du tirage         | Les garder                          | Au serveur, ils ne sortent pratiquement jamais (tirage exactement sur une borne) ; comportement identique en pratique |
| `random() × 100 < probabilité` (fiche)   | `random() > p` → perdu (serveur)    | Équivalent : ne diffère que sur une valeur de probabilité nulle                                                       |
| Magasin en mémoire si le stockage échoue | Erreur                              | Données de test : la démo doit continuer, même en navigation privée                                                   |
| Générateur à graine exporté              | Graine seulement dans les tests     | Réutilisable par T2.4 et pour rejouer une démo                                                                        |

## 9. Écarts, imprévus et points d'attention

- **Défaut serveur, à corriger côté Supabase (hors périmètre, non modifiable ici).** Dans `draw_and_claim_campaign_prize`, l'échec à un jeu d'adresse ne bloque le gain que si `require_quiz` est vrai. Or `campaignService` ne met `require_quiz` à vrai **que pour le quiz**. **En production, un joueur de Hit It qui n'atteint pas le seuil peut donc gagner.** La démo applique la règle voulue (« échec → défaite ») : elle sera donc **plus stricte que la production** pour Hit It tant que le serveur n'est pas corrigé. Correction possible : dans `resolve_game_outcome`, ne pas appeler le tirage quand `v_passed` est faux, pour tous les jeux d'adresse. **À toi de décider** quand la faire.
- **Mode « auto-pace » non simulé.** Quand une campagne a `auto_pace_prizes`, le serveur ignore la probabilité et répartit les lots par quota quotidien. La démo utilise toujours la probabilité. Pour ces campagnes, les chances de la démo diffèrent donc de la production.
- **Numéros de téléphone en clair dans `localStorage`** (clé anti-doublon, comme le demande la fiche). Ce sont des données de test saisies dans le Studio ; mais si la démo servait sur un appareil partagé (salon, stand), des numéros réels y resteraient. Protection possible : ne garder qu'une empreinte du numéro. **À toi de dire** si tu la veux.
- **Campagne de démonstration (sans vraie campagne).** Ses 3 questions n'ont pas de bonnes réponses dans les presets (volontairement : les presets sont visibles du runtime). T2.6 devra fournir des règles de démo pour elle, bonnes réponses comprises.
- **Messages d'erreur, contrôles d'entrée, idempotence** : T2.4.
