## 5. Le code expliqué

### 5.1 `store.ts` — un store par Studio

`createStudioStore(options)` fabrique un store neuf. Il n'y a **pas** de store global : le brouillon en exportait un (`useStudioStore`), créé à l'import du module, donc partagé par tout ce qui l'importe et construit avant même que la campagne soit connue. L'ossature (T6.2) crée le sien au montage et le transmet par contexte ; les tests créent le leur, sans historique commun.

**L'état :**

| Champ             | Contenu                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| `config`          | l'`ExperienceConfig` éditée                                                                      |
| `campaign`        | le `CampaignSnapshot` (lots, questions, règles) : lu, jamais édité ici                           |
| `campaignId`      | la campagne liée, ou `null` en mode autonome                                                     |
| `storedUpdatedAt` | le `updatedAt` de la version **en stockage** : ce que la prochaine sauvegarde s'attend à écraser |
| `ui`              | panneau, écran, langue, mode (`demo`/`scripted`/`static`), scénario, `viewport`, `focusPath`     |
| `saveStatus`      | `idle` · `saving` · `saved` · `error`                                                            |
| `issues`          | les contrôles de conception de T1.11, toujours ceux de la `config` courante                      |
| `layoutIssues`    | ce que l'audit de l'aperçu remonte (rempli par T6.10)                                            |

`ui.viewport` vaut par défaut 390 × 844, zoom `fit`, cadre affiché (`DEFAULT_VIEWPORT`) ; T6.9 le remplira depuis les préférences mémorisées, par l'option `viewport`.

**Les éditions** passent toutes par une seule fonction, qui horodate :

```ts
const edit = (change: (config: ExperienceConfig) => ExperienceConfig) =>
  set((state) => ({
    config: { ...change(state.config), updatedAt: now() },
  }));
```

Actions : `updateTheme`, `updateBrand`, `updateScreen(key, patch)`, `updateSection`, `updateForm`, `updateGame`, `updateLegal`, et `updateConfig` pour les champs de premier niveau sans action dédiée (langues, `prizeDisplay`, `features`) dont les panneaux Content et Game ont besoin. Puis :

- `applyPreset(id)` ne remplace **que le thème** : les textes de la marque, le formulaire et les mentions restent ;
- `replaceConfig(config)` (import JSON, T6.7) et `resetToDefaults()` gardent l'**identité** de la configuration éditée (`id`, `campaignId`) : sinon l'autosave écrirait un JSON importé sous la clé d'une autre campagne ;
- chacune est **un pas** d'historique.

**Les contrôles suivent la configuration, d'où qu'elle vienne.** Le brouillon recalculait `issues` dans `edit` : une annulation, qui ne restaure que `config` (c'est tout ce que l'historique contient), laissait les contrôles de l'état annulé. Ils sont désormais recalculés par un abonnement du store à lui-même :

```ts
store.subscribe((state, previous) => {
  if (state.config !== previous.config) {
    store.setState({
      issues: validateExperience(state.config, state.campaign),
    });
  }
});
```

Ce `setState` ne crée pas d'entrée d'historique, parce que zundo compare les états partiels (`config` seule) et les trouve égaux.

**L'historique** (zundo) :

```ts
partialize: (state) => ({ config: state.config }),
limit: HISTORY_LIMIT, // 50
equality: (a, b) => a.config === b.config,
```

Changer d'écran, de langue, d'appareil, de panneau, le statut de sauvegarde : rien de tout cela n'entre dans l'historique. Une annulation ramène la configuration et **laisse l'aperçu où l'utilisateur l'a mis**. L'historique s'utilise par `store.temporal.getState().undo()` / `redo()` ; le type `StudioStore` expose `temporal`, que T6.2 branche sur les boutons et sur Ctrl+Z.

**Les actions qui ne sont pas des éditions :**

- `hydrate(config, storedUpdatedAt)` : la configuration relue du stockage devient le **point de départ** ; l'historique est vidé (il n'y a rien à annuler au chargement) et la langue de l'aperçu passe à la langue par défaut de la configuration ;
- `setCampaign(campaign)` : après un `refetch()` de la campagne (T6.6), les contrôles sont recalculés, sans pas d'historique ;
- `setPanel(panel, focusPath?)` : ouvre un panneau et, s'il est donné, désigne le champ à montrer (clic dans l'aperçu `xp:edit-target`, T6.2 ; lien du panneau de validation, T6.8) ;
- `setScreen`, `setLocale`, `setMode(mode, scenario?)`, `setViewport(patch)`, `setSaveStatus`, `setStoredUpdatedAt`, `setLayoutIssues`.

### 5.2 `useAutosave.ts` — sauvegarder sans bouton

```ts
const { status, lastSavedAt, error, retry } = useAutosave({
  store,
  repository,
});
```

- **Une écriture par pause dans la frappe** : chaque changement de `config` relance un minuteur de 800 ms (`AUTOSAVE_DEBOUNCE_MS`). Quatre frappes rapprochées donnent une seule écriture, avec la dernière valeur.
- **Rien pour l'aperçu** : l'abonnement ne réagit qu'à un changement de `config`.
- **Une annulation est sauvegardée** comme n'importe quelle modification (c'est un changement de `config`).
- **Pas de réécriture au chargement** : un `hydrate` change `config` **et** `storedUpdatedAt` en même temps ; ce cas est ignoré.
- **Détection de conflit** : chaque sauvegarde envoie `expectedUpdatedAt: storedUpdatedAt`. Le brouillon gardait cette valeur dans le hook, vide jusqu'à la première écriture : un Studio ouvert dans deux onglets pouvait écraser l'autre à sa première sauvegarde. Elle vit maintenant dans le store, remplie par le chargement puis par chaque sauvegarde réussie.
- **Ce qui est « enregistré »** : seule la configuration réellement écrite. Une modification faite pendant l'écriture reste en attente et son propre minuteur la portera.
- **Erreurs** : un échec renvoyé par le dépôt (`STORAGE_FULL`, `CONFLICT`, `STORAGE_UNAVAILABLE`) ou une exception passent le statut à `error`, avec le message du dépôt (en anglais, prêt à afficher). La modification reste en attente ; `retry()` la réécrit immédiatement.
- **Garde de sortie** : tant qu'une modification n'est pas écrite (en attente ou en erreur), fermer l'onglet déclenche l'avertissement du navigateur (`beforeunload`). Désactivable (`guardUnload: false`) pour les tests et l'aperçu.

Le statut vit dans le store (`saveStatus`) et le hook le relit : la barre du haut (T6.2) peut l'afficher sans recevoir le hook.

### 5.3 `loadIntoStudio.ts` — le rechargement

```ts
const loaded = await loadIntoStudio(store, repository);
```

Lit la configuration de la campagne du store (`repository.load({ campaignId, fallbackGameType })`). Elle arrive migrée et réparée (T1.6, T1.9) ; elle est passée à `hydrate`. Sans configuration stockée, le store garde ses valeurs par défaut et la fonction renvoie `null`. Le `ParseResult` est renvoyé pour que le Studio puisse signaler une configuration réparée.

## 6. Décisions et alternatives

| Décision                                                          | Alternative écartée                        | Raison                                                                                                   |
| ----------------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| Une fabrique `createStudioStore`, pas de store global             | Le singleton `useStudioStore` du brouillon | Un store créé à l'import ignore la campagne et partage son historique entre toutes les instances         |
| Contrôles recalculés par abonnement au changement de `config`     | Les recalculer dans `edit`                 | L'annulation ne passe pas par `edit` : les contrôles restaient ceux de l'état annulé                     |
| `storedUpdatedAt` dans le store                                   | Le garder dans une `ref` du hook           | Le chargement le connaît avant le hook ; sinon la première sauvegarde ne détectait aucun conflit         |
| `hydrate` vide l'historique                                       | Le chargement comme un `replaceConfig`     | Annuler juste après l'ouverture ramènerait aux valeurs par défaut, puis les sauvegarderait               |
| `replaceConfig` et `resetToDefaults` gardent `id` et `campaignId` | Remplacer tel quel                         | Un import venu d'une autre campagne serait écrit sous la clé de cette autre campagne                     |
| Ajout de `updateConfig`                                           | Une action par champ de premier niveau     | Langues, `prizeDisplay` et `features` n'ont qu'un ou deux écrans d'édition ; une action générique suffit |
| Un conflit reste en `error` jusqu'au rechargement                 | Recharger ou fusionner automatiquement     | Le message du dépôt dit quoi faire ; une fusion silencieuse perdrait le travail de l'un des deux onglets |
