## 1. Objectif

Donner au runtime **un document à lui**, de la taille exacte de l'appareil simulé : la route `/xp-frame`. Le Studio la chargera dans une iframe (T6.2), et les deux fenêtres dialogueront par un **pont de messages** typé et filtré.

C'est ce qui rend l'aperçu fidèle : dans l'iframe, `window.innerWidth` vaut la largeur de l'appareil, quel que soit le zoom affiché autour. Les requêtes média, `dvh`, `position: fixed`, le défilement et le focus se comportent donc comme sur le vrai appareil, exactement comme le mode appareil des DevTools (principe 10 du plan).

La tâche ne dessine encore aucun écran joueur. Elle livre l'hôte, le pont et deux **pages de contrôle** (fixtures) qui prouvent que la mise en page de T3.2 bascule aux bons seuils dans un vrai navigateur.

## 5. Le code expliqué

### 5.1 `previewBridge.ts` : le pont de messages

**Rôle :** faire dialoguer le Studio et l'iframe, sans jamais traiter un message qui ne vient pas de l'autre moitié de notre propre application.

**Les messages** (repris tels quels de la fiche) :

| Sens           | Message          | Contenu                                                                                           |
| -------------- | ---------------- | ------------------------------------------------------------------------------------------------- |
| Studio → cadre | `xp:config`      | Configuration **complète** + `CampaignSnapshot` (jamais un différentiel : l'envoi est idempotent) |
| Studio → cadre | `xp:ui`          | Écran, langue, mode (`demo`, `scripted`, `static`), scénario, zones de sécurité, `restartKey`     |
| Cadre → Studio | `xp:ready`       | « J'écoute » : le Studio n'envoie rien avant                                                      |
| Cadre → Studio | `xp:flow-event`  | L'écran courant du parcours (utilisé à partir de T4.1)                                            |
| Cadre → Studio | `xp:edit-target` | Le chemin `data-xp-edit` de l'élément cliqué (le Studio ouvrira le champ correspondant)           |

`xp:layout-report` n'existe pas encore : T3.8 l'ajoutera, comme le prévoit la fiche.

**Le filtre, en trois contrôles**, commun aux deux côtés :

```ts
const onMessage = (event: MessageEvent) => {
  if (event.origin !== win.location.origin) return; // 1. notre origine seulement
  const source = expectedSource();
  if (!source || event.source !== source) return; // 2. la fenêtre attendue seulement
  if (!hasType(event.data, types)) return; // 3. un message de ce sens seulement
  listener(event.data as In);
};
```

1. **Origine** : un site tiers qui embarquerait notre cadre, ou qu'on embarquerait, ne peut rien injecter.
2. **Fenêtre source** : même sur notre origine, seul le parent (côté cadre) ou l'iframe de l'aperçu (côté Studio) est écouté. Une autre iframe ou un autre onglet de l'application est ignoré. La source attendue est relue **à chaque message** (`expectedSource()`), car `iframe.contentWindow` change quand l'iframe se recharge.
3. **Type et sens** : un message du mauvais sens (par exemple `xp:ready` reçu par le cadre) ou d'un type inconnu est ignoré. Tout ce qui est rejeté l'est **en silence**, sans erreur ni journal.

**À l'envoi**, la cible est toujours notre origine (`postMessage(message, win.location.origin)`), jamais `"*"` : si la fenêtre d'en face a changé de site, le navigateur ne livre rien.

**Cas limites gérés :**

- cadre ouvert dans son propre onglet (`source=local`) : `win.parent === win`, `post` ne fait rien ;
- iframe pas encore chargée (`contentWindow === null`) : rien n'est envoyé, rien n'est reçu, aucune erreur.

**Exporté :** `ToFrameMessage`, `FromFrameMessage`, l'interface `Bridge<Out, In>` (`post` + `subscribe`, qui renvoie la fonction de désabonnement), `createFrameBridge(win)` et `createStudioBridge(iframe, win = window)`. Le paramètre `win` permet de tester le pont avec de fausses fenêtres.

### 5.2 `fixtures.ts` : les pages de contrôle

**Rôle :** donner des configurations fixes, adressables par l'URL (`/xp-frame?fixture=<nom>&locale=ar`), pour le script de balayage de T3.8 et pour les contrôles à la main.

| Fixture         | Ce qu'elle montre                                                                |
| --------------- | -------------------------------------------------------------------------------- |
| `layout-debug`  | Le mode de mise en page courant, la taille du viewport, les tokens du thème      |
| `theme-presets` | Les 5 presets de style, chacun dessiné avec ses propres variables (critère T3.1) |

- Chaque fixture est **fabriquée à la demande** (`createDefaultExperience` + campagne de démonstration de la roue, preset `midnight-gold`), jamais partagée entre deux rendus.
- `getFixture` utilise `Object.hasOwn` : `?fixture=constructor` ou `?fixture=toString` renvoient `null` au lieu d'une propriété héritée d'`Object`.
- `readFixtureLocale` n'accepte que `ar` et `en` ; toute autre valeur donne le français.
- Chaque tâche suivante ajoutera ses fixtures à ce registre.

### 5.3 `FrameHost.tsx` : la page `/xp-frame`

**Rôle :** choisir la source de configuration selon l'URL, préparer le document, et rendre le contenu dans le thème.

| URL                          | Composant      | Usage                                                                |
| ---------------------------- | -------------- | -------------------------------------------------------------------- |
| `?fixture=<nom>`             | `FixtureFrame` | Pages de contrôle ; un nom inconnu affiche la liste des fixtures     |
| `?source=local&campaignId=…` | `LocalFrame`   | Onglet séparé (« Open in new window », T6.9), suivi en direct        |
| par défaut (`source=bridge`) | `BridgeFrame`  | Aperçu du Studio : attend la configuration envoyée par `postMessage` |

**Préparation du document (au montage de `FrameHost`) :**

- `ensureViewportFitCover(document)` (T3.2) : sans `viewport-fit=cover`, `env(safe-area-inset-*)` vaut 0 même sur un vrai iPhone ;
- `<meta name="robots" content="noindex">`, retirée au démontage ;
- titre du document « Player Experience preview ».

**`Stage`** rend le contenu dans le thème :

- un conteneur qui porte les zones de sécurité reçues (`safeAreaStyle`), **au-dessus** de la racine du runtime, pour surcharger les valeurs par défaut de `:root` (décision de T3.2) ;
- `ThemeScope` avec la classe `.xp-runtime` : variables, fond, `dir`, `lang`, `min-height: 100dvh` ;
- l'image de fond résolue par `services.assets.resolveUrl`, et la feuille de Plus Jakarta Sans chargée à la demande (`ensureFontStylesheet`, T3.1 l'avait prévu pour l'hôte du cadre) ;
- le badge « Demo » : la route tourne **toujours** sur les services de démonstration.

**`BridgeFrame`**, l'aperçu du Studio :

```tsx
const bridge = useMemo(() => injected ?? createFrameBridge(window), [injected]);
useEffect(() => {
  const unsubscribe = bridge.subscribe((message) => { … });
  // Sent after subscribing: the Studio only posts once it has heard from the frame.
  bridge.post({ type: "xp:ready" });
  return unsubscribe;
}, [bridge]);
```

- Le pont est créé **une seule fois** : un nouveau pont à chaque rendu se réabonnerait et redirait « prêt ».
- `xp:ready` part **après** l'abonnement : aucun message du Studio ne peut arriver avant que le cadre écoute.
- Tant qu'aucune configuration n'est arrivée : « Waiting for the Studio… ».
- `xp:ui` : pour l'instant, seules **la langue et les zones de sécurité** sont appliquées. L'écran, le mode, le scénario et `restartKey` n'ont de sens qu'avec le parcours (T4.1).
- **Clic sur un élément éditable** : un écouteur en phase de capture remonte au plus proche `[data-xp-edit]` et envoie `xp:edit-target` avec son chemin (par exemple `screens.welcome.title`). Un clic ailleurs n'envoie rien.

**`LocalFrame`**, l'onglet séparé :

- lit la configuration par `repository.load({ campaignId })` (T2.2, qui la valide par le schéma) ; sans configuration enregistrée, affiche la configuration par défaut de la roue ;
- **suit les enregistrements en direct** : l'événement `storage` (émis dans les **autres** onglets quand le Studio enregistre) relance la lecture si la clé commence par `xp:experience:`, ou si `key === null` (stockage vidé) ;
- ignore une lecture qui se termine après la fermeture (drapeau `active`), pour ne jamais mettre à jour un composant démonté.

**Les services** : un seul jeu de services locaux pour tout le cadre, créé au premier besoin (`frameServices()`). Le parcours (T4.1) les utilisera ; en T3.3, ils servent au dépôt et à la résolution des images.

### 5.4 `DebugViews.tsx` : les deux pages de contrôle

Ce sont elles que le script de balayage (T3.8) et un relecteur regardent. Elles utilisent donc **les mêmes tokens que les vrais écrans**, sans aucune couleur écrite.

- **`LayoutDebugView`** :
  - le mode en gros (`stack · regular · compact`), calculé par `useLayoutMode` (T3.2) ;
  - la taille du viewport, suivie par `useSyncExternalStore` sur l'événement `resize` ;
  - deux volets qui reproduisent la disposition du futur cadre : empilés en `stack`, côte à côte en `split` (`split:flex-row`, la variante CSS de T3.2). **Le JS affiche le mode, le CSS dispose les volets** : si les deux divergeaient, cela se verrait immédiatement ;
  - les 6 couleurs du thème (`--xp-primary` … `--xp-text-muted`).
- **`ThemePresetsView`** : une carte par preset, chacune dans son propre `ThemeScope` (titre, texte secondaire, bouton principal, pastilles). C'est la page de démonstration des 5 presets que demandait T3.1.

### 5.5 `theme/recipes.ts` : les recettes de style partagées (hors fiche)

| Export               | Rendu                                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------------- |
| `tint(var, %)`       | `color-mix(in srgb, var(--xp-…) X%, transparent)` : la transparence d'une variable du thème               |
| `primaryButtonStyle` | Dégradé de la marque (`--xp-primary-light` → `--xp-primary-deep`), texte `--xp-on-primary`, ombre teintée |
| `glassSurfaceStyle`  | Surface vitrée (flou + saturation), fond opaque à 72 % si le flou n'est pas disponible (D5)               |
| `cardStyle`          | Carte légèrement détachée du fond, bordure discrète, arrondi `--xp-radius-lg`                             |

Le type de `tint` (`` `--xp-${string}` ``) refuse à la compilation toute variable qui n'est pas du thème. Voir le §9 pour les raisons et les points ouverts.

### 5.6 La route (`src/AppRouter.tsx`)

```tsx
const XpFrame = lazy(() =>
  import("./features/player-experience").then((module) => ({
    default: module.FrameHost,
  })),
);
…
<Route path="/xp-frame" element={<Suspense fallback={null}><XpFrame /></Suspense>} />
```

- **Avant `/*` et hors `ProtectedRoute`**, comme `/ui-maker` (demandé par la fiche) : l'aperçu n'exige pas de session, et le script de balayage peut l'ouvrir sans se connecter.
- **Import dynamique de `index.ts`**, et non de `runtime/host/FrameHost` : la règle ESLint des frontières (T0.3) interdit à l'application d'importer un fichier interne du module.
- **Chargement différé vérifié dans le build** : le cadre (et `zod`) est dans son propre fichier `index-lc0y3o-f.js` (139,7 kB, 45 kB compressé) ; le bundle du tableau de bord ne contient ni le cadre ni `zod`, seulement le lien vers ce fichier.

### 5.7 La garde `ltr:` / `rtl:` (hors fiche)

Avec Tailwind v4, `rtl:` correspond à « un ancêtre quelconque porte `dir="rtl"` », et `ltr:` à « un ancêtre quelconque porte `dir="ltr"` ». Dès que deux portées de thème s'imbriquent (la page de contrôle des presets en contient 6), un élément en arabe dans une page en français reçoit **les deux** variantes, et la dernière déclarée l'emporte. Le badge « Demo », d'abord placé avec `ltr:right-2 rtl:left-2`, a révélé le problème.

La règle : **propriétés logiques** (`start`/`end`, `ps`/`pe`, `ms`/`me`, `text-start`), qui suivent le `dir` le plus proche. `noFixedSizes.test.ts` refuse désormais `ltr:` et `rtl:` dans `runtime/`, et le README du module le dit.

## 6. Décisions et alternatives

| Décision                                                                 | Alternative écartée                                       | Raison                                                                                                                                                                                                    |
| ------------------------------------------------------------------------ | --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Filtre origine **et** fenêtre source **et** type                         | Origine seule (comme beaucoup d'exemples)                 | Plusieurs iframes de même origine coexisteront (aperçu, « Check all sizes » en T6.10) : l'origine ne suffit pas à savoir qui parle                                                                        |
| Source attendue relue à chaque message                                   | Fenêtre mémorisée à la création du pont                   | `iframe.contentWindow` change à chaque rechargement de l'iframe                                                                                                                                           |
| Messages rejetés en silence                                              | Erreur ou journal                                         | Extensions et outils de développement postent aussi des messages : rien d'anormal à journaliser                                                                                                           |
| Configuration du pont **non revalidée** par `zod` dans le cadre          | `parseExperienceConfig` à chaque `xp:config`              | Elle vient du store du Studio (même origine, fenêtre vérifiée), qui ne contient que des configurations déjà validées ; la revalider toutes les 100 ms coûterait sans rien protéger. **À valider par toi** |
| `FrameHost` compose lui-même les services locaux (`createLocalServices`) | Services injectés par `AppRouter`                         | La route est une racine de composition, comme le sera `/play/:slug` ; la fiche T4.1 le prévoit. `services/local` n'est jamais importé directement (règle ESLint respectée). **À valider par toi** (A4)    |
| Route dans `AuthProvider`, comme `/ui-maker`                             | Route hors `AuthProvider`                                 | C'est ce que dit la fiche ; conséquence notée au §9.3                                                                                                                                                     |
| Badge « Demo » côté **fin** de lecture (`end-…`)                         | « En haut à droite » dans toutes les langues (fiche T4.1) | En arabe, la lecture commence à droite : le badge passe à gauche, comme le reste de l'en-tête. Utilise les propriétés logiques (§5.7)                                                                     |
| `xp:ready` envoyé après l'abonnement                                     | Envoyé au montage, avant                                  | Aucune fenêtre où le Studio parlerait à un cadre sourd                                                                                                                                                    |
| Deux pages de contrôle dans `DebugViews.tsx`                             | Tout dans `FrameHost.tsx`                                 | Garder chaque fichier sous 250 lignes (C2)                                                                                                                                                                |
| `Object.hasOwn` dans `getFixture`                                        | `FIXTURES[name]`                                          | `?fixture=constructor` renverrait une fonction d'`Object`                                                                                                                                                 |
| `runtime/host/` dans la couverture                                       | Couverture limitée aux couches déjà mesurées              | Le pont est une frontière de sécurité : il mérite d'être mesuré                                                                                                                                           |

### 9.3 Point d'attention : `AuthProvider` autour de `/xp-frame`

Comme `/ui-maker`, la route est dans `AuthProvider`. Le cadre lui-même ne lit aucune donnée serveur, mais **l'`AuthProvider` qui l'entoure, si**. Quand l'utilisateur est connecté (le cas du Studio), chaque chargement de l'iframe déclenche `getSession`, puis une requête `profiles` et une requête `organizations`. Avec un seul aperçu, c'est négligeable. En T6.10, « Check all sizes » rechargera l'iframe pour chaque appareil du catalogue, en portrait et en paysage, soit une cinquantaine de fois ; le script de balayage de T3.8, lui, n'est pas connecté : il ne déclenche aucune requête de profil.

**Proposition (non appliquée)** : sortir `/xp-frame` de l'`AuthProvider` dans `AppRouter.tsx`. C'est une restructuration de quelques lignes, mais hors de la fiche (« une route »). À décider, au plus tard avant T6.10.
