## 1. Objectif

Donner au runtime une mise en page qui fonctionne à **toutes** les tailles de l'enveloppe (de 280 à 2560 px de large, de 320 à 1600 px de haut), en portrait comme en paysage. Et le faire à partir d'**une seule source** de points de rupture, pour que le TypeScript et le CSS basculent toujours au même pixel.

Cette tâche ne dessine encore aucun écran. Elle pose les **règles et les outils** que les tâches T3.3 à T3.8 et les phases 4 et 5 utiliseront.

## 5. Le code expliqué

### 5.1 Deux axes, un palier de largeur

Le mode se calcule sur le **viewport du document**. Dans l'aperçu du Studio, le runtime est dans une iframe à la taille de l'appareil simulé (T3.3) : ce viewport **est** celui de l'appareil.

| Axe         | Valeur    | Condition                                       | Effet (appliqué à partir de T3.4)                                 |
| ----------- | --------- | ----------------------------------------------- | ----------------------------------------------------------------- |
| Disposition | `stack`   | par défaut                                      | Une colonne ; pleine largeur sous 600 px, colonne centrée au-delà |
|             | `split`   | largeur ≥ 560 px **et** rapport ≥ 6/5 (paysage) | Deux volets : texte et bouton à gauche, jeu à droite              |
| Densité     | `tight`   | hauteur < 600 px                                | Espacements réduits, visuel du slot 2 masqué                      |
|             | `regular` | 600 à 899 px                                    | Valeurs du design de référence                                    |
|             | `roomy`   | hauteur ≥ 900 px                                | Espacements et jeu agrandis                                       |
| Largeur     | `compact` | < 360 px                                        | Marges réduites, étiquettes à la ligne                            |
|             | `wide`    | ≥ 600 px                                        | Colonne plafonnée                                                 |

Exemples vérifiés par les tests (plan §8.3) :

| Taille                              | Mode                        |
| ----------------------------------- | --------------------------- |
| 360×800 (Android d'entrée de gamme) | `stack · regular`           |
| 844×390 (téléphone en paysage)      | `split · tight`             |
| 834×1194 (iPad Pro 11")             | `stack · roomy`             |
| 1366×657 (ordinateur, zone visible) | `split · regular`           |
| 1920×969 (écran FHD, zone visible)  | `split · roomy`             |
| 280×653 (téléphone pliable fermé)   | `stack · regular · compact` |

### 5.2 Une seule source, deux usages

- **`breakpoints.ts`** contient les nombres (`BREAKPOINTS`) et en construit les requêtes média (`MEDIA_QUERIES`).
- **`layout.css`** déclare les mêmes requêtes comme **variantes Tailwind v4** : `split:flex-row`, `tight:gap-2`, `compact:px-3`, `roomy:…`, `wide:…`.
- **Un test lit `layout.css`** et échoue si une requête diffère de `breakpoints.ts`.
- **`useLayoutMode()`** interroge le navigateur avec **exactement ces requêtes** (`matchMedia`). Le JavaScript et le CSS basculent donc au même pixel, même sur des tailles fractionnaires. Sans `matchMedia` (environnement de test), il calcule à partir des dimensions de la fenêtre.

**Pourquoi `src/index.css` est modifié.** Avec Tailwind v4, une variante `@custom-variant` doit être déclarée dans la feuille qui importe Tailwind, sinon les classes `split:…` ne sont pas générées. Une ligne d'import suffit ; le build a été contrôlé : les règles de `layout.css` sont bien dans le CSS produit.

### 5.3 La racine, les zones de sécurité

- **`.xp-runtime`** : `min-height: 100dvh` (la hauteur qui suit la barre d'adresse mobile) et aucun défilement horizontal. C'est le **seul** endroit du runtime qui utilise la hauteur de l'écran. Ce n'est pas la classe de `ThemeScope` (`.xp-root`), qui peut servir ailleurs (vignettes de presets dans le Studio).
- **`--xp-safe-top|right|bottom|left`** valent `env(safe-area-inset-*)` (encoche, barre d'accueil). L'aperçu les **surcharge** selon l'appareil simulé (`safeAreaStyle`), car `env()` vaut toujours 0 sur un ordinateur.
- **`ensureViewportFitCover(document)`** ajoute `viewport-fit=cover` à la balise viewport. Elle est absente de `index.html` : **sans elle, `env()` vaut 0 même sur un vrai iPhone**. L'hôte du cadre (T3.3) l'appelle au montage, dans son propre document.

### 5.4 `useElementSize`

Renvoie `[ref, { width, height }]`, mis à jour par `ResizeObserver`. Les jeux et les canvas se dimensionneront sur **leur conteneur**, jamais sur l'écran. Une taille identique renvoie le **même objet** : rien à redessiner.

### 5.5 La garde « aucune taille fixe »

`noFixedSizes.test.ts` parcourt tout `runtime/` et **échoue** s'il trouve :

| Interdit                      | Pourquoi                                               | À la place                                                |
| ----------------------------- | ------------------------------------------------------ | --------------------------------------------------------- |
| `sm:`, `md:`, `lg:`, `xl:`    | Suivraient la fenêtre du Studio, pas l'appareil simulé | `split:`, `tight:`, `roomy:`, `compact:`, `wide:`         |
| `w-[260px]`, `min-h-[620px]`… | Cassent sur les petits et les grands écrans            | Unités de conteneur (`cqw`, `cqh`), pourcentages, contenu |
| `100vh`, `h-screen`           | Faux sur mobile (barre d'adresse)                      | La racine seule, en `100dvh`                              |

Exceptions : les bordures, et les minima des zones tactiles (`min-h-[44px]` à `min-h-[56px]`). Le test prouve aussi qu'il attrape les tailles du prototype (`w-[260px]`, `sm:w-[280px]`, `min-h-[620px]`, `max-w-[320px]`, `h-screen`, `100vh`).

## 6. Décisions et alternatives

| Décision                                                  | Alternative écartée                                | Raison                                                                                           |
| --------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `useLayoutMode` par `matchMedia` avec les requêtes du CSS | Calcul sur `innerWidth` à chaque redimensionnement | Même bascule au pixel près que le CSS                                                            |
| `.xp-runtime` distinct de `.xp-root`                      | `100dvh` sur `ThemeScope`                          | `ThemeScope` peut servir hors du runtime (vignettes)                                             |
| Zones de sécurité par défaut sur `:root`                  | Sur `.xp-root`                                     | Une valeur posée sur la racine du runtime empêcherait l'aperçu de la surcharger depuis un parent |
| `h-screen` interdit aussi                                 | Seulement `100vh` (fiche)                          | `h-screen` vaut `100vh` dans Tailwind                                                            |
| `runtime/layout/` dans la couverture                      | Couverture limitée à `domain`, `services`, `theme` | Logique pure, qui mérite d'être mesurée                                                          |

## 9. Écarts, imprévus et points d'attention

- **Fichier hors du module modifié : `src/index.css`**, une ligne d'import, imposée par Tailwind v4 (§5.2).
- **ESLint** : `ResizeObserverCallback` est un type sans valeur globale à l'exécution (`no-undef`), remplacé par `ConstructorParameters<typeof ResizeObserver>[0]`.
- **Test de taille réécrit** : ma première version comptait les rendus React ; or React peut refaire un rendu avant d'abandonner une mise à jour identique. Le test vérifie maintenant que l'objet taille reste le même.
- **Les variantes n'ont pas encore d'effet visible** : aucun composant ne les utilise encore. Leur bascule réelle se vérifie en T3.3 (fixture `layout-debug`, captures d'écran).

## 10. Qualité visuelle

Pas d'écran ici, mais c'est la condition de la règle D17 (« beau sur tous les écrans ») : en paysage et sur ordinateur, la disposition en deux volets sera une **vraie** mise en page, pas un téléphone perdu au milieu. Elle est calculée sur l'appareil simulé, et non sur la fenêtre du Studio.
