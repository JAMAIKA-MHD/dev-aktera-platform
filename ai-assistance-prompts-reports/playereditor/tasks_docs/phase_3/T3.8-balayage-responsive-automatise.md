## 1. Objectif

Vérifier **toutes** les tailles de l'enveloppe (RWD1 : 280 → 2560 px de large, 320 → 1600 px de haut), pas quatre échantillons, et outiller les phases suivantes. La tâche livre une **définition unique** d'une mise en page cassée (`layoutAudit`), utilisée à deux endroits : par le cadre, qui la partage en direct avec le Studio (message `xp:layout-report`, T6.9 et T6.10), et par un script qui balaie l'enveloppe dans un Chrome headless (`npm run xp:responsive`). Ce que le Studio signale et ce que le script signale ne peuvent donc jamais diverger.

## 5. Le code expliqué

### 5.1 L'audit (`runtime/layout/layoutAudit.ts`)

**Rôle :** dire, pour un document réellement mis en page, ce qui est cassé et où, sous une forme que le Studio sait exploiter.

```ts
export interface LayoutIssue {
  kind: LayoutIssueKind;
  selector: string; // where, for a developer
  editPath: string | null; // nearest data-xp-edit: the Studio field to open
  detail: string;
}
export function layoutAudit(root: HTMLElement): LayoutIssue[];
```

- **`selector`** est lisible par un humain : `[data-xp-slot="title"]`, `[data-xp-slot="cta"] button`, `span.xp-badge`… La fonction `describe` prend le nom du slot le plus proche, puis la balise et la première classe `xp-*`. Ce n'est pas un sélecteur CSS unique, c'est une adresse compréhensible dans un rapport.
- **`editPath`** reprend l'attribut `data-xp-edit` le plus proche (`screens.welcome.title`, `brand`, `legal`…) : en T6.10, un clic sur l'avertissement ouvrira ce champ.
- **`TOLERANCE = 0.5`** : un arrondi sous-pixel n'est pas un défaut. **`TOUCH_MIN = 44`** : la cible tactile minimale (RWD5).

**Les 7 contrôles, dans l'ordre du code :**

| #   | Type                               | Ce qui est mesuré                                                                                                                    |
| --- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | `horizontal-overflow`              | La page défile de côté : `documentElement.scrollWidth > innerWidth`                                                                  |
| 2   | `horizontal-overflow`              | Un élément sort du viewport à gauche ou à droite, **en tenant compte de ce que ses ancêtres coupent**                                |
| 3   | `text-clipped`                     | Un élément qui porte son propre texte a `scrollWidth > clientWidth` ou `scrollHeight > clientHeight`, hors des zones `data-xp-clamp` |
| 4   | `slot-overlap`                     | Deux enfants directs de `.xp-frame` marqués `data-xp-slot` se recouvrent                                                             |
| 5   | `cta-too-small`, `cta-unreachable` | Le bouton principal du slot `cta` fait moins de 44 × 44 px ; ou il n'est ni visible ni collant                                       |
| 6   | `game-below-floor`                 | Le slot `interaction` est moins haut que son plancher `--xp-game-min`                                                                |
| 7   | `wheel-not-square`                 | Un élément `data-xp-wheel` n'est pas carré, à ± 1 px                                                                                 |

**Le point délicat : ce que le joueur voit vraiment (contrôle 2).** Beaucoup d'éléments débordent volontairement de leur parent : le bandeau légal qui défile, le reflet qui balaie le bouton, le halo derrière le jeu. Ces parents coupent leur contenu (`overflow: hidden`), donc le joueur ne voit rien dépasser. L'audit calcule, pour chaque élément, la **zone de coupe** héritée de ses ancêtres (`clipOf`, mémorisée dans une `Map` pour ne mesurer chaque ancêtre qu'une fois), et ne compare au viewport que la partie visible de la boîte :

```ts
const clip = clipOf(element.parentElement);
const left = clip ? Math.max(box.left, clip.left) : box.left;
const right = clip ? Math.min(box.right, clip.right) : box.right;
```

**La racine du runtime ne compte pas comme coupe.** `.xp-runtime` a `overflow-x: clip` (T3.2) : elle masque justement ce que l'audit cherche. Si on la prenait en compte, un élément trop large serait « invisible » et jamais signalé. `clipOf` s'arrête donc à `root`.

**Texte coupé (contrôle 3).** Seuls les éléments qui portent **leur propre** nœud texte sont mesurés (sinon chaque conteneur serait signalé à la place de son enfant). Les boîtes en ligne (`clientWidth` et `clientHeight` nuls) n'ont pas de taille propre : elles sont ignorées. Les coupes voulues (`line-clamp-2` du sous-titre, ellipse du nom de marque) sont marquées `data-xp-clamp` depuis T3.4 et ne comptent pas.

**Chevauchement (contrôle 4) et CTA collant.** Quand le contenu est plus haut que l'écran, le CTA reste collé en bas (`position: sticky`, T3.5) et **flotte volontairement** au-dessus du contenu, sur son dock vitré. Pendant ce temps, `useIsStuck` pose `data-xp-stuck` sur le slot : l'audit l'exclut des chevauchements. Pour le contrôle 5, un CTA hors de l'écran n'est un défaut que s'il n'est pas collant (`getComputedStyle(ctaSlot).position === "sticky"`).

**Plancher du jeu (contrôle 6).** `--xp-game-min` vaut `12.5rem` ou `15rem` selon la densité (T3.5). `toPixels` convertit une valeur en `rem` avec la taille de police de la racine ; une valeur inconnue donne `NaN`, et le contrôle ne s'applique pas.

**`layoutReport(root)`** ajoute la taille du viewport et le mode de mise en page (`computeLayoutMode`, T3.2) : c'est exactement le contenu du message `xp:layout-report`.

**Cas limites gérés :** document sans fenêtre (rien à auditer), cadre sans CTA ni zone de jeu (l'écran d'attente n'a pas de CTA), éléments non rendus (boîte 0 × 0), éléments SVG (contrôlés pour le débordement, pas pour le texte).

### 5.2 Le partage de l'audit (`runtime/host/layoutReport.ts`)

**`exposeLayoutAudit(win)`** pose `window.__xpLayoutAudit`, qui lance l'audit sur la racine du runtime (`.xp-runtime`, ou `body` avant qu'elle existe), et renvoie la fonction qui l'enlève. `FrameHost` l'appelle dans son effet de montage, à côté de la balise `robots noindex` : l'audit existe tant que le cadre existe.

**`useLayoutReport(onReport)`** envoie un rapport **une fois les choses stabilisées** : chaque déclencheur relance un minuteur de 150 ms (`REPORT_DELAY_MS`) ; une rafale de rendus ou un redimensionnement à la souris donne un seul rapport. Les déclencheurs :

| Déclencheur                             | Pourquoi                                                                     |
| --------------------------------------- | ---------------------------------------------------------------------------- |
| Chaque rendu de l'appelant              | La configuration, la langue ou l'écran ont pu changer                        |
| `resize` de la fenêtre                  | L'iframe a changé de taille (appareil, rotation, poignées du Studio)         |
| `ResizeObserver` sur `<html>`           | Le contenu a grandi sans redimensionnement (police chargée, texte plus long) |
| `animationend` sur le document (bulles) | **Ajouté pendant le balayage** : voir ci-dessous                             |

Rien n'est envoyé tant que `onReport` vaut `null` : `BridgeFrame` passe `null` tant que le Studio n'a pas envoyé de configuration (il n'y a rien à auditer à part le message d'attente).

**Pourquoi `animationend`.** Les slots entrent en montant (`xp-rise`, 520 ms, décalés de 70 ms chacun ; le CTA part à 350 ms). Mesuré pendant cette entrée, un CTA tenu en bas est décalé par sa `transform` : `useIsStuck` ne le voit pas encore « collé », `data-xp-stuck` est absent, et l'audit croit à un chevauchement avec les sections. Sans ce déclencheur, le premier rapport (150 ms après le montage, en pleine entrée) restait le dernier : le Studio aurait gardé un faux avertissement sur tous les écrans courts. Les animations en boucle (halo, point « live ») ne se terminent jamais : elles ne déclenchent rien.

### 5.5 Le script de balayage (`scripts/xp-responsive-check.mjs`)

**Rôle :** passer une ou plusieurs pages `/xp-frame?fixture=…` sur toute l'enveloppe, dans un vrai Chrome, et dire où la mise en page casse.

```
npm run xp:responsive -- <url> [<url>…] [--quick | --full] [--out <dossier>]
```

**Sans dépendance (Node 22).** Le script lance Chrome en headless (`--remote-debugging-port=0` : Chrome choisit un port libre et l'écrit dans `DevToolsActivePort`, dans un profil temporaire), puis lui parle par le **protocole DevTools** avec le `WebSocket` natif de Node 22. Chrome est cherché dans `CHROME_PATH`, puis aux emplacements standard de Windows, macOS et Linux.

**Les entrées lues du dépôt :** `presets/devices.json` pour le catalogue, et **l'enveloppe lue dans `runtime/layout/breakpoints.ts`** (RWD3 : source unique ; si le bloc `ENVELOPE` ne peut pas être lu, le script s'arrête avec le code 2).

**Ouvrir une page (`open`)** : navigation, puis attente de l'évènement `load`, puis attente que le cadre soit monté (`window.__xpLayoutAudit` existe : la route est chargée en différé), des polices (`document.fonts.ready`), et de la **fin de l'entrée échelonnée des slots** : toutes les animations finies de `document.getAnimations()` doivent être terminées (les animations en boucle sont écartées ; garde de 5 s).

**Auditer (`audit`)** : deux images et 30 ms pour que les requêtes média, React et le CTA collant se stabilisent, retour en haut de page, puis `window.__xpLayoutAudit()`. **Un audit qui ne peut pas tourner ne passe jamais pour un succès** : si la page a été rechargée entre-temps (voir §9.2) ou n'expose plus l'audit, le script s'arrête avec une erreur.

**Les phases, pour chaque URL et chaque langue :**

| Phase     | Tailles                                                                                                                                  | Par défaut | `--quick`  |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ---------- |
| `widths`  | 280 → 2560 px de large, à 640 et 900 px de haut                                                                                          | pas 16 px  | pas 48 px  |
| `heights` | 320 → 1200 px de haut, à 360 et 1366 px de large                                                                                         | pas 20 px  | pas 60 px  |
| `catalog` | chaque appareil, en portrait et en paysage (les ordinateurs tels que listés), densité et tactile émulés, page rechargée, capture d'écran | 36 tailles | 36 tailles |
| `resize`  | de 280 à 1920 px à 700 px de haut, par pas de 8 px, **sans rechargement** ; audit tous les 64 px                                         | 26 audits  | 26 audits  |

- La largeur maximale est toujours testée même si le pas ne tombe pas dessus (`range` ajoute la borne).
- **Catalogue** : `Emulation.setDeviceMetricsOverride` (taille, densité, `mobile`, orientation) et `Emulation.setTouchEmulationEnabled`, puis rechargement pour que le viewport mobile s'applique. Hors de l'enveloppe (Galaxy Fold en paysage), seuls les débordements horizontaux comptent (`relevant`).
- **Redimensionnement continu** : la zone de jeu est repérée au début ; à la fin, si ce n'est plus le même nœud DOM, le script signale `remounted` : un redimensionnement ne doit jamais remonter le jeu (RWD4, la partie serait perdue).
- **Langues** : `fr` et `ar` par défaut ; `fr` seul avec `--quick` ; `fr`, `ar` et `en` avec `--full`. La langue passe par le paramètre `locale` de l'URL.
- **Console** : erreurs et avertissements (`Runtime.consoleAPICalled`), exceptions non rattrapées (`Runtime.exceptionThrown`) et messages du navigateur (`Log.entryAdded`), relevés passe par passe.

**Le rapport**, dans `--out` (ou un dossier temporaire) :

- `report.md` : par URL et par langue, le nombre de tailles testées, le nombre de tailles en défaut, les messages de console, puis **un défaut par ligne** (type, élément, champ du Studio, détail, tailles concernées : les 6 premières et le compte des autres), et la **liste de toutes les tailles testées**, phase par phase, dans un bloc repliable ;
- `report.json` : tous les résultats bruts ;
- les captures d'écran du catalogue (`<n>-<fixture>-<langue>-<appareil>-<orientation>.png`).

**Code de sortie :** 0 si aucune taille n'a de défaut et que la console n'a aucune erreur ; 1 sinon ; 2 si le balayage ne peut pas tourner (pas de Chrome, pas d'audit sur la page, page rechargée pendant le balayage).

## 6. Décisions et alternatives

| Décision                                                                   | Alternative écartée                                                          | Raison                                                                                                                             |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Le script appelle `window.__xpLayoutAudit()` dans la page                  | Recopier les contrôles dans le script                                        | Une seule définition de « cassé » (plan §9.3) : le Studio et le balayage ne peuvent pas diverger                                   |
| Protocole DevTools à la main, avec le `WebSocket` de Node 22               | Puppeteer ou Playwright                                                      | La fiche l'exige (C10 : pas de dépendance nouvelle) ; une centaine de lignes suffisent                                             |
| Coupe des ancêtres calculée, racine exclue                                 | Comparer chaque boîte brute au viewport                                      | Sinon le bandeau légal, le reflet du bouton et les halos seraient signalés à tort ; et la racine masque ce qu'on cherche           |
| CTA collant exclu des chevauchements via `data-xp-stuck`                   | L'exclure dès qu'il est `sticky`                                             | Un CTA `sticky` qui n'est pas tenu en bas est à sa place normale : là, un chevauchement est un vrai défaut                         |
| Attendre la fin des animations finies avant d'auditer                      | Un délai fixe (1,1 s au départ)                                              | En émulation mobile à haute densité, la page est plus lente : le délai fixe tombait pendant l'entrée (faux défauts, §9.1)          |
| Relancer le rapport en direct sur `animationend`                           | Ne rien faire, ou ignorer les éléments en cours d'animation                  | Le premier rapport tombe pendant l'entrée : il faut en envoyer un à la fin. Masquer les éléments animés cacherait de vrais défauts |
| Un rechargement imprévu, ou un audit absent, arrête le balayage (code 2)   | Compter l'audit absent comme « aucun défaut » (version initiale)             | Un balayage qui n'a rien vérifié ne doit jamais passer pour réussi (R6)                                                            |
| Enveloppe lue dans `breakpoints.ts` par une expression régulière           | La recopier dans le script (version initiale) ; `--experimental-strip-types` | RWD3 (source unique) ; le drapeau expérimental afficherait un avertissement et dépendrait de la version de Node                    |
| Liste des tailles testées dans `report.md`, repliée ; pas dans le terminal | Le seul nombre de tailles                                                    | Critère d'acceptation : « le rapport liste les tailles testées » ; le terminal reste lisible                                       |
| Ordinateurs balayés tels que listés, étiquetés « landscape »               | Les étiqueter « portrait » (version initiale)                                | Ils sont listés en paysage : l'étiquette « portrait » des captures était fausse                                                    |

## 9. Écarts, imprévus et points d'attention

### 9.1 Le balayage a trouvé un défaut, dans le rapport en direct

Au premier balayage rapide (`--quick`) de `welcome-midnight-gold`, 7 tailles du catalogue étaient en défaut : `sections and cta overlap by 324 x 32 px` sur les appareils courts (Android compact en portrait, et les téléphones en paysage). Les captures montraient le CTA bien tenu en bas, mais **sans son dock vitré** : les chips passaient sous le bouton.

Diagnostic (un script de mesure dans le scratchpad, en émulation mobile puis bureau, à 800 × 360) : `useIsStuck` fonctionne. Le dock apparaît dès la fin de l'animation d'entrée du CTA : vers 2 s après la navigation en bureau, vers 2,9 s en émulation mobile à densité 2 (le rendu à haute densité est plus lent). Le script auditait après un délai fixe (chargement + 1,1 s), donc **pendant** l'entrée, quand la `transform` décale encore le CTA.

Deux corrections :

1. **Le script** attend le montage du cadre, puis la fin de toutes les animations finies, au lieu d'un délai fixe (§5.5).
2. **Le rapport en direct** avait le même défaut, en pire : son premier rapport part 150 ms après le montage, en pleine entrée, et rien ne le relançait ensuite. Le Studio aurait gardé un faux « slot-overlap » sur tous les écrans courts. `useLayoutReport` écoute désormais `animationend` (§5.2), avec un test. Ce défaut était **latent** : en mode pont, `BridgeFrame` affiche encore la vue `layout-debug` (sans cadre ni CTA) jusqu'à T4.1. Il serait apparu dès que le parcours y serait rendu. Il n'est donc vérifiable aujourd'hui que par le test unitaire ; le mécanisme, lui, est mesuré dans Chrome (le dock n'apparaît qu'à la fin de l'entrée).

Relancé : 192 tailles, 0 défaut, 0 message de console.

### 9.2 Les rechargements du serveur de dev

Vite recharge la page (`page reload scripts/xp-responsive-check.mjs` dans son journal) **dès qu'un fichier du dépôt change**, même hors de l'application (un script, un test). Pendant un premier balayage complet, mes retouches du script ont rechargé les pages de Chrome : deux passes se sont arrêtées (`Inspected target navigated or closed`), et trois rechargements étaient tombés **pendant** des passes qui avaient « réussi ».

Ces résultats sont écartés. La faille venait du script : pendant un rechargement, `window.__xpLayoutAudit` n'existe pas, l'audit renvoyait `null`, compté comme « 0 défaut ». Désormais, un rechargement imprévu (évènement `Page.frameNavigated` hors d'une navigation du script) ou un audit absent arrête le balayage avec le code 2.

**Conséquences pratiques :**

- ne pas modifier de fichier du dépôt pendant un balayage sur le serveur de dev, et ne pas écrire le rapport dans le dépôt (`--out`) ;
- pour un long balayage, on peut le lancer sur le build de production : `npm run build`, puis `npx vite preview --port 4173`, puis `node scripts/xp-responsive-check.mjs "http://localhost:4173/xp-frame?fixture=…"`. Le serveur de prévisualisation ne surveille aucun fichier. C'est ce que j'ai fait pour le balayage complet ; la commande de la fiche, elle, a été passée sur le serveur de dev.

### 9.3 Ajouts hors fiche (à valider, R5)

- **Contrôle `remounted`** dans la phase de redimensionnement : la zone de jeu ne doit pas être remontée. La fiche demande « aucune erreur console » ; RWD4 demande que les moteurs supportent un redimensionnement en cours de partie. Remonter la zone perdrait la partie : c'est ce que le contrôle attrape.
- **Option `--full`** (fr, ar et en) : la fiche parle d'un « mode complet » qui ajoute l'anglais, sans nommer l'option.
- **Plusieurs URL** en une commande : pratique pour passer toutes les fixtures d'une tâche en une fois.
- **`Stage.tsx`** : extraction de `FrameHost.tsx` pour respecter C2 (moins de 250 lignes), sans changement de comportement.

### 9.4 Point d'attention : les zones sûres ne sont pas émulées

Le catalogue décrit les zones sûres en portrait (encoche de 47 px et barre de 34 px sur l'iPhone 12, par exemple), mais le balayage ne les applique pas : il émule la taille, la densité, le mode mobile et le tactile, comme le demande la fiche. Dans les captures, l'en-tête de l'iPhone 12 commence donc tout en haut. Les zones sûres sont déjà prises en charge par le runtime (`--xp-safe-*`, T3.2) et par le pont (`xp:ui`, `safeArea`, T3.3) : le Studio les appliquera par appareil en T6.9. Si l'on veut les balayer aussi, deux pistes : un paramètre d'URL `safeArea` pour les fixtures, ou `Emulation.setSafeAreaInsetsOverride` (expérimental, selon la version de Chrome). Non fait ici (R5).
