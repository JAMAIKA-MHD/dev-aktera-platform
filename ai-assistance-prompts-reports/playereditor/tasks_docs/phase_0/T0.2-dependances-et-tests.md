## 1. Objectif

Installer les deux outils dont toute la suite dépend :

- **`zod`**, pour valider la configuration aux frontières (chargement, import de fichier : règle A6) ;
- **`vitest`**, pour tester le domaine, les services, puis les composants.

Jusqu'ici, `npm test` se contentait d'afficher un message. Désormais, **`npm run verify` (et donc le hook `pre-push`) lance de vrais tests.**

## 2. Où elle se situe

- **Avant :** aucun outil de test ; `package.json` avait `"test": "echo \"No tests configured yet.\""`.
- **Après :** Vitest tourne dans un navigateur simulé (jsdom) et peut afficher des composants React avec Testing Library ; la couverture de code est mesurée sur `domain/` et `services/`.
- **Utilisé par :** toutes les tâches de la phase 1, dont les fiches demandent des tests (couverture ≥ 90 % sur `domain/`), puis les phases 2 à 6.

```
npm test ──► vitest run ──► vitest.config.ts ──► vite.config.ts (plugin React, alias "@")

                                   ├── environnement jsdom (document, window…)

```

### `vitest.config.ts`

```ts
import { defineConfig, mergeConfig } from "vitest/config";
import viteConfig from "./vite.config";

// Reuse the app's Vite config (React plugin, "@" alias) so tests resolve modules exactly like the app.
export default defineConfig((env) =>
  mergeConfig(typeof viteConfig === "function" ? viteConfig(env) : viteConfig, {
    test: {
      environment: "jsdom",
      globals: true,
      setupFiles: ["src/test/setup.ts"],
      include: ["src/**/*.test.{ts,tsx}"],
      coverage: {
        provider: "v8",
        include: ["src/features/player-experience/{domain,services}/**"],
      },
    },
  }),
);
```

- **`mergeConfig` avec `vite.config.ts`** : les tests utilisent le même plugin React et le même alias `@` que l'application. Sans cela, un import `@/src/...` marcherait dans l'application mais échouerait dans les tests, ou l'inverse.
- **`typeof viteConfig === "function"`** : `vite.config.ts` exporte une fonction (`defineConfig(() => ({...}))`). On l'appelle avec l'environnement fourni par Vitest ; si un jour elle devient un simple objet, le code continue de fonctionner.
- **`environment: "jsdom"`** : un navigateur simulé, indispensable pour les composants et pour `localStorage`, dont les adaptateurs se serviront (phase 2).
- **`globals: true`** : demandé par la fiche. Son effet utile est de permettre à Testing Library de **nettoyer automatiquement** l'écran après chaque test. Par convention, les tests importent quand même explicitement `describe`, `it` et `expect` depuis `vitest` (voir §6).
- **`include`** : seuls les fichiers `*.test.ts` et `*.test.tsx` sous `src/` sont des tests.
- **`coverage.include`** : la couverture ne mesure que `domain/` et `services/` du module, là où le plan exige 90 % (plan §13.1). Mesurer toute l'application noierait ce chiffre.

### `src/test/setup.ts`

```ts
// Global test setup, loaded by vitest.config.ts before every test file.
// React Testing Library unmounts rendered trees after each test on its own,
// because `globals: true` exposes `afterEach`. Register shared matchers or mocks here if needed.
export {};
```

La fiche prévoit ce fichier vide avec un commentaire, puisque `@testing-library/jest-dom` n'est pas ajouté. Le commentaire dit à quoi il sert et pourquoi il n'y a rien à nettoyer à la main. `export {}` en fait un module TypeScript, ce qu'exige l'option `isolatedModules` du projet.

### `src/test/harness.test.tsx`

```tsx
describe("test harness", () => {
  it("runs in a jsdom environment", () => {
    /* document.createElement fonctionne */
  });
  it("renders React components", () => {
    /* render + screen.getByText */
  });
  it("validates data with zod", () => {
    /* un objet valide passe, un nom vide échoue */
  });
});
```

Chaque test vérifie **un maillon de l'outillage** : l'environnement navigateur, l'affichage React (donc JSX, plugin et React 19), et `zod`. Si l'un échoue un jour, c'est l'outillage qui est cassé, pas l'application : le commentaire en tête du fichier le rappelle.

### `package.json`, les scripts

```json
"test": "vitest run",
"test:watch": "vitest",
"test:cov": "vitest run --coverage",
```

- `npm test` : une exécution complète, puis arrêt. C'est ce qu'utilise `npm run verify`, qui n'a pas changé.
- `npm run test:watch` : relance les tests à chaque modification, pour le développement.
- `npm run test:cov` : exécution avec rapport de couverture (dossier `coverage/`, déjà ignoré par Git).

### `eslint.config.js` et `tsconfig.json` : le rapport de couverture

`npm run test:cov` génère `coverage/`, un rapport HTML qui contient des fichiers JavaScript. Ce dossier était déjà dans `.gitignore`, mais :

- **ESLint** ne lit pas `.gitignore` : il analysait `coverage/block-navigation.js` et signalait un avertissement (77 au lieu de 76) ;
- **TypeScript** incluait 3 fichiers de `coverage/`, à cause de l'option `allowJs` du projet.

J'ai ajouté `"coverage/**"` aux exclusions d'ESLint et `"coverage"` à celles de TypeScript.

## 6. Décisions et alternatives

| Décision                                                             | Alternative écartée                                    | Raison                                                                                                                                                                                                                                           |
| -------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `jsdom` **29.1.1**                                                   | `jsdom` 30.1.0, la plus récente                        | La 30 exige Node ≥ 22.22.2 ; la machine a Node 22.14.0. L'installation aurait réussi avec un simple avertissement, mais les tests auraient pu échouer de façon imprévisible. La 29.1.1 demande Node ≥ 22.13.0                                    |
| Ajouter `@testing-library/dom`                                       | S'en tenir à la liste de la fiche                      | Dépendance paire obligatoire de `@testing-library/react` 16. C'est un ajout technique imposé, pas un choix : je le signale (règle C10)                                                                                                           |
| Un test d'outillage permanent, en 3 cas                              | Le test temporaire `expect(1 + 1).toBe(2)` de la fiche | Un test qui ne vérifie rien ne protège rien. Celui-ci prouve que jsdom, React et zod fonctionnent ; il peut rester. De plus, `vitest run` **échoue** s'il ne trouve aucun test : supprimer le test temporaire aurait cassé `verify` jusqu'à T1.1 |
| Imports explicites (`import { describe, it, expect } from "vitest"`) | Utiliser les globales de Vitest dans les tests         | Pas besoin d'ajouter les types `vitest/globals` à tout le projet, ni de régler ESLint pour `no-undef`. Chaque test dit d'où viennent ses fonctions                                                                                               |
| Réutiliser `vite.config.ts`                                          | Une configuration Vitest indépendante                  | Une seule source pour le plugin React et l'alias `@` : les tests ne peuvent pas diverger de l'application                                                                                                                                        |
| `zod` en dépendance de production                                    | En dépendance de développement                         | Il valide les données dans le navigateur, à l'exécution                                                                                                                                                                                          |
| `zod` 4                                                              | `zod` 3                                                | Version actuelle, sans raison de prendre l'ancienne. Rappel pour T1.6 : en v4, les erreurs se lisent avec `error.issues` et se mettent en forme avec `z.treeifyError()` ; `error.format()` et `error.flatten()` de la v3 sont dépréciés          |

## 9. Écarts, imprévus et points d'attention

- **`jsdom` 29 au lieu de 30**, à cause de la version de Node (§6). **Si tu mets Node à jour (≥ 22.22.2 ou ≥ 24.15.0)**, on pourra passer à `jsdom` 30.
- **`@testing-library/dom` ajouté**, en dépendance paire obligatoire (§6).
- **Premier lancement des tests lent** (41 s), à cause du démarrage de jsdom sous Windows ; les lancements suivants prennent environ 6 s. À surveiller quand les tests seront nombreux.
- **Exclusions de `coverage/` dans `tsconfig.json` et `eslint.config.js`** : ces lignes sont collées à celles de T0.1 dans les mêmes fichiers, et Git ne peut pas les séparer proprement. Elles partent donc dans le commit de T0.1 (voir la documentation de T0.1, « Modifié par T0.2 »).
- **Hors périmètre, noté et non corrigé :** les 21 vulnérabilités `npm audit` des dépendances existantes.
