## 5. Le code expliqué

### 5.1 `CampaignStudio` — le Studio sur les données de l'application

```tsx
<CampaignStudio
  campaigns={campaigns} prizeTemplates={prizes}          // useCampaigns, usePrizeTemplates
  campaignId={…} onCampaignChange={…}
  onEditCampaignSettings={handleEditFromStudio} onRefreshCampaign={refetchCampaigns}
  onClose={() => setActiveTab("campaigns")}
/>
```

Il construit lui-même ce que le Studio lit : `buildCampaignSnapshot` (ce que le runtime a le droit de voir) et, à part, `buildDemoRules` (probabilité, stock, poids, bonnes réponses, pour la carte des règles en lecture seule). Le sélecteur propose les campagnes non archivées et « Standalone ». `App.tsx` le charge en **lazy** : le Studio et le runtime ne pèsent pas sur le bundle du tableau de bord.

### 5.2 L'onglet « Player Screen » et `/studio`

L'onglet rend le Studio en plein écran (à la place de `PlayerUIMaker`), avec une attente dessinée pendant le chargement. Le bouton **×** de la barre du haut revient aux campagnes. `/studio` rend l'application protégée directement sur cet onglet (`App` reçoit `initialTab`) ; `/ui-maker` redirige vers `/studio`. Le choix « Standalone » est mémorisé par une valeur à part (`"standalone"`), pour que la sélection automatique de la première campagne ne l'écrase pas.

### 5.3 « Edit in campaign settings » : le Wizard par-dessus le Studio

Changer d'onglet aurait **démonté** le Studio : historique d'annulation, aperçu, et une modification en attente de sauvegarde. Le Wizard s'ouvre donc **par-dessus** le Studio (fenêtre plein écran, `z-[110]`), en édition sur la campagne, à l'étape demandée : `rules` → 2 (Game Rules), `prizes` → 3 (Reward Weights), `questions` → 4 (Challenge Builder).

```ts
const handleEditFromStudio = (campaignId, section) =>
  new Promise<void>((resolve) => { … setStudioWizard({ campaign, step: WIZARD_STEP[section] }) });
```

La promesse se résout à la fermeture du Wizard (enregistrement ou « Cancel & Exit »), **après** `refetchCampaigns()` : le Studio reçoit la campagne rechargée, recalcule ses contrôles, et une traduction de question devenue périmée est signalée (T6.11). L'enregistrement passe par la même écriture que le Wizard du tableau de bord (`persistCampaign`, extraite de `handleSaveCampaign`, qui garde sa navigation).

### 5.4 Le Wizard ne crée plus de `uiProject`

- `createProjectForGameType` n'est plus appelé (les deux appels sont retirés, avec l'import).
- La RPC `save_campaign_full_in_place` **écrase** `player_screen_config` : le Wizard renvoie donc la valeur déjà en base, telle quelle (`baseCampaign?.playerScreenConfig`) ; une nouvelle campagne n'en reçoit plus.
- La page publique `/play/:slug` ne lit pas `uiProject` (vérifié) : aucun effet sur les joueurs.
- `initialStep` (1 à 4, défaut 1) ouvre le Wizard sur l'étape voulue. Le bouton de l'étape 4 devient « Customize in Player Studio ».

### 5.5 Aucune modification perdue à la fermeture

`useAutosave` attendait 800 ms après la dernière frappe ; fermer le Studio dans l'intervalle perdait la modification. Au démontage, ce qui attend est désormais écrit aussitôt (test ajouté).

### 5.6 Un défaut du tableau de bord révélé par l'aperçu

Dans le vrai tableau de bord, connecté, **l'aperçu restait vide** : l'iframe était recréée toutes les deux secondes. Cause : l'iframe charge l'application (même origine, même stockage) ; son client Supabase annonce la session de l'utilisateur ; l'`AuthProvider` du tableau de bord réagissait à **chaque** événement d'authentification en repassant `loading` à vrai ; `ProtectedRoute` affichait alors son écran d'attente, **démontait tout le tableau de bord**, donc le Studio et son iframe… qui recommençait. Le même défaut faisait clignoter tout le tableau de bord à l'ouverture d'un second onglet.

Correction dans `AuthContext.tsx` : un événement pour **l'utilisateur déjà chargé** (session relue, jeton rafraîchi, annonce d'un autre onglet) met la session à jour sans écran d'attente ; seuls un autre utilisateur ou `USER_UPDATED` rechargent le profil. Test de non-régression ajouté.

## 9. Écarts, imprévus et points d'attention

- **Données locales** : pour tester connecté, un utilisateur `studio.test@octoreach.local` (mot de passe `StudioTest!2026`) a été **ajouté** à la base locale, rattaché à l'organisation de démonstration « Ooredoo Algeria (Demo) ». Rien d'autre n'a été modifié (le poids changé pour le test a été remis). À supprimer si tu le souhaites : `delete from auth.users where email = 'studio.test@octoreach.local';` (le profil suit en cascade).
- **Le retour avec un vrai enregistrement du Wizard** (et non une modification directe en base) n'a pas été rejoué : l'enregistrement d'une campagne active demande une confirmation supplémentaire. Le chemin est le même (`persistCampaign` puis `closeStudioWizard`) ; à vérifier par toi lors de la recette.
- **Fichiers hors fiche** : `AuthContext.tsx` (§5.6), indispensable au critère « ouvrir l'onglet, sélectionner une campagne et éditer fonctionne » ; `panels/formGame.test.tsx` : le test des segments de la roue (nombreuses modifications) dépassait les 5 s par défaut lors d'une exécution complète en parallèle (il passe seul) — délai porté à 20 s, rien d'autre de changé.
- **Hors périmètre, noté** : l'aperçu en « Full flow (demo) » joue encore avec des chances égales reconstruites du snapshot, pas avec les vraies règles (le pont n'envoie que le snapshot). Proposé pour l'après-MVP.
