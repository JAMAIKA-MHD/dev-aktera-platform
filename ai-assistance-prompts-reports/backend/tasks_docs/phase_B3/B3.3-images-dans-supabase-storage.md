## 1. Objectif

Envoyer les images du Studio (logo, fond, couverture du grattage, cible Hit It, images de lots) dans le bucket `campaign-media` de Supabase Storage, au lieu de les coller dans le design sous forme de texte (data URL). Le design ne garde que leur chemin : la page joueur reste légère sur mobile (diagnostic I2).

## 2. Avant / après

```
Avant : fichier ──► compression ──► data URL collée dans le design (≤ 400 Ko par image)
Après : fichier ──► compression ──► Storage : campaign-media/<organisation>/experience/<campagne>/<usage>-<uuid>.webp
                                    le design garde { kind: "storage", bucket, path }
        affichage : resolveUrl ──► <SUPABASE_URL>/storage/v1/object/public/campaign-media/<chemin>
```

**La compression ne change pas** : mêmes tailles maximales par usage (fond 1920 px, logo 512 px, grattage 1280 px), WebP d'abord, qualité 0,82.

## 5. Le code expliqué

### 5.1 `imageCompression.ts`

Le code **déplacé** depuis `dataUrlAssetStorage.ts` : `MAX_SIDE_BY_PURPOSE`, `ENCODE_QUALITY`, `ImageCodec`, `browserImageCodec`, `fitWithin`, et le choix WebP → PNG (logo) / JPEG (photo).

Nouvelle fonction **`compressImage(file, purpose, codec)`**, qui regroupe les étapes communes aux deux stockages :

1. le fichier doit être une image, sinon `NOT_AN_IMAGE` ;
2. il doit pouvoir être décodé, sinon `UNREADABLE` ;
3. il est redimensionné et réencodé ;
4. le résultat doit être une image, sinon `UNREADABLE` ;
5. l'image décodée est toujours fermée.

**La limite de poids reste à l'appelant**, car elle dépend de l'endroit où l'image est gardée (400 Ko dans le design, 5 Mo dans le bucket).

`dataUrlAssetStorage.ts` garde exactement le même comportement : `compressImage`, puis limite de 400 Ko, puis conversion en data URL. Il **réexporte** les anciens noms : ses 14 tests passent **sans modification**.

### 5.2 `storageUrl.ts`

`publicStorageUrl(supabaseUrl, bucket, path)` → `…/storage/v1/object/public/<bucket>/<chemin>`, chaque segment du chemin étant encodé.

C'est une fonction **pure, hors de `services/supabase/`**, pour que le cadre d'aperçu (runtime) puisse s'en servir en B4.2 sans importer d'adaptateur Supabase (rules §7.3).

### 5.3 `createSupabaseAssetStorage({ client, supabaseUrl, organizationId, campaignId })`

- **`upload(file, purpose)`**
  1. `compressImage`.
  2. Limite du bucket : 5 Mo, sinon `TOO_LARGE`.
  3. Chemin `<organizationId>/experience/<campaignId>/<purpose>-<uuid>.<webp|png|jpg>`. **Le premier dossier doit être l'organisation** : la règle d'envoi du bucket (`campaign_media_org_insert`) n'accepte que le dossier de l'organisation du membre.
  4. Envoi avec `contentType`, `cacheControl: 31536000` (1 an : un nouvel envoi a toujours un nouveau chemin, donc aucune image périmée en cache) et `upsert: false` (jamais d'écrasement).
  5. Renvoie `{ kind: "storage", bucket: "campaign-media", path }`.
  6. En cas d'échec d'envoi (droits, réseau) : `UNREADABLE`, avec le message « The image could not be uploaded. Check your connection and try again. » Le port garde ses 3 codes.
- **`resolveUrl(ref)`** : une référence `storage` donne l'URL publique ; `dataUrl` et `remote` sont renvoyées telles quelles, ce qui garde les anciens designs affichables.

## 6. Décisions et alternatives

| Décision                                | Alternative écartée      | Raison                                                                             |
| --------------------------------------- | ------------------------ | ---------------------------------------------------------------------------------- |
| Même compression que le stockage local  | Envoyer l'original       | Des pages légères sur mobile ; même rendu qu'avant                                 |
| Limite de 5 Mo (celle du bucket)        | Garder 400 Ko            | L'image ne pèse plus sur le design ; la compression la garde de toute façon petite |
| Nom de fichier unique + cache d'1 an    | Écraser le même nom      | Pas d'image périmée en cache, pas d'écrasement concurrent                          |
| Pas de suppression des anciennes images | Nettoyer au remplacement | Plus simple (R6) ; après le MVP                                                    |

## 10. Écarts, imprévus et points d'attention

1. **La cible Hit It n'affichera pas une image Storage.** `runtime/games/hitIt/HitTarget.tsx` lit directement `image.url`. Pour une référence `storage` (qui n'a pas d'`url`), il affiche l'icône de la marque au lieu de l'image. Le fond et le logo passent bien par `resolveUrl`.
   - **Correction prévue en B4.2** (« Images Storage dans l'aperçu »), qui traite précisément de l'affichage de ces images.
   - La couverture du grattage et les images de lots peuvent être envoyées depuis le Studio, mais le runtime ne les affiche pas encore (même avant ce travail) : rien à corriger ici.
2. **Contrôle réel fait en dehors du dépôt** (script jetable) : le bucket et ses règles d'accès existent déjà (migration de juillet) ; aucune modification SQL.
