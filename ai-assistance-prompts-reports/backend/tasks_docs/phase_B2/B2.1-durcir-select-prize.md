## 1. Objectif

Faire appliquer par `select-prize`, la seule autorité sur le résultat d'un joueur, toutes les règles attendues par le nouveau parcours joueur :

- **Consentement obligatoire**, avec sa preuve gardée (loi 18-07, défaut S7).
- **Même tentative rejouée = même réponse** : une coupure réseau suivie de « Réessayer » ne fait plus perdre son lot au joueur (F4).
- **Code coupon unique**, même quand deux gagnants arrivent en même temps (F2).
- **Période de la campagne vérifiée**, et **un code sur chaque erreur** (F5).

La réponse reste compatible avec l'ancienne page joueur.

## 5. Le code expliqué

### 5.1 Structure de `select-prize/index.ts`

- **`json(status, body)` et `fail(status, code, error)`** : toutes les réponses passent par eux, avec les en-têtes CORS. `fail` ajoute toujours `ok: false`, un `code` et le message `error`.
- **`type ErrorCode`** : la liste officielle des 6 codes, à savoir `INVALID_INPUT`, `CONSENT_REQUIRED`, `CAMPAIGN_CLOSED`, `ALREADY_PARTICIPATED`, `DRAW_FAILED` et `SERVER_ERROR`. Le test de contrat du front la lit (§5.4).
- **`readConsent(metadata)`** : exige `accepted === true`, `acceptedAt` (une date valide) et `policyVersion` (non vide) ; `locale` est facultatif. Renvoie une preuve **nettoyée**. C'est elle qui est enregistrée, pas l'objet brut envoyé par le client.
- **`readClientRequestId(metadata)`** : identifiant de tentative (1 à 100 caractères), ou `null`.
- **`loadPrize`** : relit le nom et le message du lot (réponse d'un rejeu).
- **`claimCoupon(prizeId, entryId)`** : appelle la fonction SQL existante `claim_campaign_prize_coupon`. Elle réserve le prochain code libre sous verrou, l'inscrit dans `coupon_redemptions` et sur la participation. `claimCoupon` met ensuite `is_used = true` sur le code, comme l'ancienne version (colonne conservée par cohérence). Si l'appel échoue, le joueur **garde son gain, sans code**, et un avertissement est journalisé.

### 5.2 Les étapes (numérotées comme dans le commentaire d'en-tête)

1. **Entrée :** campagne et téléphone présents ; téléphone algérien valide (`05`, `06` ou `07` + 8 chiffres, après normalisation de `+213…`).
2. **Consentement :** sans preuve valide → `400 CONSENT_REQUIRED`.
3. **Rejeu :** si une participation existe déjà avec **la même campagne, le même téléphone et le même `client_request_id`**, on renvoie sa réponse (lot, code, `game_outcome` minimal) avec `replayed: true`. Rien n'est écrit. Placé **avant** la vérification des doublons, pour que le rejeu ne soit pas pris pour une 2ᵉ participation. Une **nouvelle** tentative du même téléphone (autre identifiant) reste refusée à l'étape 6 : la protection anti-doublon est intacte.
4. **Visite** (`record_campaign_impression`), inchangée, jamais bloquante.
5. **Campagne :** introuvable → `404 CAMPAIGN_CLOSED` ; pas `active` → `400 CAMPAIGN_CLOSED` ; **hors de `start_date`–`end_date`** → `400 CAMPAIGN_CLOSED` (« Campaign is not running. »). C'est la même règle que la lecture publique `get_public_experience` (B1.2).
6. **Doublon :** `max_entries` (1 par défaut) → `400 ALREADY_PARTICIPATED`.
7. **Stock épuisé** → `400 CAMPAIGN_CLOSED` (règle inchangée).
8. **Résultat du jeu :** `resolve_game_outcome` (notation du quiz / Hit It, puis tirage atomique ; un jeu raté perd, B1.3). Erreur SQL → `500 DRAW_FAILED`. Si la fonction répond `ok: false` (la campagne a changé d'état entre l'étape 5 et le tirage) → `400 CAMPAIGN_CLOSED`. Avant, ce cas était enregistré comme une défaite.
9. **Enregistrement :** la participation, avec `metadata = { ...metadata du client sauf human_token, consent, client_request_id, game_type, server_timestamp }`. Collision sur l'index unique `(campagne, téléphone)` (deux requêtes au même instant) → `400 ALREADY_PARTICIPATED`, **avec** son code désormais.
10. **Coupon :** si gagnant, `claimCoupon` **après** l'enregistrement, parce que la fonction SQL a besoin de l'identifiant de la participation.

Réponse : `{ ok: true, entry: { id, redeemed_coupon_value }, prize, coupon, game_outcome }`. L'ancienne page lit `entry.id`, `entry.redeemed_coupon_value`, `prize`, `coupon` et `game_outcome` : tout est présent.

### 5.3 Le script `scripts/backend/select-prize-smoke.mjs` (`npm run backend:smoke`)

- **Il prépare ses propres données** : un modèle de lot (stock 100) avec 40 codes `SMOKE-<run>-NN`, et 6 campagnes (roue, en pause, terminée, Hit It seuil 8, quiz à une question, épuisée). Toutes ont une probabilité de gain de 1, pour que chaque tirage soit gagnant.
- **Il joue en joueur anonyme** : clé anon, directement contre `select-prize`.
- **Il supprime tout à la fin, même en cas d'échec** (`finally`).

### 5.4 Le test de contrat du front (`participation.test.ts`)

Il existait déjà pour **figer la liste des codes d'erreur de `select-prize`**, afin qu'un changement côté serveur soit remarqué. Le changement est ici voulu, donc le test est mis à jour :

- il lit le type `ErrorCode` du serveur (au lieu de chercher `code: "…"` dans le texte) ;
- il fige les 6 codes ;
- il vérifie que chaque code est soit un code du joueur (`ALREADY_PARTICIPATED`, `CAMPAIGN_CLOSED`, `INVALID_INPUT`), soit l'un des 3 codes propres au serveur, que la passerelle de B3.2 traduira (`CONSENT_REQUIRED` → `INVALID_INPUT` ; `DRAW_FAILED` et `SERVER_ERROR` → échec réessayable).

## 10. Écarts, imprévus et points d'attention

1. **Perdant sous forte simultanéité (comportement existant, hors périmètre).** `draw_and_claim_campaign_prize` réserve le stock avec `FOR UPDATE SKIP LOCKED` sur **une seule** ligne de stock par lot. Quand plusieurs joueurs tirent exactement au même instant, ceux qui trouvent la ligne verrouillée **ne l'attendent pas** : ils reçoivent « perdu », même avec une probabilité de gain de 100 %. Dans T8, 3 à 4 joueurs sur 10 perdent ainsi.
   - C'est un choix de la migration `20260702165436` (« graceful non-winner »), pas un effet de B2.1. Aucun stock n'est perdu et aucun code n'est dupliqué.
   - Impact réel faible hors pics : il faut deux tirages dans la même fraction de seconde.
   - **Noté pour après le MVP** : remplacer `SKIP LOCKED` par une attente courte (`FOR UPDATE` simple), pour être équitable.
2. **`prize_templates.item_value` n'existe pas.** Le repli de `claim_campaign_prize_coupon`, utilisé quand plus aucun code individuel n'est libre, lit cette colonne et lèvera une erreur s'il est atteint. `claimCoupon` rattrape cette erreur : le joueur garde son gain, sans code. L'ancienne version tombait dans le même cas sans erreur visible. Hors périmètre ; à corriger dans la fonction SQL après le MVP.
3. **Ordre de déploiement (important).** L'ancienne page joueur n'envoie **pas** de consentement : avec cette version de la fonction, toutes ses participations seraient refusées. La fonction ne doit donc être déployée dans le cloud **qu'après** la nouvelle page (tasks.md B6.3). En local, l'ancienne page ne charge de toute façon aucune campagne (B0.1 §10.3).
4. **Stock perdu si l'enregistrement échoue après le tirage (F3)** : inchangé, accepté pour le MVP.
5. **Vérification du typage Deno :** elle n'est pas faite par le projet (ESLint ignore `supabase/functions`, et Deno n'est pas installé). La fonction a été compilée et exécutée par l'Edge Runtime local sur les 11 scénarios.
6. **Edge Functions :** relancées pour cette tâche (`npx supabase functions serve --env-file .env.local`, 3,8 Go de mémoire libre à ce moment-là) ; elles tournent encore en arrière-plan.
