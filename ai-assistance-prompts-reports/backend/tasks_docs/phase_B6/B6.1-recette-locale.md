## 4. Défauts trouvés et corrections

### 4.1 Défaut n° 1 — deux gagnants simultanés pouvaient recevoir le même code coupon

- **Trouvé par :** `npm run backend:smoke`, scénario T8 (10 joueurs au même instant). Sur un passage, deux gagnants ont reçu `SMOKE-1e504dce-04`.
- **Périmètre :** B2.1 (« coupon réservé sans doublon »). Correction dans un commit `fix(Supabase)` dédié.
- **Cause :** `claim_campaign_prize_coupon` (migration `20260818150000`) choisit le premier code libre avec `FOR UPDATE SKIP LOCKED`. « Libre » veut dire « sans ligne dans `coupon_redemptions` ». Mais cette ligne est dans **une autre table** : le verrou posé sur le code ne la protège pas.
  1. Le joueur A verrouille le code 4, crée sa ligne de `coupon_redemptions`, puis valide.
  2. La requête du joueur B a pris sa photo de la base **avant** la validation de A. Elle arrive sur le code 4 **après** : le verrou est libéré, et, dans sa photo, le code 4 n'a pas de ligne. B le prend.
  3. L'insertion de B dans `coupon_redemptions` tombe sur la contrainte unique : `ON CONFLICT DO NOTHING` n'insère rien, **sans erreur**.
  4. La fonction écrit quand même le code 4 dans la participation de B et le renvoie. Deux joueurs ont le même code.
- **Correction :** migration `supabase/migrations/20260929150000_claim_coupon_without_duplicates.sql`. C'est l'insertion dans `coupon_redemptions` qui décide :
  ```sql
  LOOP
    SELECT … FOR UPDATE SKIP LOCKED;        -- the next free code (fresh snapshot each time)
    EXIT WHEN v_item_id IS NULL;             -- no free code left → same fallback as before
    INSERT INTO coupon_redemptions …
    ON CONFLICT (prize_template_item_id) DO NOTHING
    RETURNING id INTO v_redemption_id;       -- NULL = someone else got this code first
    IF v_redemption_id IS NOT NULL THEN … RETURN v_coupon_code; END IF;
  END LOOP;
  ```
  - Si rien n'est inséré, le code a été pris entre-temps : on essaie le suivant.
  - Chaque tour relit la base avec une photo à jour : la boucle s'arrête quand plus aucun code n'est libre.
  - Tout le reste est **identique** : ordre des codes, mise à jour de la participation, repli sur le modèle, valeur renvoyée, droits (`service_role` seulement, comme B1.1).
- **Preuve (test de charge SQL, `pgbench`, 24 connexions simultanées, 480 réclamations pour 600 codes, 4 tours) :**

  | Version                                | Codes réservés / 480 | Codes donnés à un joueur qui ne les possède pas |
  | -------------------------------------- | -------------------- | ----------------------------------------------- |
  | Avant (copie temporaire de l'ancienne) | 299 à 350            | **119 à 164 par tour**                          |
  | Après (`20260929150000`)               | **480**              | **0** (4 tours sur 4)                           |

  Avec plus de gagnants que de codes (720 réclamations pour 600 codes) : exactement **600** codes réservés, **0** doublon. La boucle s'arrête bien. Les 120 suivantes tombent sur le repli existant, qui lit une colonne absente (`prize_templates.item_value`, déjà noté en B2.1 §10.2 : `select-prize` le rattrape, le joueur garde son gain sans code).

  Le test a créé ses propres données (campagne en pause, 600 codes, 2000 participations fictives) et une copie temporaire de l'ancienne fonction ; tout a été supprimé à la fin (vérifié : 0 campagne, 0 fonction restante).

- **Script `select-prize-smoke.mjs` :** le détail de T8 affiche maintenant le `code` des réponses en erreur (`500:DRAW_FAILED`), au lieu de « lose ». Aucun changement de ce qui est vérifié.
- **Commit :** `fix(Supabase): never hand the same coupon code to two simultaneous winners`.

## 5. Points d'attention (non corrigés)

### 5.1 Erreurs 500 sous 10 appels simultanés, en local

Sur certains passages de `backend:smoke`, avant **et** après la correction, 1 à 6 des 10 appels simultanés de T8 renvoient `500` (`DRAW_FAILED` ou `SERVER_ERROR`).

- **Cause, dans les journaux :** la passerelle locale (Kong) écrit `recv() failed (104: Connection reset by peer) while reading response header from upstream` vers PostgREST. La fonction reçoit « An invalid response was received from the upstream server ». La base, elle, n'enregistre **aucune erreur**.
- C'est la pile Docker locale (connexions entre Kong et PostgREST, machine chargée), pas le code de `select-prize` ni le SQL. Le même test de charge, directement en SQL (§4.1), n'a eu **aucun échec** sur 2 400 réclamations.
- **Effet pour un joueur :** une erreur réseau. La page affiche « Réessayer » et renvoie la **même** tentative (idempotence de B2.1) : pas de double participation.
- **À surveiller en ligne** lors de la recette sur `demo` (B6.3).

### 5.2 Joueurs simultanés qui perdent (déjà noté en B2.1 §10.1)

Le tirage existant (`draw_and_claim_campaign_prize`) ne fait pas attendre un joueur quand le stock est verrouillé par un autre : il perd. Inchangé ; après le MVP.
