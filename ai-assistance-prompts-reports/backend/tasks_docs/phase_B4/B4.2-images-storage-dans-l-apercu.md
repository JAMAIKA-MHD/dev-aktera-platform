## 1. Objectif

Depuis B4.1, une image envoyée depuis le Studio va dans Supabase Storage : le design ne garde que `{ bucket, path }`. Cette tâche fait en sorte que **l'aperçu** (l'iframe `/xp-frame` du Studio et du sandbox) sache afficher ces images, y compris **la cible du jeu Hit It**, qui lisait directement `image.url` (constat de B3.3).

## 5. Le code expliqué

### 5.1 `resolveAppStorage(bucket, path)`

```ts
const base = import.meta.env.VITE_SUPABASE_URL;
return base ? publicStorageUrl(base, bucket, path) : null;
```

L'URL publique d'un objet du projet Supabase de l'application. Elle vit dans `services/storageUrl.ts`, un module pur hors de `services/local/` et de `services/supabase/` : le runtime peut l'importer sans enfreindre ses règles (rules §7.3, vérifié par ESLint).

### 5.2 Le cadre `/xp-frame`

Ses deux « racines de composition », `FrameExperience` (le parcours joueur) et `Stage` (les vues de contrôle), créent leurs services avec `createLocalServices({ …, resolveStorage: resolveAppStorage })`. Le tirage reste en démo : seule la résolution des images change.

### 5.3 La cible Hit It

```ts
const services = useOptionalExperienceServices();
const src = !image
  ? null
  : services
    ? services.assets.resolveUrl(image) // Storage, data URL or remote
    : "url" in image
      ? image.url // on its own: only a URL it already has
      : null;
```

- **Dans l'aperçu et sur la page publique**, la cible est toujours rendue sous un `ServicesProvider` : l'image est résolue comme le fond et le logo.
- **Sans services** (un composant affiché seul, par exemple dans un test), le comportement d'avant est gardé.
- `useOptionalExperienceServices` renvoie `null` au lieu de lever une erreur quand il n'y a pas de fournisseur (`useExperienceServices`, lui, en lève une).

**Aucun changement visuel** : même balisage, mêmes classes, mêmes couleurs du thème. Seule la source de l'image change.

## 6. Décisions et alternatives

| Décision                                   | Alternative écartée                                     | Raison                                                                                    |
| ------------------------------------------ | ------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Résoudre dans `HitTarget` via les services | Passer une URL déjà résolue par le moteur et l'accroche | Deux appelants à modifier au lieu d'un ; la cible est le seul endroit qui affiche l'image |
| Hook facultatif                            | `useExperienceServices` (qui lève une erreur)           | Garder la cible utilisable seule, comme avant                                             |
| URL construite depuis `VITE_SUPABASE_URL`  | La passer par le pont d'aperçu                          | L'iframe fait partie de la même application : elle connaît déjà l'URL du projet           |

## 10. Écarts, imprévus et points d'attention

1. **Changement dans une zone protégée** (runtime, rules §3.1) : `HitTarget.tsx`. Il est **nécessaire** (sans lui, une image de cible envoyée depuis le Studio n'apparaît jamais), **minimal** (la source de l'image seulement) et documenté ici, conformément à rules §3.2.
2. La couverture du grattage et les images de lots ne sont pas affichées par le runtime (déjà avant ce travail) : rien à résoudre pour elles.
