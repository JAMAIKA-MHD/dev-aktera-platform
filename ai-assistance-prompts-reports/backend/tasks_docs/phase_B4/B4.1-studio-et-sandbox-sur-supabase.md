## 1. Objectif

Pour une **vraie campagne**, le Studio lit et enregistre le design sur Supabase (table `campaign_experiences`), et le sandbox du dashboard montre ce même design. Le Studio « autonome » (campagne démo) reste dans le navigateur, comme avant.

## 2. Avant / après

```
Avant : Studio / sandbox ──► createLocalServices() ──► localStorage (tous les cas)

Après : App.tsx ── backend = { client Supabase, URL } ──► CampaignStudio / CampaignSimulator
          vraie campagne (avec organisation) ──► createStudioServices ──► campaign_experiences + Storage
                                                                        (tirages : toujours démo)
          Studio autonome (démo)             ──► createLocalServices   ──► localStorage (inchangé)
```

**Nouveau garde-fou :** si le design enregistré ne peut pas être lu (serveur injoignable), le Studio **n'affiche plus les valeurs par défaut comme si de rien n'était**. Il affiche « Could not load the saved design. » avec « Retry », et **rien ne peut être modifié ni enregistré** tant que la lecture n'a pas réussi. Sinon, la première modification aurait enregistré les valeurs par défaut par-dessus le vrai design.

## 5. Le code expliqué

### 5.1 `useCampaignServices(backend, campaign, rules)`

- Il renvoie `createStudioServices(...)` quand il y a un `backend`, une campagne **et** son `organizationId`. Sinon il renvoie `undefined`, et le composant garde `createLocalServices()` comme avant.
- **Les services sont créés une seule fois par campagne** : `useMemo` sur `backend`, `campaign.id` et `organizationId`, pas sur l'objet campagne. Pourquoi : de nouveaux services déclencheraient un **rechargement** du design, qui effacerait ce que la marque est en train de taper. C'est le cas quand la campagne est relue après le Wizard (un lot renommé).
- Les règles de tirage passent par une référence. Elles ne servent qu'à la passerelle démo propre au Studio. L'aperçu, lui, construit ses propres services dans son iframe.

### 5.2 Le chargement dans `PlayerExperienceStudio`

```ts
loadIntoStudio(store, services.repository).then(
  () => setLoaded(true), // design loaded (or none stored): editing allowed
  (error) => setLoadError(error.message), // server unreachable: editing blocked
);
```

- Avant, `.finally(() => setLoaded(true))` marquait le Studio « chargé » même en cas d'échec.
- `loadAttempt` relance le chargement quand on clique « Retry ».
- `useAutosave({ …, enabled: loaded })` : aucune écriture tant que le design n'est pas chargé.

### 5.3 `StudioShell`

Avec `loadError` :

- un encadré « Could not load the saved design. » remplace les panneaux, avec l'explication, le détail technique et « Retry » ;
- l'aperçu et le bouton « Preview » sont masqués ;
- la barre du haut et le menu restent, ce qui permet de changer de campagne ou de revenir au dashboard.

### 5.4 `useAutosave({ enabled })`

Une référence suit `enabled`. Tant qu'elle vaut `false`, une modification de la configuration ne programme **aucune** écriture. Par défaut `true` : les usages existants ne changent pas.

### 5.5 `App.tsx`

```ts
const STUDIO_BACKEND: StudioBackend = {
  client: supabase,
  supabaseUrl: import.meta.env.VITE_SUPABASE_URL as string,
};
```

Il est passé à `CampaignStudio` (onglet Player Screen, route `/studio`) et à `CampaignSimulator` (le sandbox). L'import du type `StudioBackend` est un `import type` : il n'alourdit pas le bundle du dashboard. Le module Player Experience reste chargé à la demande.

## 6. Décisions et alternatives

| Décision                                           | Alternative écartée                       | Raison                                                     |
| -------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------- |
| Organisation lue sur la campagne                   | Via `useAuth()` dans `App.tsx`            | Déjà chargée par `useCampaigns` ; une dépendance en moins  |
| Bloquer l'édition si le chargement échoue          | Laisser éditer et sauvegarder             | Protège le vrai design contre les valeurs par défaut       |
| Garder le menu et la barre du haut en cas d'erreur | Tout masquer                              | La marque peut changer de campagne ou revenir au dashboard |
| Services stables par campagne                      | Recréés à chaque relecture de la campagne | Un rechargement effacerait la saisie en cours              |

**À vérifier par toi, dans le navigateur** (`npm run dev`, compte de test) :

1. Onglet Player Screen, une vraie campagne : changer le titre de l'accueil, attendre « Saved », recharger la page → le titre est gardé.
2. Ouvrir la même campagne dans un 2ᵉ navigateur (ou une fenêtre privée) → même design.
3. Modifier dans les deux → le second affiche le message de conflit (« saved meanwhile elsewhere… »).
4. « Edit in campaign settings » → enregistrer le Wizard → le design n'a pas bougé.
5. Studio autonome (« Standalone (demo campaign) ») → fonctionne comme avant (navigateur).
6. Sandbox → affiche le design enregistré ; les parties restent en démo (`DEMO-…`), aucune ligne dans les participations.

## 10. Écarts, imprévus et points d'attention

1. **Garde-fou ajouté au-delà de la fiche** : le sandbox affiche lui aussi un message en cas d'échec de lecture, au lieu de jouer les valeurs par défaut.
2. **Deux tout premiers enregistrements simultanés** d'une campagne sans design (deux onglets ouverts avant tout enregistrement) : le 2ᵉ écrase le 1ᵉʳ, car tous deux partent sans version attendue. Cas rare ; tous les enregistrements suivants sont protégés.
3. Les designs déjà faits dans ton navigateur n'apparaissent pas encore sur une vraie campagne : c'est l'objet de **B4.3** (import automatique).
4. Les images envoyées depuis le Studio vont désormais dans Storage ; l'aperçu les affichera après **B4.2**.
