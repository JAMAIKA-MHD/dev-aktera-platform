## 1. Objectif

Un joueur qui **rate** un jeu d'adresse doit **toujours perdre** :

- **Hit It :** moins de touches que le seuil (`win_threshold`) ;
- **Quiz :** score sous le seuil de réussite (`pass_threshold_percentage`).

Aujourd'hui, il peut gagner et consommer du stock (défaut F1 du diagnostic).

## 2. Avant / après

**Avant :** `resolve_game_outcome` notait la partie, puis appelait **toujours** `draw_and_claim_campaign_prize(campagne, réussi)`. Cette fonction ne tient compte d'un échec que si la campagne a `require_quiz = true`. Or `campaignService` ne le met que pour certaines campagnes quiz, et jamais pour Hit It.

```
Hit It raté ──► resolve_game_outcome ──► draw_and_claim(…, passed = false)
                                             └─ require_quiz = false → tirage normal → GAGNÉ possible ✗
```

**Après :**

```
Jeu d'adresse raté  ──► resolve_game_outcome ──► « perdu », sans tirage ✓ (rien n'est consommé)
Jeu d'adresse réussi ──► resolve_game_outcome ──► draw_and_claim(…, true) → tirage normal
Roue, grattage, boîtes ─► inchangé
```

C'est la même règle que le moteur de démo du Studio (`demoDrawEngine.ts`) : l'aperçu et la production se comportent désormais pareil.

## 5. Le code expliqué

La fonction est une **copie** de sa version actuelle (`20260831151000_resolve_game_outcome_rpc.sql`), avec seulement ces changements :

1. **Une constante `v_lost`** : le résultat « perdu », avec la même forme JSON que celui que renvoie `draw_and_claim_campaign_prize` quand on perd :
   ```sql
   v_lost CONSTANT JSONB := jsonb_build_object('ok', true, 'is_winner', false,
     'prize_id', null, 'prize_name', null, 'win_message', null);
   ```
2. **Branches `quiz` et `hit_it`** : après le calcul de `v_passed`,
   ```sql
   IF v_passed THEN
     v_draw_result := public.draw_and_claim_campaign_prize(p_campaign_id, true);
   ELSE
     v_draw_result := v_lost;          -- no draw: nothing is claimed
   END IF;
   ```
   On passe `true` en cas de réussite : le filtre `require_quiz` de `draw_and_claim_campaign_prize` ne peut donc jamais bloquer un joueur qui a réussi. La réponse garde ses champs `score` / `passed` (quiz) et `hits` / `passed` (Hit It), que `select-prize` enregistre dans `entries.quiz_passed`.
3. **`SET search_path = public`** ajouté, bonne pratique de sécurité pour une fonction `SECURITY DEFINER` (rules §5, S7).
4. **Droits réappliqués** : exécutable par `service_role` seulement, comme en B1.1. La migration se suffit ainsi à elle-même.

Tout le reste est identique : vérification de la campagne, notation du quiz, index du segment de la roue, contenu des boîtes mystère.

## 6. Décisions et alternatives

| Décision                             | Alternative écartée                                             | Raison                                                                                                                                                                 |
| ------------------------------------ | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Corriger dans `resolve_game_outcome` | Modifier `draw_and_claim_campaign_prize` (règle `require_quiz`) | Le filtre n'a pas à connaître le type de jeu ; et `draw_and_claim_campaign_prize` est aussi appelée par l'outil de test du dashboard (B1.1), qu'on ne veut pas changer |
| Couvrir aussi le quiz                | Hit It seulement (fiche du plan)                                | Le scénario a montré que le quiz raté gagne aussi quand `require_quiz = false`                                                                                         |
| Copier la fonction entière           | Une fonction « enveloppe »                                      | PostgreSQL ne permet pas de modifier une partie d'une fonction ; une copie fidèle est la façon la plus lisible                                                         |

## 7. Tests

Scénario SQL, dans une **transaction annulée** (aucune trace en base) :

- une campagne Hit It (seuil de 8 touches) et une campagne Quiz (1 question, seuil de 100 %), toutes deux `active`, avec `win_probability = 1` (tout tirage gagne), `require_quiz = false`, et 1 lot en stock ;

Le scénario est dans le journal de cette tâche. Il n'est pas commité : une vérification ponctuelle, pas un test permanent. Le script de B2.1 couvrira ces cas de bout en bout par `select-prize`.

## 10. Écarts, imprévus et points d'attention

1. **Le quiz était aussi touché**, pas seulement Hit It : dès que `require_quiz` vaut `false` sur une campagne quiz, par exemple une campagne dont le type a été changé en quiz après sa création. Corrigé en même temps, avec la même règle.
2. `draw_and_claim_campaign_prize` garde son paramètre `p_quiz_passed` et son filtre `require_quiz` : l'outil de test du dashboard s'en sert encore.
